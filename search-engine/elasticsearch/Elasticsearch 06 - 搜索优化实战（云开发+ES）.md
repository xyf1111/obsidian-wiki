# Elasticsearch 06 - 搜索优化实战（云开发 + ES）

> 用 Elasticsearch + 腾讯云开发优化网站搜索的完整实战：从数据库模糊查询的痛点出发，经历技术选型、ES 集群搭建、公共服务封装、索引设计、数据同步到检索接口改造的全流程。

## 背景

网站搜索此前用数据库模糊查询（包含）实现，开发简单但很不灵活，典型问题：

- **空格问题**：资源名为「Java 设计模式」，用户搜「Java设计模式」搜不出来，因为关键词不含空格。
- **词序问题**：资源名为「Java 并发编程实战」，用户搜「Java 实战」，明明两个词都包含，却什么都搜不出来。

搜索功能对信息聚合类站点至关重要，直接影响用户体验。随着用户量增大，必须优化。

## 技术选型

提高搜索灵活性可以使用**全文搜索**技术，前端和后端都可实现。

**前端全文搜索**

适用于数据有限且全部存储在客户端（如个人博客文章以文件形式存放）的场景，无需从服务器请求动态数据。现成库如 `Lunr.js`：

```js
var idx = lunr(function () {
  this.field('title')
  this.field('body')
  this.add({ title: "yupi", body: "wx搜程序员鱼皮，阅读我的原创文章", id: "1" })
})
idx.search("鱼皮")
```

优点：无需后端、简单方便、节省服务器压力、无需联网、无额外网络开销、检索快。

**后端全文搜索**

在服务器上完成，从远程数据库搜索后直接返回给前端。主流技术是 **Elasticsearch**——分布式、RESTful 风格的搜索和数据分析引擎。功能强大灵活，但需要自己搭建、定义数据、管理词典、上传维护数据，可操作性很强，新手和大佬设计出的 ES 搜索系统差距很大。

不熟悉 ES 的同学可直接用现成全文检索服务，如 **Algolia**：通过其 API 上传数据、再调用其 API 检索即可，提供一定免费空间，适合小型网站和学习使用。

**选择**

编程导航最终选择自建 ES 搜索引擎，原因：

- 资源数不固定、无规律动态更新，不适合前端全文检索；
- 日后数据量较大，且可能按用户搜索动态优化检索系统（如自定义编程词典），自建可任意定制；
- 不用向其他平台发送网站数据，保证数据安全。

## ES 安装选型

**自建**：购买服务器按官方文档手动安装。搭建不难，但后期维护成本巨大——性能分析、监控、告警、安全都要自己配置；数据量大了还要考虑集群搭建、水平扩容。

**云服务**：选择腾讯云 ES，自动搭建现成 ES 集群服务，提供可视化架构管理、集群监控、日志、高级插件、智能巡检等功能。虽然价格贵，但节省大量时间成本，值得。

> 另有定制化搜索服务 Elastic App Search 可尝试。

## ES 公共服务

目标不是直接写业务逻辑，而是先开发一个公共的 ES 服务。ES 操作可以简单理解为数据库，公共服务应具备基本增删改查供其他函数调用。

**Node 连接**

后端用腾讯云开发 + Node.js，选用官方推荐的 `@elastic/elasticsearch` 库。为保证数据安全，使用**内网地址**连接：

```js
const client = new Client({
  node: 'http://10.0.61.1:9200',  // 内网地址
  auth: {
    username: esConfig.username,
    password: esConfig.password,
  },
});
```

**switch 封装增删改查**

做一步抽象：用 `switch` 分支根据请求参数区分操作，不用把每个操作独立写成接口。云开发中函数久未调用会释放资源，下次请求冷启动导致返回较慢，把多个操作封装到同一函数也能减少冷启动几率。

```js
const { op, index, id, params } = event;
switch (op) {
  case 'add':    return doAdd(index, id, params);
  case 'delete': return doDelete(index, id);
  case 'search': return doSearch(index, params);
  case 'update': return doUpdate(index, id, params);
}
```

**本地调试**：用云开发自带 `tcb` 命令行工具本地执行函数。先把 ES 连接地址改成公网，再执行：

```
tcb fn run --name <functionName> --params "{\"op\": \"add\"}" --path <functionPath>
```

执行成功后可通过 Kibana 面板或 curl 在 ES 中看到新插入的数据。

**远程测试**：本地测试通过后把 ES 连接地址改回内网 IP 并发布到云端，编写其他函数通过 `callFunction` 请求公共服务：

```js
function addData() {
  app.callFunction({
    name: 'esService',
    data: { op: 'add', index: 'resource', id, params: data },
  });
}
```

**内网配置**：远程请求返回超时，日志显示 ES 连接不上——原因是云函数所在机器和 ES 不在同一内网。需要在云开发控制台更改 ES 公共服务的**私有网络配置**，选择和购买 ES 时相同的子网，修改后即可插入成功。

## 数据索引

建立索引（类似数据库的表）来约定数据类型、分词等信息，不允许随意插入数据。

**ik 中文分词器 mapping 示例**：资源名指定为 `text` 类型开启分词，用 `ik_max_word` 做索引分词、`ik_smart` 做搜索分词，并挂 `keyword` 子字段用于精确匹配：

```json
{
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "analyzer": "ik_max_word",
        "search_analyzer": "ik_smart",
        "fields": {
          "keyword": { "type": "keyword", "ignore_above": 256 }
        }
      },
      "likeNum": { "type": "long" }
    }
  },
  "aliases": { "resource": {} }
}
```

- 点赞数用 `long` 类型，只允许传数字；
- 为索引指定**别名**（aliases），便于后续修改字段时重建索引；
- 配置好后通过 curl 或 Kibana 调用 ES 新建索引接口即可。

## 数据同步

数据库资源数据需同步到 ES。三种策略对比：

| 策略 | 做法 | 优缺点 |
| --- | --- | --- |
| **双写** | 插入数据库时同时插入 ES | 要改动所有写数据库的旧代码；存在一边写成功、另一边失败导致数据不一致的风险 |
| **定时同步** | 每隔一段时间把最新插入/修改的数据从数据库复制到 ES | 对现有代码侵入最小，完全不用改代码；不实时 |
| **实时同步** | 监听数据库 binlog，任何变更立即感知 | 实时性最高；需引入 Canal 等组件 |

- 定时同步实现方式：`Logstash` 数据传输管道，或自己编写定时任务程序。
- 实时同步：阿里开源项目 `Canal` 可实时监听 MySQL 并推送通知给下游。

**实战选择**：编程资源搜索对实时性要求不高，选**定时同步**。云开发默认提供定时函数功能，写一个云函数**每 1 分钟执行一次**，每次读取数据库中**近 5 分钟内**发生变更的数据（防止上次执行失败遗漏），并配置**超时时间**防止执行时间过长失败。crontab 表达式可在云开发 - 云函数控制台可视化配置。

开启定时同步后，还要编写并执行一个**首次同步函数**，把历史全量数据同步到 ES。

## 数据检索

- **Kibana 调试**：ES 搜索 DSL 语法（取列、搜索、过滤、分页、排序）对新手有些麻烦，尤其是布尔表达式组合，稍不注意就查不出数据。建议先在 Kibana 调试工具中编写查询语法，查出预期数据后再编写后端搜索函数。
- **接口兼容**：后端搜索函数接受的请求参数尽量与原接口保持一致，减少改动。
- **动态拼接**：根据前端传来的请求动态拼接查询语法，如按资源名搜索：

```js
if (name) {
  query.bool.should = [{ match: { name } }];
}
```

**新旧接口并存**：新 ES 搜索接口发布不意味着老数据库查询接口淘汰，可同时保留——按名称搜索资源用新接口（更灵活），审核状态、搜索某用户发布过的资源等场景用老接口从数据库查。分摊负载、职责分离，让对的技术做对的事情。
