# Java 设计 07 - 评论功能设计方案

> 前后端嵌套评论功能实现方案总结：前端两种显示方式（前端状态判断 / 后端数据驱动）+ 后端两种存储方案（单表简单方案 / 双表流水号完备方案）。

## 一、前端显示方案

### 问题背景

不同角色看到的评论操作不同（如本人发布的评论可编辑修改，且逻辑上不能举报自己），同一页面需要状态量控制不同页面元素的显隐。

### 方案一：前端设置状态量，后端维护数据特征

前端根据后端返回的数据特征自行维护状态量、完成逻辑判断，判断结束后前端即可实现不同情况的合理显示。该方案后端省事，前端需自己做相当一部分判断。

**优势：**

1. 前后端职责分明：前端负责逻辑判断与显示，后端专注于数据维护
2. 前端自由度高：可更灵活地处理和呈现不同状态，定制化程度较高
3. 性能优化：前端按需控制页面显示逻辑，减轻后端负担

**不足：**

1. 前端逻辑复杂：需处理复杂的状态判断和页面显示逻辑，增加开发难度
2. 可能重复逻辑：多个地方需要类似状态控制时，需重复实现相同逻辑

### 方案二：数据驱动，后端返回状态量

后端在返回评论信息时，将状态量一并返回给前端，前端专注于状态量判断和显示，后端专注于状态量维护（数据本就从此返回，维护方便）。

**优势：**

1. 简化前端逻辑：前端只需根据后端返回的状态量做简单判断
2. 统一数据源：状态相关信息均来自后端，避免状态不一致
3. 后端灵活性：修改状态相关逻辑无需修改前端代码

**不足：**

1. 前后端关联紧密：逻辑高度耦合，后端需考虑更多前端逻辑，开发难度增加
2. 性能考虑：需传输更多数据到前端，增加网络传输成本

### 选型考虑

| 考虑因素 | 倾向方案 |
|----------|----------|
| 项目对前端交互有较高定制需求 | 方案一 |
| 团队前端技术水平高，能轻松处理复杂逻辑 | 方案一 |
| 后端能方便地维护状态逻辑 | 方案二 |
| 对网络传输和前端性能要求较高 | 方案一 |

> 实际应用中可综合两种方案：简单的状态量由后端返回，复杂的逻辑由前端处理。

## 二、后端存储方案

### 评论结构划分

评论功能的关键在于如何合理存储评论的嵌套和父子关系，可做如下结构划分：

1. **文章-一级评论（父级评论）**：用户对文章做出的评论
2. **一级评论-二级评论（父-子评论）**：其他用户对文章评论的评论，以及父级评论者对这些评论的回复，即评论者之间的交互——此时已与文章无关

### 简单方案：单表 article_comment

除文章表外，只设计一张评论表，字段包括：

- `articleId`：文章 id
- `senderId`：发送者 id
- `receiverId`：接收者 id
- `comment`：评论内容

**实现方式与限制：**

- `receiverId` 为空表示该条评论针对文章，反之针对评论者
- 同一个人对一篇文章最多只能有一条评论，才能保证三元组（articleId-senderId-receiverId）的唯一性，即他人对某评论的回复才能保证唯一
- 该方案下被评论者无法对评论者进行回复
- 未实现两级评论的解耦（文章-评论、评论-评论）
- 若业务能容忍以上限制，可非常简单快速地实现评论功能

### 完备方案：两张表

除文章表外设计两张表，突破简单方案的限制，实现完整的多级评论功能。

**article_comment（评论内容表）：**

- `articleId`：文章 id
- `userId`：评论者 id
- `callId`：流水号，作为该条记录的唯一标识
- `comment`：评论内容

**comment_relation（评论关系表）：**

- `userId`：评论者 id
- `comment`：评论内容
- `self_callId`：该条记录的流水号，唯一标识
- `target_callId`：被评论那条记录的流水号，来源有两个：① article_comment 表中的 callId（父级评论的流水号）；② comment_relation 表中其他记录的 self_callId

通过这两张表即可实现多级评论和回复。

### 关键设计：为什么用流水号 callId 而不用 id

1. **id 可能冲突**：`target_callId` 的来源跨两张表，若用记录 id，两个表各自的 id 可能重复造成冲突
2. **callId 唯一性**：流水号是该方案的核心，必须保证其唯一性
3. **核心价值——评论与被评论对象解耦**：无需关注评论者的具体信息，只需将流水号作为唯一标识，父级关系用 target 与 self 区分；若把文章评论换成歌曲评论，只需修改 article_comment，comment_relation 可直接复用，实现了评论与被评论之物的解耦

## 三、两方案对比与选型

### 方案对比

| 维度 | 简单方案（单表） | 完备方案（双表） |
|------|------------------|------------------|
| 表结构 | 一张 article_comment | article_comment + comment_relation |
| 多级评论和回复 | 不支持 | 支持（核心优势） |
| 两级解耦 | 未实现 | 评论与被评论对象解耦 |
| 易实现和维护 | 结构简单，前后端开发轻松 | 结构复杂，维护成本较高 |
| 性能 | 表结构简单，查询操作有一定优势 | 相对复杂 |
| 灵活性/扩展性 | 低 | 高，流水号设计便于扩展点赞、举报等功能 |
| 定制化程度 | 低 | 高，适用复杂业务场景 |
| 可复用性 | 低 | 高，comment_relation 可复用于其他社交互动模块 |

### 选型建议

- **简单方案适用**：简单的评论系统、不需要多级回复、对数据库设计与维护要求较低的场景，可减少系统复杂性
- **完备方案适用**：复杂的评论系统、需要支持多级评论和回复、对系统扩展性和定制化程度要求较高的场景
- **总体原则**：根据具体业务需求、系统规模和团队技术水平决定，简单场景选简单方案，对评论系统要求更多时选完备方案
