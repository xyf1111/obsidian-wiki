# MySQL 19 - 误更新全表事故处理与数据安全

> 真实线上事故复盘：执行单元测试更新数据时少写一个 WHERE，全表用户变成管理员——比删库更可怕（数据污染 + 越权），从紧急止血、备份恢复到 5 项预防机制全流程拆解。

## 核心要点

### 事故还原

- 员工执行单元测试更新数据时少加了 where 条件：

```sql
-- 预期：只更新 id=1 的用户
update user set userRole = 'admin' where id = 1
-- 实际执行：全表所有用户都变成管理员
update user set userRole = 'admin'
```

- 后果比删库更严重：删库直接恢复即可，这次既有**数据污染**又出现**越权**——仅管理员可见的敏感信息存在泄露风险

### 紧急处理流程（止血 → 恢复）

1. **防扩散（第一时间）**：先把 user 表所有角色重置为普通用户，防止有人继续利用管理员权限做坏事（此时还能依据 VIP 信息 + 程序日志判定用户原本身份）
2. **停止线上前后端服务**：便于后面恢复数据；同时防止用户发现自己突然从会员降级，引发大量人工咨询
3. **数据恢复**：得益于分钟级备份，直接把数据恢复到事故发生前的最近正常时间点
4. **增量数据同步**：恢复备份时间点之后新增的用户数据
   - 策略：更新 `updateTime > 事故时间` 的数据，按 id 点对点覆盖除 userRole 外的列；无对应 id 则新增（类似 `saveOrUpdate`）
   - **坑**：updateTime 是修改时自动更新的字段 → 所有数据都是最新时间，相当于全量数据都要比较一遍
   - 单线程太慢 → 多线程分批同步：每 1000 条一组，`CompletableFuture.runAsync` + `saveOrUpdateBatch` 并发执行，`allOf().join()` 等待全部完成
   - 更优方案：联表查询、对比哪些行发生了变动再修改（当时情况紧急 + 数据量级可控，选了理解成本最低的方式）
5. **上线前全量备份** + 思考是否还有遗漏，才恢复上线

### 事故时间线（总时长约 2 小时）

| 环节 | 耗时 |
|------|------|
| 人工发现事故（靠用户反馈，非监控） | 30 分钟 |
| 定位问题 | 5-10 分钟 |
| 策略制定与同步 | 5-10 分钟 |
| 数据备份恢复 | 15 分钟 |
| 增量数据同步 | 40 分钟 |
| 上线前备份 + 其他考虑 | 10 分钟 |

### 5 项预防措施

1. **控制操作权限**：禁止不带 where 条件的 update / delete；MySQL 开启 `sql_safe_updates` 配置——缺少 where 的更新直接报错拒绝执行
2. **生产环境隔离**：不允许本地直连线上数据库；先写代码 → 提交审核 → 发布上线后再执行修改；规模上来后本地 / 测试 / 预发布 / 线上环境必须严格区分（小团队图省事共用一库是事故温床）
3. **SQL 审批**：修改关键库数据不能直接执行 SQL，先提交到审核平台，领导和数据库运维确认后才能执行——每条 SQL 至少 2 个人看过
4. **数据库审计**：记录和监控数据库访问及 SQL 执行情况，精细化风险控制（自建：开启日志 / 审计插件；或使用云服务自带审计规则）
5. **提升风险意识**：让团队所有同学认识到事故的严重性——再多的防护也限制不了故意搞事的人

### 做得好的地方

- **完整又灵活的数据备份（分钟级）是线上项目必备**——本次能快速恢复全靠备份，无备份后果不堪设想
