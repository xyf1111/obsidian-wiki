# Redis 08 — Redis Cluster 集群

## 为什么需要集群

| 场景 | 单节点问题 | 集群方案 |
|------|-----------|---------|
| 数据量 > 内存 | 放不下 | 数据分片 |
| 单点故障 | 宕机服务不可用 | 主从切换 |
| QPS 过高 | 单节点瓶颈 | 多节点分摊 |

## 数据分片

Redis Cluster 使用 **16384 个哈希槽**（hash slot）进行数据分片：

```bash
# CRC16(key) % 16384 → 分配到对应节点
HASH_SLOT = CRC16(key) & 16383
```

### 槽位分配

```
Node A: 0-5460
Node B: 5461-10922
Node C: 10923-16383

写 key="user:123":
CRC16("user:123") % 16384 = 4500
→ 路由到 Node A
```

### 添加/移除节点

```bash
# 添加节点（自动迁移部分槽位）
redis-cli --cluster add-node 新节点:6379 现有节点:6379

# 重新分片
redis-cli --cluster rebalance 任意节点:6379

# 移除节点
redis-cli --cluster del-node 节点:6379 节点ID
```


## 集群内部通信与槽位路由细节

### 每个节点都存着整份拓扑

集群里没有"元数据服务器"，**每个节点本地都保存完整的集群视图**，而不只是自己负责的槽：

| 字段 | 含义 |
|------|------|
| 节点 ID | 40 位十六进制串，创建后终身不变（IP 换了身份也不变） |
| IP / 端口 | 客户端服务端口 + 集群总线端口 |
| 角色 | master / slave，以及所属 master 的 ID |
| 槽位归属 | 用 bitmap 记录（是"哪些槽"，不是"哪段区间"） |
| 状态 | online / PFAIL / FAIL |
| epoch | `configEpoch`（槽位归属版本）+ `currentEpoch`（集群版本） |

节点间通信走独立的 **cluster bus**，不是客户端那条连接：

```
服务端口 6379        ← 客户端，RESP 文本协议
总线端口 16379       ← 节点间，二进制协议（= 服务端口 + 10000）
```

- 总线端口固定为 **服务端口 + 10000**（7000 → 17000），部署时防火墙/安全组必须双向放通，否则节点互相看不见、集群一直处于 fail 状态
- 用二进制协议 + 固定头部，因为它要**高频携带完整拓扑**，RESP 文本太胖
- 只跑节点间的事：握手、心跳、故障广播、槽位变更通知、集群内 Pub/Sub 转发

### Gossip：随机抽样，不是全网广播

心跳节奏（每 100ms、随机 5 个节点）见下文「主从与故障转移」，这里只讲**传播机制**：

- 每轮从候选节点里挑 **1 个最久没通信过**的发 `PING`，对方回 `PONG`。选"最久未通信"而非纯随机，是为了保证每个节点都会被覆盖，不会长期漏掉某个角落
- 每个 PING/PONG 除自身信息外，还捎带约 **1/10** 的其他节点信息（gossip 段），一次交互就顺带传播了第三方的状态
- 因此信息呈**指数扩散**：约 `O(log N)` 轮全网收敛，总消息量 `O(N log N)` 而不是广播的 `O(N²)`
- 这种"随机挑一个、用局部交换逐步抹平差异"的思路就是**反熵（anti-entropy）**：无中心、无全量同步，代价是**最终一致**——拓扑变更存在秒级窗口，期间可能拿到旧路由，所以必须有 MOVED 兜底
- 单节点的判断只是"个人意见"：PFAIL 是本地视图，必须凑够多数派才升级成 FAIL

| 消息 | 方向 | 作用 |
|------|------|------|
| `MEET` | A → 新节点 B | 握手邀请，效果等同"强制 B 把我加进它的节点表"，`CLUSTER MEET` 与新节点入群用它 |
| `PING` | 任意 → 任意 | 周期心跳，携带自身槽位 bitmap、角色、epoch 和 gossip 段 |
| `PONG` | 收到 PING/MEET 后回复 | 同 PING 的载荷，作为存活确认；也可主动发（如槽位变更后通知对方） |
| `FAIL` | 判定方 → 全网 | 某 master 被多数派确认下线后广播，收到即落库为 FAIL 并触发其从节点选举 |

除此之外还有 `PUBLISH`（集群内广播业务消息）和 `UPDATE`（通知对方更新槽位配置）等。

### 故障判定与 epoch 抬升

```
1. A 在 cluster-node-timeout 内没回 PONG → B 本地标记 A = PFAIL（带过期时间，仅代表 B 的看法）
2. B 通过 gossip 段把自己的 PFAIL 看法传出去，其他 master 独立验证
3. 超过半数 master 都认为 A = PFAIL → 其中一方广播 FAIL A
4. FAIL 全网生效，同时 currentEpoch + 1
5. A 的从节点带着最新 epoch 发起选举，向各 master 拉票，票数过半且 epoch 最大者当选
6. 新 master 用自己的 configEpoch 接管槽位并广播，其他节点更新槽位表
```

- **currentEpoch**：集群级单调递增版本号，故障、选举、槽位变更都会 +1，用来给"同一件事的多份报告"排序、去重
- **configEpoch**：每个 master 各持一个，冲突时**大者胜**，保证一个槽只有一个合法主人
- 这也解释了为什么至少要 3 个 master：2 个 master 时"半数以上"就是 2，任一宕机就永远凑不够票，故障确认和选举全部停摆

### 为什么是 16384 而不是 65535

槽位不是用"区间"存的，而是 `myslots[CLUSTER_SLOTS / 8]` 这样的**位图**：第 i 位为 1 表示"我有槽 i"。这个位图是心跳消息头里最占空间的部分：

| 槽位数 | 位图大小（slots ÷ 8 ÷ 1024） | 每个心跳包头部 | 结论 |
|--------|------------------------------|---------------|------|
| **16384（2^14）** | 16384 / 8 / 1024 = **2 KB** | 2 KB | 作者选定，够用且轻 |
| 65536（2^16） | 65536 / 8 / 1024 = **8 KB** | 8 KB | 心跳频繁，4 倍带宽纯属浪费 |

1. **消息大小**：心跳本身不装业务数据，头部就该尽量小。65536 个槽时消息头直接膨胀到 8KB，浪费带宽；16384 只要 2KB
2. **集群规模**：官方建议节点数不超过 **1000**。16384 / 1000 ≈ 16 个槽/节点，仍然能均匀分片；槽再多也没有实际分配意义
3. **传播成本**：位图会随 gossip 在 N 个节点间反复传，2KB → 8KB 意味着全网流量翻 4 倍
4. **与 CRC16 天然匹配**：CRC16 输出 16 bit（0~65535），取低 14 位（`& 16383`，等价于 `% 16384`）即得槽号，不需要额外哈希；用 65536 反而要多处理取模分布，毫无收益

### 一次 GET 的三种结局

| 服务端返回 | 触发条件 | 客户端动作 |
|-----------|---------|-----------|
| 正常值 | 槽归本节点且数据就在本节点 | 直接用，无重定向 |
| `-MOVED <slot> <ip:port>` | 槽属于别的节点（本地槽位表已是新的） | 更新本地 slot→node 缓存并重发，后续同槽请求不再问 |
| `-ASK <slot> <ip:port>` | 槽正在迁移，key 已搬走但槽还没正式过户 | **只这一次**带 `ASKING` 前缀转发，**不更新**缓存 |

```
MOVED：槽归属已确定，缓存长期生效
client → Node1: GET user:1001
client ← Node1: MOVED 12345 10.0.0.3:7000
client → Node3: GET user:1001       ✅ 并缓存 12345 → Node3

ASK：迁移中的临时跳转，用完即弃
client → Node1: GET user:1001
client ← Node1: ASK 12345 10.0.0.3:7000
client → Node3: ASKING + GET user:1001   ⚠️ 仅此一次，不写缓存
```

- `ASKING` 不能省：目标节点此时对该槽处于 IMPORTING 状态，不带 `ASKING` 会直接回 MOVED，两边来回踢皮球
- 客户端缓存槽位表后绝大多数请求一跳命中，只有扩容/故障转移期间才会多一跳
- go-redis / Jedis / Lettuce 都内置这套逻辑，业务代码无感（见上文「客户端访问」）

迁移与主从切换的基础机制见 [[Redis 04 - 主从复制]]。

## 主从与故障转移

### 节点通信

```
Gossip 协议：
每隔 100ms Ping 随机 5 个节点
交换集群状态：节点存活、槽位信息、配置纪元
```

### 故障检测

```bash
# 节点标记 PFAIL（疑似下线）
# 半数以上 Master 标记 PFAIL → FAIL（确认下线）
# Slave 自动升级为 Master
cluster-node-timeout 15000  # 15s 无响应判定为宕机
```

### 故障转移

```
1. Master A 宕机
2. 其他节点检测到 PFAIL → FAIL
3. Master A 的 Slave 发起选举
4. 多数 Master 投票同意
5. Slave 成为新 Master
6. 槽位分配给新 Master
（整个过程 ~10-15s）
```

## 集群限制

| 限制 | 说明 | 解决方案 |
|------|------|---------|
| **多键操作** | `MGET`/`MSET` 跨槽位报错 | 使用 hash tag |
| **事务** | `MULTI`/`EXEC` 跨节点不支持 | Hash Tag 让 key 在同一个槽 |
| **Pipeline** | Pipeline 跨节点会变慢 | 按节点分组 |
| **Lua 脚本** | 脚本涉及的 key 必须在同一个节点 | Hash Tag |
| **大 Key** | 无法分片 | 业务拆分 |

### Hash Tag

```go
// 普通 key：可能分布在不同节点
key1 = "user:123:profile"
key2 = "user:123:orders"

// 使用 Hash Tag：确保在同一个槽位
key1 = "{user:123}:profile"
key2 = "{user:123}:orders"

// Hash Tag 规则：只对 {} 内的内容计算 CRC16
// 所以 {user:123} 的哈希值相同
HASH_SLOT("user:123".CRC16())  // 相同！
```

## 哨兵 vs 集群

| 对比 | Sentinel（哨兵） | Cluster（集群） |
|------|-----------------|----------------|
| 数据分片 | ❌ | ✅ 16384 个槽 |
| 高可用 | ✅ 自动切换 | ✅ 自动切换 |
| 水平扩展 | ❌ 不能扩分片 | ✅ 在线扩容 |
| 客户端 | 连接哨兵获取 Master | 连接任意节点自动路由 |
| 最大节点 | 一般 3-5 个 | 理论 1000+ |
| 最小部署 | 1主1从+3哨兵 | 6节点（3主3从） |
