# DevOps 11 - 多环境管理（环境隔离与配置）

> 多环境：根据实际需要，将同一个项目（同一套代码）区分出多个可**同时存在、互不影响**的运行环境（本地/开发/测试/预发布/生产）。实现原理三步走：抽象配置类 → 配置文件化 → 注入环境参数。

## 为什么需要多环境

- 场景：数百万用户正在使用的网站，要开发上线新功能——直接更新服务器文件？代码有 Bug 会立即影响线上用户
- 写好代码先在本地测试再上线？如果本地和线上连接**同一个数据库**，本地测试插入的假数据、修改的表结构都会影响线上数据
- 结论：需要把环境隔离开，让本地/开发环境的折腾不影响线上用户

## 常用环境（5 种，约定俗成）

环境不是越多越好：搭建要额外工作量，依赖资源越多成本越高、维护越麻烦。企业中常用的就几种（不同团队划分方式可能不同）：

| 环境 | 标识 | 用途与特点 |
|------|------|-----------|
| 本地环境 | local | 前端/后端独立开发、自主测试；项目与依赖（数据库/缓存/队列等）跑在自己电脑上，需自行搭建 |
| 开发环境 | dev | 前端后端（多程序员）一起协作开发、联调；项目与依赖放在员工可直接访问的开发机上，不用自己搭；小团队 local + dev 一套就够（本地可连公用数据库） |
| 测试环境 | test | 开发联调完成、做出完整功能后交给测试同学找 Bug；通常配独立测试数据库；每次改完 Bug 都要重新发布让测试复验 |
| 预发布环境 | pre | 最接近线上：调用的后端接口、数据库、服务**与线上一致**，唯一区别是前端访问域名不同；因此能看到真实用户数据，可发现测试环境因数据不足查不出的 Bug；测试通过、产品经理体验过才能发布到此 |
| 生产环境 | prod | 线上环境，真实用户使用；不能随意修改、发布必须格外小心；机器/数据库资源由专业运维负责，登录机器、改配置需严格审批 |

## 如何实现（三步原理：搞多套配置）

### 1. 抽象配置类

把代码中随环境变化的变量集中到配置类管理，避免「死值」散落多处难以维护：

```java
// 数据库配置类
class DBConfig {
  String ip = "10.0.0.1";
  int port = 3306;
  long timeout = 1000L;
}

// 从类中获取
DB db = new DB();
db.setIp(cf.getIp());
db.setPort(cf.getPort());
```

### 2. 配置文件化

用专门配置文件维护配置，用户改配置不用找代码、改代码。常见格式：`properties`、`yaml`、`yml`、`json`：

```properties
# db.properties
db.ip=10.0.0.1
db.port=3306
db.timeout=1000
```

想加载哪个配置文件就加载哪个——搞一套测试环境配置，只需新建 `db-test.properties`（文件名中加环境名）并加载它即可。前端后端大部分多环境实现都是这个原理，所以项目中总能看到一堆 `application-dev.yml` / `application-prod.yml` 之类的文件（Spring Boot 多环境配置见 [[java/路线/Java 44 - Spring Boot 学习路线|Spring Boot 学习路线]]）。

### 3. 注入环境参数

前两步仍需在代码里写死「加载哪个文件」，上线前改代码既麻烦又可能忘记（把开发环境项目发到线上）。理想效果：**切换环境时整个项目零修改**——把「指定环境」留到打包/启动时通过命令注入：

```bash
# 测试环境
java -jar -Denv=test dist.jar
# 生产环境
java -jar -Denv=prod dist.jar
```

```java
// 程序读取参数，加载对应配置
String env = System.getProperty("env");
new DBConfig("db-" + env + ".properties");
```

前端同理：打包构建时传入环境变量，代码中读取或交给 Webpack 等打包工具处理：

```json
{
  "scripts": {
    "serve": "env=dev serve",
    "build:test": "env=test build",
    "build": "env=prod build"
  }
}
```

## 更进一步

企业中多环境比这复杂得多：除了代码区分环境，**流水线、镜像、容器**也通通要区分（CI/CD 见 [[devops/cicd/CI CD 04 - 学习路线与系统指南|CI/CD 学习路线与系统指南]]）。但原理都是一样的。环境差异/配置差异正是本地运行正常、上线出 Bug 的常见原因，预防手段见 [[devops/DevOps 09 - 本地运行正常上线出 Bug 的原因与预防|DevOps 09 - 上线事故预防]]。
