# 工具 35 - 第三方评论插件接入（Gitalk）

> 评论是网站的高频通用需求，用大厂开源的 Gitalk 插件，几行代码就能接入评论功能，且评论数据存放在 GitHub Issues 中、无需自己准备服务器。

## 一、为什么不自研评论功能

自己实现评论（发布、浏览、修改、回复）要考虑的问题非常多：

- 用户输入的合法性：怎么防止恶意输入和频繁提交？
- 多层级的嵌套回复：库表如何设计？
- 点赞状态的前后端变化如何处理？

此外「如何设计评论系统」也是后台开发的经典面试题（点赞、层级、状态同步等可问的点很多）。既然评论是非常常见的通用需求，已经有大量现成轮子，直接用更划算。后端侧的评论表结构与状态方案设计见 [[Java 设计 07 - 评论功能设计方案]]。

## 二、Gitalk 是什么

- **定位**：基于 GitHub Issue 和 Preact 开发的评论插件（大厂开源、免费），GitHub star 数接近 6k
- **项目地址**：https://github.com/gitalk/gitalk （中文文档：`readme-cn.md`）
- **核心优势**：只需几行代码即可接入；评论数据存储在 GitHub Issues，**不需要自己准备任何服务器**
- **登录方式**：直接使用 GitHub 账号登录，支持 Markdown 语法发表评论，尤其适合程序员相关的网站
- **功能**：支持点赞、多级回复、修改评论、删除评论，已能满足大多数评论需求

## 三、接入步骤

1. **申请 GitHub 应用**：访问 https://github.com/settings/applications/new 创建应用，获得 `clientID` 和 `clientSecret`，务必保存好
2. **引入依赖**：引入 Gitalk 压缩后的 CSS 样式与 JavaScript 脚本文件
3. **原生 HTML 项目**：先创建一个用于装载评论功能的容器（DOM 节点），再复制一段初始化 Gitalk 的代码
4. **React 项目**：支持直接引入 Gitalk 组件
5. **验证**：访问网站域名即可使用

⚠️ 如果在本地访问可能出现异常，但**线上真实域名的访问是正常的**。

## 四、初始化配置项

| 配置项 | 说明 |
|--------|------|
| `clientID` | 申请到的 GitHub 应用 id |
| `clientSecret` | 申请到的 GitHub 应用秘钥 |
| `repo` | GitHub 仓库名，比如 `'my-repo'` |
| `owner` | 仓库的创建者，比如 `'liyupi'` |
| `admin` | 仓库的管理员，比如 `['liyupi']` |
| `id` | 标注评论属于哪个页面，**尽量保证每个页面的 id 唯一**，否则各页评论会混在一起 |

## 五、局限与选用建议

1. 评论基于 GitHub，国内部分用户可能因网络原因无法使用
2. 基于 GitHub 用户体系，不适合自己网站已有用户库的情况
3. 评论数据存储于 GitHub，很难自己维护
4. 轮子的通病：越现成的往往越难自己定制和修改

实际选用时按自己的情况权衡；静态博客站常用的其他评论方案（Twikoo、Valine、Disqus 等）可参考 [[工具 13 - Hexo 博客搭建教程]] 与 [[工具 32 - 博客建站方式对比与选型]]。
