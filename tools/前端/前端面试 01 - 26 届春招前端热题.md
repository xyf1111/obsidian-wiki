## 一、CSS 中 display 属性的值及其作用

**回答重点**：`display` 决定元素的**内部显示类型**——元素自身按什么盒子参与父级布局，以及它的子元素按什么规则排列。可以理解为两段式：外部（`block` / `inline`）决定自己占不占一整行，内部（`flow` / `flex` / `grid`）决定子元素的排列方式，现代 CSS 中两者可分开写（`display: block flex` 等价于 `flex`，外部盒级、内部弹性）。

| 属性值 | 作用 |
|---|---|
| `none` | 元素不显示，且**不占据任何空间**（脱离渲染树） |
| `block` | 块级元素，独占一行，可设宽高 |
| `inline` | 行内元素，前后不换行，宽高由内容决定 |
| `inline-block` | 行内块级，不换行但**可以设置宽高** |
| `flex` | 块级弹性容器，子元素按一维弹性布局排列 |
| `inline-flex` | 行内弹性容器，子元素弹性布局 |
| `grid` | 块级网格容器，子元素按二维网格布局 |
| `inline-grid` | 行内网格容器，子元素网格布局 |
| `table` / `table-row` / `table-cell` / `table-row-group` / `table-header-group` / `table-footer-group` / `table-column` / `table-column-group` / `table-caption` | 让普通元素模拟表格各部分的显示行为（表格语义化标签默认值即这些） |
| `list-item` | 显示为列表项，带列表标记（`<li>` 的默认值） |
| `initial` | 恢复为属性默认值（`display` 的初始值是 `inline`） |
| `inherit` | 继承父元素的 `display` 值（注意 `display` 本身**不可继承**，只能显式声明） |

**其中 `flex` 和 `grid` 是前端必须熟练掌握的两种布局**：`flex` 是一维（行或列）布局，适合导航、卡片横向排列；`grid` 是二维（行 + 列同时）布局，适合整体页面骨架、宫格列表。

### 1、Flex 一维布局

关键属性只有四个：容器上 `display: flex` + `flex-direction`（主轴方向）+ `justify-content`（主轴对齐）+ `align-items`（交叉轴对齐）；子项再用 `flex: 1` 做剩余空间分配。

```css
.container {
    display: flex;
    flex-direction: row;        /* row | column | row-reverse | column-reverse */
    justify-content: center;    /* flex-start | flex-end | center | space-between | space-around */
    align-items: center;        /* flex-start | flex-end | center | baseline | stretch */
    height: 100vh;
}
.box { flex: 1; margin: 10px; }
```

- **主轴 vs 交叉轴**：`flex-direction` 一改，`justify-content` 和 `align-items` 作用的方向也随之互换，这是面试最常见的追问点。
- **垂直水平居中**：容器 `display: flex; justify-content: center; align-items: center;` 即可，是「如何实现垂直水平居中」的标准答案之一（另有 `position + transform`、`grid + place-items: center`）。

### 2、Grid 二维布局

```css
.container {
    display: grid;
    grid-template-columns: repeat(3, 1fr);  /* 3 列等宽 */
    gap: 10px;                              /* 网格间隙，旧写法 grid-gap 仍可用 */
    padding: 10px;
}
```

- `fr` 是网格专用弹性单位，按剩余空间比例分配；`repeat(3, 1fr)` 比手写三遍 `1fr` 更易维护。
- 需要「列数随宽度自动变化」时用 `repeat(auto-fill, minmax(200px, 1fr))`，可替代部分媒体查询。
- `grid` 与 `flex` 不互斥：常见做法是页面骨架用 `grid`，内部组件排列用 `flex`。

### 3、易混点

| 对比 | 区别 |
|---|---|
| `display: none` vs `visibility: hidden` | 前者不渲染、不占位（触发重排）；后者仍占位，只是不可见（只触发重绘），且 `visibility` 可继承、子元素可单独改回 `visible` |
| `inline` vs `inline-block` | 两者都不换行；`inline` 的 `width/height/margin-top/margin-bottom` 无效，`inline-block` 生效；`inline-block` 元素之间会因 HTML 空白符产生空隙，可用 `font-size: 0` 或父级 `display: flex` 消除 |
| `block` vs `flex` | `flex` 容器自身仍是块级（占满一行），区别在于**子元素**的排列规则被替换为弹性布局 |

## 二、CSS 中可继承与不可继承属性有哪些？

**回答重点**：CSS 属性分**可继承**与**不可继承**两类。可继承属性会把父元素的计算值传递给后代，不可继承属性只作用于声明它的元素本身。**判断规律：与「文本内容呈现」相关的属性大多可继承，与「盒子模型、布局、定位」相关的属性大多不可继承。**

### 1、可继承属性（文本 / 字体 / 列表 / 可见性）

`color`、`font-family`、`font-size`、`font-style`、`font-variant`、`font-weight`、`letter-spacing`、`line-height`、`text-align`、`text-indent`、`text-transform`、`visibility`、`white-space`、`word-spacing`，以及 `list-style`（部分，见下）、`cursor`、`direction`。

### 2、不可继承属性（盒子 / 布局 / 定位 / 背景）

`background`（含 `background-color` 等）、`border`、`display`、`width`、`height`、`margin`、`padding`、`position`、`top/right/bottom/left`、`z-index`、`float`、`clear`、`overflow`、`vertical-align`。

| 类别 | 代表属性 | 是否继承 |
|---|---|---|
| 文本 / 字体 | `color`、`font-*`、`line-height`、`text-align` | ✅ |
| 列表标记 | `list-style-type`、`list-style-position` | ✅ |
| 列表图片 | `list-style-image` | ❌ |
| 盒子模型 | `width`、`height`、`margin`、`padding`、`border` | ❌ |
| 布局 / 定位 | `display`、`position`、`float`、`z-index` | ❌ |
| 可见性 | `visibility` | ✅（可被子元素用 `visible` 覆盖） |

### 3、全局关键字：inherit / initial / unset / revert

| 关键字 | 行为 |
|---|---|
| `inherit` | 强制取父元素的计算值——**不可继承属性也能借此「变成」继承**，常用于表单控件（`input`、`button` 默认不继承字体，用 `font: inherit` 统一） |
| `initial` | 取属性在规范中的初始值（`color` → `canvastext`，`display` → `inline`），**不是**「浏览器默认样式」 |
| `unset` | 可继承属性等同 `inherit`，不可继承属性等同 `initial` |
| `revert` | 回滚到浏览器默认样式（用户代理样式表），重置组件样式时比 `initial` 更符合直觉 |

```css
.child {
    color: inherit;   /* 强制继承父元素的文字颜色 */
    all: unset;       /* 一次性清空所有属性，常用于组件库样式隔离 */
}
```

### 4、两个坑

- **`line-height` 的百分比 / 无单位值差异**：写 `line-height: 1.5`（无单位）时，1.5 会继承下去、后代按**自身字号**重算；写 `line-height: 150%` 或 `1.5em` 时，继承的是**已计算出的像素值**，后代字号变化不再跟随。想让行高随字号自适应，用无单位值。
- **`a` 标签颜色不继承父级**：链接有用户代理样式（`color: -webkit-link`），优先级高于继承值——继承值永远是最低优先级，「继承来的样式盖不过任何直接声明」。这也是「为什么设了 body 颜色链接还是蓝的」的原因。

## 三、Canvas 和 SVG 有什么区别？

**回答重点**：两者都能在网页上画图，但**图形模型完全不同**——Canvas 是**位图**，靠 JS 命令式地逐像素画到一块画布缓冲区，画完就「烧进像素」，没有可回读的对象模型，改内容必须清空重绘；SVG 是**矢量**，用 XML 声明每个图形元素，每个元素都是真实 DOM 节点，可以用 CSS 改样式、用事件监听交互，缩放不失真。选型口诀：**图形元素少、要无损缩放和 DOM 交互（图标、图表、地图标注）→ SVG；元素成千上万且每帧都在变（游戏、粒子、实时可视化、视频合成）→ Canvas**。

### 1、核心差异对照

| 维度 | Canvas | SVG |
|---|---|---|
| 图形模型 | 位图：像素缓冲区 + 2D 上下文，命令式绘制 | 矢量：XML 元素（`<rect>` / `<path>` / `<circle>`）声明式描述 |
| 缩放 | 放大失真；高清屏要按 `devicePixelRatio` 放大绘制缓冲区再 CSS 缩回，否则发虚 | 无损缩放，任意分辨率清晰 |
| DOM / 交互 | 无 DOM 节点，元素画完即「平」；命中检测要自己算坐标或用 `isPointInPath()` | 每个图形是 DOM 节点，`addEventListener`、`:hover`、`cursor` 直接可用 |
| 样式控制 | 只能通过 JS API 设 `fillStyle` / `strokeStyle` / 变换矩阵 | 可用 CSS 选择器、类、变量、动画、滤镜统一控制 |
| 性能特征 | 每帧成本随像素量增长、与元素数量关系小，元素越多优势越大 | 元素多时 DOM 树与重绘成本上升，复杂动画易掉帧 |
| 可访问性 / SEO | 内容不可索引、读屏读不到，需要额外的 fallback 文本 | 元素可带 `role` / `aria-label` / `<title>`，可被索引 |
| 导出 | `toDataURL()` 直接导出 PNG / JPEG | 本身是文本，可直接存 `.svg` |

### 2、Canvas 的特点与优劣

- **即时渲染**：`ctx.fillRect()` 画完就无法再「取回」那个矩形，只能清屏重绘（所以动画 = 每帧重画整个场景）。
- 优点：高性能（大量元素、高频更新）、像素级控制（`getImageData` / `putImageData` 可做滤镜与图像处理）、适合实时渲染。
- 缺点：放大失真、无内置交互（命中检测手写）、复杂图形代码量大且难维护。
- **最常见的坑**：宽高要用 `width` / `height` **属性**（决定绘制缓冲区尺寸）设置；用 CSS 设置只是把整块画布拉伸 → 图像糊掉，这是「Canvas 在高清屏模糊」的头号原因。

```js
const canvas = document.getElementById('myCanvas');
const ctx = canvas.getContext('2d');
ctx.fillStyle = 'green';
ctx.fillRect(10, 10, 100, 100);
```

### 3、SVG 的特点与优劣

- **声明式**：`<rect x="10" y="10" width="100" height="100" fill="green"/>` 就是 DOM 里的一棵子树，改属性即改图。
- 优点：无损缩放（响应式 / 高 DPI 友好）、可样式化可交互、文本格式可读可维护、可访问性好。
- 缺点：元素量级大时性能不如 Canvas；复杂滤镜与动画的浏览器兼容性参差；文件体积随元素数增长。

```html
<svg width="500" height="500" viewBox="0 0 500 500">
  <rect x="10" y="10" width="100" height="100" fill="green"/>
</svg>
```

### 4、常见追问

- **图标为什么都用 SVG**：能跟随 `currentColor` 变色、可被 CSS 覆盖、任意尺寸不失真；海量小图标用 sprite（`<symbol>` + `<use>`）复用，避免重复请求。
- **游戏 / 地图为什么用 Canvas**：元素多、每帧都变，重绘位图比维护几千个 DOM 节点便宜；瓦片地图再进一步上 WebGL（`three.js` / `PixiJS`）。
- **能混用**：SVG 做可交互 UI 层（标注、图标、图例）+ Canvas 做底层高频动画，是数据可视化和地图的典型架构。
- **不阻塞主线程**：`OffscreenCanvas` + Web Worker 把绘制移出主线程，避免大动画卡顿。

## 四、DOCTYPE（文档类型）的作用是什么？

**回答重点**：`<!DOCTYPE>` 是**文档类型声明（Document Type Declaration）**，不是 HTML 标签、也没有闭合标签，必须出现在文档**最顶部第一行**（在任何标签和注释之前）。它唯一的作用是告诉浏览器用哪个 DTD 解析文档，从而决定**渲染模式**：有合法声明 → 标准模式（严格按 W3C 规范解析），缺失或写错 → 怪异模式（退回 IE5 时代的兼容行为）。两种模式下 CSS 盒模型、行高、百分比高度等解释不同，同一份 CSS 会渲染出不同结果。

### 1、三种渲染模式

| 模式 | `document.compatMode` | 触发条件 | 后果 |
|---|---|---|---|
| 标准模式（Standards） | `CSS1Compat` | 有合法 DOCTYPE（现代页面统一 `<!DOCTYPE html>`） | 按 W3C 规范解析，`width` 只含内容 |
| 怪异模式（Quirks） | `BackCompat` | 完全没有 DOCTYPE，或写了非法值 | 走 IE5 兼容行为，**`width` 包含 padding + border** |
| 准标准模式（Almost Standards） | `CSS1Compat` | 部分 HTML 4.01 / XHTML 1.0 Transitional 声明 | 基本按标准解析，仅行内元素与图片的垂直排版有差异 |

运行时用 `document.compatMode` 检测；第三方库（jQuery 等）也靠它判断盒模型行为。

### 2、怪异模式下的典型差异

- **盒模型**：`width` 含 `padding` 和 `border`（相当于标准模式下的 `box-sizing: border-box`），同样的 CSS 会「窄一圈」。
- **行内元素与图片**：`line-height` 对行内元素的计算规则不同，图片底部基线间隙的处理也不同。
- **百分比高度**：标准模式下父元素高度未定则 `height: 100%` 失效（按 0 或内容算），怪异模式会继续向上找。
- **表格字体**：怪异模式下表格内文字不会从 `body` 继承字体。
- **JS 兼容行为**：`document.all` 只在怪异模式「存在」，历史上被用来嗅探浏览器。

### 3、HTML5 的写法

```html
<!DOCTYPE html>
```

- HTML5 只有这一种声明：**不引用 DTD、大小写不敏感**（`<!doctype html>` 同样合法），设计目标就是最大向后兼容——认识它的浏览器全部进入标准模式，而 HTML 4.01 / XHTML 那套冗长声明（带 DTD URL）在 HTML5 时代已无必要。
- 现代脚手架（Vite / Next.js 的 `index.html`、各类模板）会自动带上；VSCode 输入 `!` + Tab（Emmet）即可生成含它的骨架。

## 五、ES6 箭头函数和普通函数有什么区别？

**回答重点**：真正的语义差异只有一条——**箭头函数没有自己的 `this`**，它捕获**定义时**外层作用域的 `this`（`arguments` / `super` 同理），于是：`this` 在定义时就固化，`call` / `apply` / `bind` 都无法改写；没有 `Construct` 内部方法与 `prototype`，不能 `new`；不能作 Generator、不能用 `yield`。其余差异都是语法糖层面的简写。

### 1、语法简写对照

| 场景 | 普通函数 | 箭头函数 |
|---|---|---|
| 完整写法 | `function (a) { return a + 1 }` | `(a) => { return a + 1 }` |
| 单参数省括号 | — | `a => a + 1` |
| 单表达式省 `{}` 与 `return` | — | `(a, b) => a + b`（返回对象字面量需包一层 `({...})`） |
| 无参 | `function () {}` | `() => {}` |
| 只调用不返回 | — | `() => void doSomething()` |

两个坑：**参数括号与 `=>` 之间不能换行**（`let f = (a)` 换行后 `=>` 直接 `SyntaxError: Unexpected token '=>'`）；加了 `{}` 就必须显式 `return`，写成 `(a) => { a + 1 }` 会返回 `undefined`。

### 2、this：唯一真正的语义差异

```js
var id = "GLOBAL";
const obj = {
  id: "OBJ",
  a: function () { console.log(this.id); }, // 普通函数：this 由调用方式决定
  b: () => { console.log(this.id); },       // 箭头函数：this = 定义处外层的 this
};
obj.a(); // 'OBJ'
obj.b(); // 'GLOBAL'
```

- 普通函数的 `this` 在**调用时**按调用方式确定（`obj.a()` → `obj`；裸调用在严格模式下 → `undefined`）；
- 箭头函数的 `this` 在**定义时**绑定到词法外层，之后永不改变：`f.call({id:'obj'})`、`f.apply(...)`、`f.bind(...)()` 全部无效（只能传参）。
- 推论：箭头函数**不适合当对象方法**（拿不到对象自身的 `this`），适合做**回调**（`setTimeout`、`map` / `filter`、Promise 链），省掉 `const self = this` 或 `.bind(this)`。

### 3、不能做的事与替代方案

| 能力 | 普通函数 | 箭头函数 | 替代 |
|---|---|---|---|
| `new` 构造实例 | ✅ | ❌ `TypeError: xxx is not a constructor` | 普通函数 / `class` |
| `arguments` 对象 | ✅（自身实参） | ❌ 拿到的是**外层函数**的 `arguments` | rest 参数 `(...args)` |
| 作为 Generator | ✅ | ❌ 不能用 `yield` | `function*` |
| `super` / `new.target` | ✅ | ❌ 不支持（类字段里的箭头函数可访问外层 `super`） | 普通方法 |
| `call` / `apply` / `bind` 改 `this` | ✅ | ❌ 无效 | — |
| `prototype` 属性 | ✅ | ❌ `undefined` | 用普通函数挂原型方法 |

```js
const logArgs = (...args) => console.log(args); // 替代 arguments
```

### 4、常见追问

- **React 类组件为什么用箭头函数**：`handleClick = () => {...}` 作为类字段，`this` 在定义时绑定到实例，省掉构造器里的 `this.handleClick = this.handleClick.bind(this)`。
- **为什么不能改写 `this`**：箭头函数不创建自己的 `this` 绑定记录，沿作用域链查 `this` 时直接落到外层，`call` / `bind` 只能改形参和普通 `this` 绑定。
- **Vue options API 为什么不能用箭头函数写 `methods`**：`methods` 依赖 `this` 指向组件实例，箭头函数会把它绑定到模块作用域（通常是 `undefined`），`this.xxx` 全部拿不到。

> 相关：[[JavaScript 01 - 学习路线]]

## 六、HTML 中 img 的 srcset 属性有什么作用？

**回答重点**：`srcset` 让**同一个 `<img>` 提供多个候选图源**，每个源带一个描述符（宽度 `500w` 或像素密度 `2x`）。浏览器在解析到标签时、**图片下载前**就根据当前**视口宽度 + 设备像素比（DPR）**选出最合适的一张去下载——小屏手机不会去拉 1500px 的大图，从而节省带宽、加快加载。它只影响「选哪张图」，不改变布局。

### 1、两种描述符

| 描述符 | 写法 | 含义 | 配套属性 |
|---|---|---|---|
| 宽度描述符 | `small.jpg 500w` | 该文件的**自然宽度**是 500px | 必须配 `sizes`，否则退化按 `100vw` 估算 |
| 像素密度描述符 | `logo@2x.png 2x` | 供 2 倍屏使用 | 无需 `sizes`，固定尺寸图标常用 |

同一组 `srcset` 内不能混用 `w` 和 `x`。

```html
<img
  src="small.jpg"
  srcset="small.jpg 500w, medium.jpg 1000w, large.jpg 1500w"
  sizes="(max-width: 600px) 500px, (max-width: 900px) 1000px, 1500px"
  alt="示例图片">
```

- `srcset`：候选源 + 自然宽度；`src` 作为不支持 `srcset` 的老浏览器兜底。
- `sizes`：告诉浏览器「在这些媒体条件下，图片**在页面上会占多宽**」，浏览器据此算出需要的实际像素（占了 500px 宽、屏幕 2x → 需要 1000px 的图），再去 `srcset` 里挑。

### 2、与 `<picture>` 的分工

`srcset` 解决的是**同一张图的不同分辨率**；`<picture>` + `<source media="...">` 解决的是**艺术方向（art direction）**——不同断点换成不同裁剪/比例/格式（如窄屏用竖构图，宽屏用横构图），或优先给 WebP/AVIF。`<picture>` 内的 `<img>` 是必填兜底项。

## 七、HTML 中 title 与 h1 标签的区别是什么？

**回答重点**：两者都影响 SEO 但**位置和可见性完全不同**——`<title>` 在 `<head>` 里，显示在**浏览器标签页 / 书签 / 搜索结果的标题行**，页面正文里看不见；`<h1>` 在 `<body>` 里，是**页面内**最大最显眼的主标题，决定内容层次。一句话：`<title>` 决定「搜索结果怎么展示你」，`<h1>` 决定「搜索引擎怎么理解这页讲什么」。

| 维度 | `<title>` | `<h1>` |
|---|---|---|
| 位置 | `<head>` 内，文档级 | `<body>` 内，内容级 |
| 可见性 | 页面**外**可见（标签页、书签、SERP 标题） | 页面**内**可见（正文主标题） |
| 数量 | 每个文档**恰好一个** | 语义上一个页面只应有一个（多 section 场景可多个，但要克制） |
| SEO 侧重 | SERP 标题与点击率；过长会被截断（约 60 字符） | 内容主题与层级结构 |
| 能否省略 | 不能，属必需元素 | 可以，但不利于可访问性与 SEO |

### 常见追问

- **能否用 `<h1>` 代替 `<title>`**：不行。没有 `<title>` 时浏览器标签页显示 URL，搜索引擎自行拼标题，书签也失去可读名称。
- **`<h1>` 写多个会不会被惩罚**：HTML5 大纲允许，但实践中仍建议页面主标题唯一，其余用 `<h2>`/`<h3>`，否则主题信号变弱。

## 八、HTML 的 script 标签中 defer 和 async 有什么区别？

**回答重点**：两者都让外部脚本**并行下载、不阻塞 HTML 解析**（对比裸 `<script>` 是「下载 + 执行全程阻塞」）。差别在**执行时机与顺序**：`defer` 等 **HTML 解析完成后、`DOMContentLoaded` 之前**按**文档顺序**执行，适合依赖 DOM、互相有依赖的脚本；`async` 是**谁先下载完谁先执行**、执行时可能打断解析，顺序不可控，只适合独立、无依赖的脚本（统计、广告）。

| 维度 | 裸 `<script>` | `async` | `defer` |
|---|---|---|---|
| 下载 | **阻塞**解析 | 并行，不阻塞 | 并行，不阻塞 |
| 执行时机 | 立即，下载完就执行 | 下载完立即执行，**可能打断解析** | HTML 解析完成后、`DOMContentLoaded` 前 |
| 执行顺序 | 文档顺序 | **不确定**（先下完先跑） | **保证文档顺序** |
| 能否拿到完整 DOM | 不能（后续节点还没解析） | 不能保证 | 能 |
| 典型场景 | 必须同步生效的小脚本、埋点前置 | 独立第三方脚本（广告、计数器、CDN 监控） | 业务代码、有依赖关系的多个脚本、需操作 DOM |

```html
<script src="a.js" defer></script>
<script src="b.js" defer></script>  <!-- 即使 b 先下载完，也等 a 执行完 -->
<script src="analytics.js" async></script>
```

- `defer` 只对外部脚本有效；**行内 `<script>` 上写 `defer` 无效**（行内没有下载过程，写完就执行）。
- 两者都不改变 `DOMContentLoaded` 之前的窗口：`defer` 脚本在 `DOMContentLoaded` **前**跑完，`async` 可能在它之前也可能之后。
- 现代构建工具（Vite / Webpack）产出的入口脚本默认带 `type="module"`，而**模块脚本默认就是 defer 行为**（按顺序、解析后执行）。
- 想进一步减阻塞：`rel="preload"` 提前拉关键脚本、`rel="prefetch"` 空闲时预取后续路由脚本。

## 九、HTML 的 src 和 href 属性有什么区别？

**回答重点**：`src`（source）是**把外部资源加载进来、替换掉这个元素本身**，适用于 `<script>`、`<img>`、`<audio>`、`<video>`、`<iframe>`；`href`（hyperlink reference）是**建立一条指向目标地址的引用关系**，链接本身仍留在文档里，适用于 `<a>`、`<link>`、`<area>`。必答句：「**src 是替换，href 是引用**」——这决定了 `src` 触发立即请求、`href` 多数要等用户点击或渲染阶段才真正使用。

| 维度 | `src` | `href` |
|---|---|---|
| 语义 | 元素的内容源（嵌入 / 替换） | 超链接目标或外部资源关联 |
| 典型标签 | `script`、`img`、`audio`、`video`、`iframe`、`source` | `a`、`link`、`area` |
| 何时发请求 | 解析到标签即请求 | `<a>` 点击后才跳转；`<link rel=stylesheet>` 解析时请求 |
| 是否阻塞 | `script` **阻塞解析与执行**；`img`/`iframe` 异步不阻塞 | 下载并行不阻塞解析，但 stylesheet 默认 **render blocking** |
| 出错表现 | 图片不显示、脚本不执行、功能缺失 | 点击后跳 404 或错误页 |
| 常用优化 | `async`/`defer`、`loading="lazy"`、CDN、WebP、压缩 | `rel="preload"`、`media="print" onload` 异步化 CSS、动态插 `<link>` |

```html
<script src="app.js" defer></script>              <!-- 阻塞型资源，用 defer 化解 -->
<img src="a.webp" loading="lazy" onerror="this.src='fallback.png'">
<link rel="stylesheet" href="main.css">           <!-- 引用式，默认阻塞渲染 -->
<a href="/detail">详情</a>                        <!-- 引用式，点击才请求 -->
```

- **`script` 放页面底部**的原因是裸 `<script>` 会暂停 HTML 解析直到下载 + 执行完成；`img` 的加载与解码是异步的，不会阻塞解析，别把「src 阻塞」当通用规律。
- `href` 侧的 render blocking 常被忽略：CSS 不阻塞解析但阻塞**渲染**，首屏关键 CSS 内联、非关键 CSS 用 `media` 切换或 JS 动态加载。
- `src` 错误可以兜底（`onerror`、动态插 script 时监听 `onerror`），`href` 错误只能靠友好 404 页 + 链接巡检。

## 十、HTML 行内元素、块级元素、空元素有哪些？

**回答重点**：按**默认 `display` 值**把元素分三类——行内元素**不换行、宽高由内容决定**（`span`、`a`、`b`、`i`、`strong`、`em`、`label`、`select`）；块级元素**独占一行、默认撑满父容器宽度**（`div`、`p`、`h1`~`h6`、`ul`、`ol`、`li`、`header`、`section`、`form`）；空元素**没有结束标签、不能有子内容**（`img`、`br`、`hr`、`input`、`meta`、`link`）。必答句：「**分类看的是默认 display，不是标签名——CSS 一改就变**」。

| 类别 | 默认 display | 常见元素 | 可设 width/height | 可包含块级元素 |
|---|---|---|---|---|
| 行内 | `inline` | `span`、`a`、`b`/`i`、`strong`/`em`、`label`、`select` | 否（替换元素除外） | 否（写了也是非法嵌套） |
| 块级 | `block` | `div`、`p`、`h1`~`h6`、`ul`/`ol`/`li`、`header`/`footer`/`nav`、`form` | 是 | 是 |
| 空（void） | 随标签 | `img`、`br`、`hr`、`input`、`meta`、`link`，另有 `area`/`base`/`col`/`embed`/`source`/`track`/`wbr` | 取决于 display | 否（无子节点） |

- **`img`、`input`、`video` 是行内但能设宽高**：它们属于 replaced element（替换元素），尺寸由替换内容决定，这是「行内元素不能设宽高」的唯一例外，面试高频追问。
- 行内元素上下 `margin`/`padding` **不撑开行高**（会画到相邻行上），需要垂直间距时改 `inline-block` 或块级。
- HTML5 新增语义标签（`header`/`nav`/`section`/`article`/`aside`/`footer`）默认都是**块级**；`<br>` 是空元素且 `display: inline`，`<hr>` 是空元素且块级——「空元素」和「行内/块级」是两个独立维度。
- 现代口径不必背清单：拿不准就查 MDN 的默认样式，或直接写 `display` 显式声明。各 `display` 取值的差异见本文档「一」。

## 十一、HTML5 相比于 HTML 有哪些更新？

**回答重点**：六条主线——① **语义化标签**（`header`/`footer`/`nav`/`article`/`section`/`aside`，利于 SEO 与无障碍）；② **表单增强**（`email`/`date`/`number` 等新 type + `placeholder`/`required`/`pattern` 原生校验）；③ **原生音视频**（`audio`/`video`/`source`，摆脱 Flash 插件）；④ **新 API**（Canvas、Geolocation、Drag and Drop、Web Storage、WebSocket）；⑤ **离线与连接性**；⑥ **移除纯表现标签**（`font`/`center`/`big`/`strike`/`u` 及 `frame`/`frameset`/`noframes`）。必答句：「**HTML5 的更新 = 语义化 + 表单/媒体原生能力 + 一批 JS API 从插件手里接管**」。

| 类别 | 新增内容 | 说明 |
|---|---|---|
| 语义化 | `header` `footer` `nav` `article` `section` `aside` `main` `figure` | 取代满屏 `div class="header"`，结构可读、可被读屏与爬虫识别 |
| 媒体 | `audio` `video` `source` `track` | `source` 提供多格式回退，`track` 挂字幕 |
| 表单 type | `email` `url` `tel` `number` `range` `search` `color` `date` `time` `datetime-local` `week` `month` | `datetime` 已被规范删除（实际只有 Safari 曾支持），应改用 `datetime-local` |
| 表单属性 | `placeholder` `required` `pattern` `autofocus` `multiple` `min`/`max`/`step` | 原生校验 + `:valid`/`:invalid` 伪类，减少 JS |
| JS API | Canvas 2D、Geolocation、Drag and Drop、Web Storage、WebSocket、History、File、MutationObserver | Web Storage 分 `localStorage`（永久）与 `sessionStorage`（标签页级） |
| 其他元素 | `progress`、`meter`、`details`/`summary`、`datalist`、`output` | `progress`/`meter` 在旧 IE、Safari 支持不全 |
| 全局属性 | `contenteditable`、`spellcheck`、`data-*`、`hidden`、`draggable` | `data-*` 是组件传参的事实标准 |

```html
<video controls poster="cover.jpg">
  <source src="v.mp4" type="video/mp4">
  <source src="v.webm" type="video/webm">
  <track src="zh.vtt" kind="subtitles" srclang="zh" label="中文">
</video>
```

- **Application Cache 已废弃**：源文时代常把 `manifest` 离线缓存列为 HTML5 亮点，如今它已被规范移除，离线能力应改用 **Service Worker + Cache Storage**——面试回答这一点比背 manifest 更加分。
- 语义化标签的收益不只在 SEO：读屏软件靠 `nav`/`main` 做地标跳转，`tools/前端/工具 31` 有无障碍细则；DOM 结构也更易维护。
- 新表单 type 的校验**可被用户改 DOM 绕过**，服务端校验不可省；`type="number"` 在部分浏览器允许输入 `e`、不校验小数位，金额场景仍需 JS 兜底。
- Canvas 与 SVG 的取舍见本文档「三」，`<!doctype html>` 的触发模式见「四」。

## 十二、JavaScript 有哪些数据类型？它们的区别是什么？

**回答重点**：**8 种 = 7 种原始类型 + 1 种引用类型**。原始类型：`undefined`、`null`、`boolean`、`number`、`string`、`symbol`（ES6）、`bigint`（ES2020）；引用类型只有 `Object` 一个入口，数组、函数、Date、Map 都是它的实例。核心区别是**值语义 vs 引用语义**：原始类型赋值/传参复制的是值本身，互不影响；引用类型复制的是指向堆对象的引用，多个变量共享同一对象，改一处全体可见。必答句：「**原始类型按值传递、不可变；引用类型按引用传递、可变——所有『赋值后互相影响』的坑都来自这一条**」。

| 类型 | `typeof` 结果 | 说明 | 常见坑 |
|---|---|---|---|
| `undefined` | `"undefined"` | 声明未赋值、缺参、无 `return`、属性不存在 | 显式赋 `undefined` 会混淆「未定义」与「已清空」 |
| `null` | `"object"` | 空值 / 空对象引用，唯一值 `null` | 历史 bug：`typeof null === "object"`，判空要用 `=== null` |
| `boolean` | `"boolean"` | `true` / `false` | 包装对象 `new Boolean(false)` 是真值对象 |
| `number` | `"number"` | IEEE 754 双精度 64 位浮点，整数小数共用 | `0.1 + 0.2 !== 0.3`；安全整数上限 `2^53 - 1`；`NaN !== NaN` |
| `string` | `"string"` | UTF-16 序列，不可变 | 字符串方法都返回新串，原串不变 |
| `symbol` | `"symbol"` | 唯一且不可变，用作不会冲突的属性键 | `Symbol()` 不加 `new`；`JSON.stringify` 会忽略 symbol 键 |
| `bigint` | `"bigint"` | 任意精度整数，字面量 `10n` | 不能与 `number` 混算（`1n + 1` 抛 TypeError），不能 `Math.*` |
| `Object` | `"object"`（函数为 `"function"`） | 引用类型总称：普通对象、数组、函数、日期、正则… | `typeof` 无法区分数组/日期/正则，需 `Array.isArray` 等 |

```javascript
// 值语义 vs 引用语义
let a = 1, b = a; b++;            // a 仍为 1
const o1 = { n: 1 }, o2 = o1; o2.n = 2;   // o1.n 也变成 2

// 类型检测的四个层次
typeof 1n                 // "bigint"
Array.isArray([])         // true（跨 iframe 也可靠，优于 instanceof）
Object.prototype.toString.call(new Date())  // "[object Date]" —— 万能判型
Number.isNaN(NaN)         // true；全局 isNaN('abc') 也是 true（先转数字，别用）
```

- **「栈 / 堆」是面试口径，不是规范**：规范化只规定**值语义**，具体存储由引擎决定。V8 里小整数走 Smi 内联在指针里，大数字 / 字符串 / 对象走堆 + 指针；被闭包捕获的原始变量也会被提升到堆上的上下文对象，所以「原始类型一定在栈上」并不严格成立。
- **类型数量为什么从 6 变 8**：ES5 时代是 5 原始 + 1 引用（`null` 常被单独算，于是有「6 种」的说法），ES6 加 `Symbol`、ES2020 加 `BigInt`。答「8 种」时顺口补一句演进，比死背清单更像理解过。
- **包装对象是隐式转换的产物**：`'abc'.length` 能跑是因为引擎临时包了 `String` 对象；但 `new String('a') === 'a'` 为 `false`，判型时别用 `instanceof` 区分原始与包装。
- 浅拷贝 `{...obj}` / `Object.assign` 只复制第一层引用，深拷贝用 `structuredClone()`（原生、支持 Date/Map/Set，但不支持函数）或 `JSON.parse(JSON.stringify())`（丢 `undefined`/函数/symbol，且 Date 变字符串）。
- **类型转换**：`+` 遇字符串即拼接（`1 + '2' === '12'`），其余算术运算符强制转数字；显式转换优先用 `Number()`/`String()`/`Boolean()`，`parseInt` 必须带基数 `parseInt('08', 10)`。`null`/`undefined` 的转换差异见本文档「十三」。

> 相关：[[工具 12 - 前端学习路线]]、本文档「十三」「十四」

## 十三、JavaScript 中 null 和 undefined 的区别是什么？

**回答重点**：两者都是**原始类型、各自只有一个值、都表示「没有值」**，差别在**谁来赋值、语义是什么**：`undefined` 是**引擎自动**给出的「尚未定义」（声明未赋值、函数缺参、无 `return`、读不存在的属性）；`null` 是**开发者显式**写入的「此处为空 / 空对象引用」，是主动清空语义。必答句：「**undefined 是『还没给』，null 是『故意给空』**」。

| 维度 | `undefined` | `null` |
|---|---|---|
| `typeof` | `"undefined"` | `"object"`（早期实现的 bug，被规范保留） |
| `==` / `===` | `undefined == null` 为 `true`；`===` 为 `false` | 同左 |
| 典型来源 | 声明未赋值、缺参、无 `return`、属性不存在、`void 0` | 开发者显式赋值、`JSON.parse('null')`、DOM API 找不到元素 |
| `Number()` 转换 | `NaN` | `0` |
| 算术 | `1 + undefined` → `NaN` | `1 + null` → `1` |
| `JSON.stringify` | 对象里该键**被丢弃**，数组里变 `null` | 正常序列化为 `null` |
| 默认参数 / 解构默认值 | **触发**默认值 | **不触发**（`f(null)` 拿到 `null`） |
| 可选链 / 空值合并 | `a?.b` 对两者都短路；`??` 对两者都取右侧 | 同左 |

```javascript
function f(x = 'default') { return x; }
f(undefined);   // 'default'
f(null);        // null —— 只有 undefined 才触发默认值

JSON.stringify({ a: undefined, b: null });  // '{"b":null}'
JSON.stringify([undefined, null]);          // '[null,null]'

null == 0;      // false（== 的规范特例：null 只与 undefined 相等）
null >= 0;      // true ！关系运算符走 ToNumber，null 变 0
```

- **`null == 0` 为 `false` 但 `null >= 0` 为 `true`**，是最高频的连环追问：`==` 对 `null`/`undefined` 有专门规则（只互相相等，不与其他值做数字转换），而 `>`/`<`/`>=` 一律走 `ToNumber`。
- **判空只写 `x == null`** 可一次排除两者（ESLint 默认允许 `eqeqeq` 的 `null` 例外）；但若 `0`、`''`、`false` 也是合法值，必须用 `x === undefined || x === null` 或 `x ?? fallback`，别用 `!x` 或 `if (x)`。
- **属性存在但值为 `undefined`**：`'key' in obj` 和 `obj.hasOwnProperty('key')` 都是 `true`——「键存在」和「有值」是两件事，做配置合并时要用 `in` 而非真值判断。
- **API 约定不统一**：`document.getElementById` 找不到返回 `null`；`Array.prototype.find` 找不到返回 `undefined`；`JSON.stringify(undefined)` 返回 `undefined`（不是字符串）。写封装时统一成一种，避免调用方两边都判。
- 实践口径：**不要手动 `let x = undefined`**（语义上等价于没赋值，可读性差），要清空引用就赋 `null`；这也让 `null` 承担「已初始化但当前为空」的信号，便于调试与 GC 提示（置 `null` 有助于及时释放大对象引用）。

## 十四、JavaScript 中 Object.keys 的返回值是无序的吗？

**回答重点**：**现代引擎下是有序的**，顺序由规范 `OrdinaryOwnPropertyKeys` 固定为三段：① **数组索引型键**（`'0'`、`'1'`…）按**数值升序**；② **其余字符串键**按**插入顺序**；③ `Symbol` 键按插入顺序排最后（`Object.keys` 不返回它们，需 `Object.getOwnPropertySymbols`）。必答句：「**先数字（升序）后字符串（插入序），Symbol 不进 `Object.keys`**」——ES2015 起这是规范保证，不再依赖引擎实现。

```javascript
Object.keys({ b: 1, 1: 1, a: 1, 2: 1 });   // ['1', '2', 'b', 'a']

const arr = ['a', 'b', 'c'];
arr.test = 'x';
Object.keys(arr);                            // ['0', '1', '2', 'test']

Object.keys({ length: 3, 0: 'a', 1: 'b', 2: 'c' });  // ['0', '1', '2', 'length']
```

- **「数组索引键」有严格定义**：`String(ToUint32(key)) === key` 且值 ≠ `2^32 - 1`。所以 `'01'`、`'1.0'`、`'-1'`、`'1e3'`、`'4294967295'` 都**不算**数字键，走插入顺序；`'1'`、`'2'` 算。
- **顺序保证 ≠ 应该依赖顺序**：顺序只对「自有可枚举键」成立，代码演进（加字段、改序列化、经过 `JSON.parse` 重排）都可能改变结果。业务上需要稳定顺序就用 `Map`（**严格按插入顺序，数字键不重排**）或数组。
- **副作用提醒**：给对象塞长串数字键会让 V8 从「快属性」退化为**字典模式 / 稀疏 elements**，读写变慢、内存变高。做 ID → 数据的映射，量大时用 `Map` 或 `Object.create(null)` + 字符串前缀键（如 `'id_1'`）更稳。

| 方法 | 含原型链 | 含不可枚举 | 含 `Symbol` | 返回内容 |
|---|---|---|---|---|
| `Object.keys` | 否 | 否 | 否 | 可枚举字符串键数组 |
| `Object.values` / `Object.entries` | 否 | 否 | 否 | 值数组 / `[键, 值]` 数组 |
| `Object.getOwnPropertyNames` | 否 | **是** | 否 | 全部字符串键（含不可枚举） |
| `Object.getOwnPropertySymbols` | 否 | **是** | 仅 Symbol | Symbol 键数组 |
| `Reflect.ownKeys` | 否 | **是** | **是** | 全部自有键（同三段排序规则） |
| `for...in` | **是** | 否 | 否 | 遍历自身 + 原型链可枚举键 |

- `for...in` 也遵守「数字升序 + 插入序」，但它**会遍历到原型链**（包括被扩展的 `Object.prototype`），所以取自有键时配 `Object.hasOwn(obj, k)`（ES2022）或 `hasOwnProperty.call`。
- `Object.keys` 只接受对象：传 `null`/`undefined` 直接抛 TypeError（ES2015 起不再静默转对象），传原始值会先装箱（`Object.keys('ab')` → `['0','1']`）。

## 十五、JavaScript 的 BigInt 和 Number 类型有什么区别？

**回答重点**：JS「只有一种数字」的历史在 ES2020 被打破：`Number` 是 IEEE 754 双精度 64 位浮点，只能精确表示 ±(2^53−1) 以内的整数；`BigInt` 是**任意精度整数**，字面量加 `n`（`123n`）。二者**不是同一个类型**：`typeof 1n === 'bigint'`，**不能混合算术运算**（`1n + 1` 抛 TypeError），必须显式互转；但比较运算符可混用（`1n < 2` 为 `true`，`1n == 1` 为 `true`，`1n === 1` 为 `false`）。必答句：「**BigInt 补的是整数精度，不是小数精度——它连小数点都不能有**」。

| 维度 | `Number` | `BigInt` |
|---|---|---|
| 底层表示 | IEEE 754 双精度 64 位 | 任意精度整数，按需分配 |
| 安全整数 | ±(2^53−1)，即 `Number.MAX_SAFE_INTEGER` | 无上限，只受内存限制 |
| 小数 | 支持（存在精度损失） | 不支持，`BigInt(1.5)` 抛 RangeError |
| 字面量 / `typeof` | `123` / `'number'` | `123n` / `'bigint'` |
| 混合算术 | `1 + 1n` → TypeError | 同左，须 `BigInt(1)` 或 `Number(1n)` |
| 混合比较 | `1n == 1` 为 true、`1n === 1` 为 false、`1n < 2` 为 true | 同左 |
| `Math.*` / 位运算 | 全支持 | 无 `Math`；不支持 `>>>`；除法截断 |

```javascript
const max = Number.MAX_SAFE_INTEGER;   // 9007199254740991
max + 1 === max + 2;                   // true —— 超出后精度已丢
Number.isSafeInteger(2 ** 53);         // false

123n + 1;              // TypeError: Cannot mix BigInt and other types
123n + 1n;             // 124n
7n / 2n;               // 3n —— 整除截断，不是 3.5
Number(2n ** 53n + 1n);                // 9007199254740992 —— 转回 Number 立刻失真
BigInt('9007199254740993');            // 9007199254740993n —— 从字符串构造最安全
```

- **唯一「静默丢精度」的边界是 `Number()`**：只要超出安全整数范围，`Number(big)` 就取近似值；反向 `BigInt(num)` 对整数安全、对小数抛 RangeError。
- **`JSON.stringify` 直接抛 TypeError**（`Do not know how to serialize a BigInt`）：接口传大 ID 必须先 `String(big)` 或写 replacer；`JSON.parse` 也不会自动还原，跨端契约通常用字符串承载。
- **`Math.*` 全不可用**（`Math.max(1n, 2n)` 报错），`toFixed` / `toPrecision` 也没有，格式化只能自己转字符串。
- **`>>>` 不支持**（BigInt 无符号位概念）；`>>`、`&`、`|`、`^`、`~` 可用但两侧必须同为 BigInt；一元 `+1n` 抛 TypeError，`-1n` 合法。
- **真值判断**：`0n` 是 falsy（`Boolean(0n) === false`），非零 BigInt 为 truthy。
- **性能**：BigInt 运算比 Number 慢一到两个数量级，循环计数、普通业务字段、热路径别换；`BigInt64Array` 才有定长存储优势。
- **典型用途**：数据库 `BIGINT` / 雪花 ID（超过 2^53 的 ID 传到前端会被「抹尾」，是真实线上 bug 来源）、以「分」为单位的金额整数运算、纳秒级时间戳、大数阶乘与加密。

> 相关：[[工具 12 - 前端学习路线]]、本文档「十二」（数据类型总表）

## 十六、let、const 和 var 的区别是什么？

**回答重点**：按三条轴定性：**作用域**（`var` 函数作用域 / `let`、`const` 块级作用域）、**重复声明**（`var` 允许 / `let`、`const` 同作用域内重声明报 SyntaxError）、**提升与 TDZ**（三者都会被提升，但 `var` 提升后值是 `undefined` 可直接访问；`let`、`const` 提升后未初始化，声明语句执行前访问抛 ReferenceError，即「暂时性死区」）。必答句：「**`var` 是函数作用域 + 提升为 undefined；`let`/`const` 是块级作用域 + 提升但不初始化（TDZ）**」。

| 维度 | `var` | `let` | `const` |
|---|---|---|---|
| 作用域 | 函数 / 全局 | 块级 `{}` | 块级 `{}` |
| 重复声明 | 允许 | SyntaxError | SyntaxError |
| 重新赋值 | 允许 | 允许 | TypeError |
| 必须初始化 | 否（默认 `undefined`） | 否 | **是**（`const c;` 语法错误） |
| 声明前访问 | `undefined` | ReferenceError（TDZ） | ReferenceError（TDZ） |
| 全局声明是否成为 `window` 属性 | 是 | **否** | **否** |
| 循环中的绑定 | 全程一个绑定 | 每次迭代新建绑定 | 每次迭代新建绑定 |

```javascript
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));  // 3 3 3
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j));  // 0 1 2

console.log(a);  // undefined —— var 已提升
var a = 1;
console.log(b);  // ReferenceError: Cannot access 'b' before initialization
let b = 1;

var x = 1; var x = 2;   // 允许
let y = 1; let y = 2;   // SyntaxError: Identifier 'y' has already been declared

const o = { n: 1 };
o.n = 2;   // 合法：const 锁的是绑定，不是对象内容
o = {};    // TypeError: Assignment to constant variable
```

- **循环的差别不是「作用域大小」，而是「每次迭代新建绑定」**：规范为 `for (let …)` 每轮创建新环境记录并拷贝上一轮的值，闭包因此各捕获一份；`var` 全程共享一个绑定，回调执行时循环早已结束。
- **TDZ 连 `typeof` 也管**：声明前 `typeof b` 同样抛 ReferenceError；只有**从未声明**的变量 `typeof` 才安全返回 `'undefined'`——这是区分「TDZ」与「不存在」的经典追问。
- **`const` 不等于不可变**：对象/数组内容照改，要真正冻结用 `Object.freeze`（浅冻结，嵌套需递归或整体 `structuredClone` 后再冻）。
- **全局 `var` 会挂到 `window`，`let`/`const` 不会**（它们进全局词法环境，`window.x` 取不到）——「全局 `let` 能否用 `window` 取到」的答案是**不能**。
- **函数 / 类声明同样有 TDZ**；块内 `function` 在严格模式下是块级作用域，非严格模式有 Annex B「提升到函数作用域」的兼容行为，不要依赖。
- **最佳实践**：默认 `const`，确需重赋值才 `let`，`var` 只在维护老代码时出现；`for...of` / `for...in` 同理优先 `const`。

> 相关：[[工具 12 - 前端学习路线]]、本文档「十二」

## 十七、typeof null 的结果是什么？为什么？

**回答重点**：`typeof null === 'object'`，这是**语言级历史 bug，且被规范永久保留**。原因：1995 年 JS 在 32 位机器上用值的低位**类型标签**区分类型，对象的标签是 `000`；`null` 表示空指针（零地址），机器层面就是全零，标签位同样是 `000`，于是被判定为对象。发现时已有大量代码依赖该行为，修复会破坏向后兼容，ES 规范索性把 `typeof null` 返回 `'object'` 写进标准。必答句：「**`null` 是空指针，类型标签 `000` 与对象撞车，属于修不动的历史 bug**」。

```javascript
typeof null;             // "object"
typeof undefined;        // "undefined"
typeof function () {};   // "function"
typeof class C {};       // "function" —— class 本质仍是函数
typeof NaN;              // "number" —— NaN 属于 number 类型
typeof Symbol();         // "symbol"
typeof 1n;               // "bigint"
typeof notDeclared;      // "undefined" —— 不报错，所以判「未声明」并不可靠
```

- **正确判空**：`value === null` 是唯一可靠的写法；`value == null` 可**一并**排除 `null` 与 `undefined`（ESLint `eqeqeq` 默认放行这一例外），若两者语义要区分则必须 `===`。
- **判「纯对象」**：`value !== null && typeof value === 'object'`，`null` 必须先前置排除；要更精确用 `Object.prototype.toString.call(v)`（`'[object Null]'`、`'[object Array]'`）。
- `Object.is(value, null)` 与 `===` 对 `null` 完全等价（`Object.is` 的差异只在 `NaN` 与 `±0`）。
- **`document.all` 是另一个 `typeof` 特例**：`typeof document.all === 'undefined'`、`document.all == null` 为 `true`，但它实际存在且能取属性——HTML 规范为兼容老代码写死的「伪装成 undefined 的 falsy 对象」，知道有这个例外即可。
- **别用 `!value` 判空**：`0`、`''`、`false`、`NaN` 都会被误杀。

## 十八、typeof 和 instanceof 有什么区别？

**回答重点**：两者查的**根本不是同一个东西**——`typeof` 看值的类型，返回 8 种固定字符串之一，是判原始类型唯一可靠的手段；`instanceof` 沿**原型链**查找右操作数的 `prototype`，只返回布尔值，只能用于引用类型。因此 `typeof` 对数组/日期/正则一律给 `'object'`（分不清），`instanceof` 对原始类型一律 `false`。必答句：「**`typeof` 判原始类型、`instanceof` 判是谁 `new` 出来的**」。

| 维度 | `typeof` | `instanceof` |
|---|---|---|
| 判断依据 | 值的类型（引擎按值的类型标签） | 沿 `__proto__` 原型链找 `Ctor.prototype` |
| 返回值 | `'undefined'`/`'boolean'`/`'number'`/`'string'`/`'object'`/`'function'`/`'symbol'`/`'bigint'` | `true` / `false` |
| 适用范围 | 原始类型 + 引用类型（引用类型只能分出函数） | 仅引用类型，原始类型恒 `false` |
| 右操作数 | 无 | 必须是有 `prototype` 的函数/class，箭头函数会 TypeError |
| 可否被伪造 | 否，由值决定 | 是：改原型链、改 `Symbol.hasInstance` 都能骗过它 |
| 跨 realm（iframe / vm） | 不受影响 | **失效**，iframe 里的 `Array` 不等于当前页的 `Array` |

```javascript
// 手写 instanceof：本质就是走一遍原型链
function myInstanceof(obj, Ctor) {
  if (obj === null || (typeof obj !== 'object' && typeof obj !== 'function')) return false;
  let proto = Object.getPrototypeOf(obj);
  while (proto) {
    if (proto === Ctor.prototype) return true;
    proto = Object.getPrototypeOf(proto);
  }
  return false;
}
1 instanceof Number;                  // false —— 原始类型永远过不了 instanceof
new Number(1) instanceof Number;      // true
```

- **判型速查**：数组用 `Array.isArray`（跨 iframe 也准）；`Date`/`RegExp`/`Map`/`Promise` 用 `Object.prototype.toString.call(v)`（`'[object Date]'`）；`NaN` 用 `Number.isNaN`（不要用全局 `isNaN`，它会先做类型转换）；纯对象用 `Object.getPrototypeOf(v) === Object.prototype`。
- **别用 `obj.constructor === Foo`**：`Object.create(null)` 的对象没有 `constructor`，原型链改过之后也会骗人，且同样跨 realm 失效。
- **`Symbol.hasInstance` 是可自定义的钩子**：`class Even { static [Symbol.hasInstance](n) { return n % 2 === 0 } }`，于是 `2 instanceof Even === true`——这是 `instanceof` 语义可被改写的规范级原因。
- **`instanceof` 对 `null`/`undefined` 返回 `false` 不报错**，但右操作数写成箭头函数会抛 TypeError（箭头函数没有 `prototype`）。
- `typeof` 只有两个坑值得记：`null` 给 `'object'`（见本文档「十七」）、`document.all` 给 `'undefined'`；`typeof class C {}` 是 `'function'`，因为 class 本质仍是函数。

> 相关：本文档「十二」（类型总表）、「十七」（`typeof null`）、[[工具 12 - 前端学习路线]]

## 十九、为什么 JavaScript 中 0.1 + 0.2 不等于 0.3，如何让其相等？

**回答重点**：JS 只有一种数字类型 `Number`，底层是 **IEEE 754 双精度 64 位浮点**：1 位符号 + 11 位指数 + **52 位尾数**（有效精度 53 位）。十进制 0.1、0.2 转成二进制是**无限循环小数**（0.1 = `0.0001100110011…`，循环「0011」），塞进 52 位尾数时必须截断舍入，两个近似值相加得到 `0.30000000000000004`。这不是 JS 的 bug，C/Java/Python 同样如此。必答句：「**十进制小数在二进制里存不下，52 位尾数一舍入，误差就带进结果**」。

| 方案 | 写法 | 适用 | 坑 |
|---|---|---|---|
| 误差范围（判等首选） | `Math.abs(a - b) < Number.EPSILON` | 一般判等 | `EPSILON` 是「1 附近」的间距，量级大时必须换成相对误差 |
| `toFixed` | `Number((0.1 + 0.2).toFixed(1))` | 展示、固定小数位 | **返回字符串**，必须转 Number；`(1.005).toFixed(2)` 得 `'1.00'` |
| `toPrecision` | `Number(sum.toPrecision(12))` | 快速抹掉尾差 | 12 位是经验值，不保证所有量级安全 |
| 整数化 | 金额按「分」存整数，算完再除 | 金额、计数 | 乘除本身也可能引入新误差，只适合 10 的幂倍数 |
| 第三方库 | `decimal.js` / `big.js` / `bignumber.js` | 金融计算 | 有体积成本，结果要用库自己比较（`a.eq(b)`） |

```javascript
0.1 + 0.2;                                      // 0.30000000000000004
0.1 + 0.2 === 0.3;                              // false
Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON;     // true
(0.1 + 0.2).toFixed(1);                         // "0.3" —— 注意是字符串
```

- **`Number.EPSILON ≈ 2.220446049250313e-16`** 是「1 与比 1 大的最小可表示数」之差，只适合 1 附近的绝对容差；`1e16` 量级要用 `Math.abs(a-b) <= Number.EPSILON * Math.max(Math.abs(a), Math.abs(b))` 或直接按业务取 `1e-9`。
- **`0.1 + 0.2` 的精确值是 `0.30000000000000004440892098500626…`**，误差约 `5.55e-17`，所以它恰好小于 `EPSILON` 能判等——但这属于量级刚好合适，不是通用结论。
- **大整数同样失真**：超过 `Number.MAX_SAFE_INTEGER`（`2^53-1`）后 `2 ** 53 === 2 ** 53 + 1` 为 `true`，精确整数要换 `BigInt`（见本文档「十五」）。
- **工程口径：不要用浮点数存钱**。后端用整数分或 `BigDecimal`，前端计算走 `decimal.js`，展示交给 `Intl.NumberFormat`。
- `parseFloat('0.1') + parseFloat('0.2')` 依然是 `0.30000000000000004`——字符串转数字不会消除精度问题，只是把同一个近似值再取一遍。

> 相关：本文档「十二」（`number` 类型的坑）、「十五」（BigInt）、[[工具 12 - 前端学习路线]]

## 二十、什么是 HTML 语义化？

**回答重点**：语义化 = **用含义正确的标签表达内容结构**，两层含义：内容语义化（先想清这段是导航、正文还是补充说明）+ 代码语义化（选 `nav`/`article`/`aside`，而不是一层层 `div class="nav"`）。通俗说就是「**用正确的标签做正确的事**」。收益落在三处：机器（SEO、无障碍、内容抽取）、开发者（可读性与协作）、浏览器（地标导航、阅读模式、原生控件）。

| 标签 | 语义 | 什么时候用 |
|---|---|---|
| `header` / `footer` | 区块的页眉 / 页脚 | 页面级或 `article`/`section` 内部都可以有 |
| `nav` | 导航链接组 | 主导航、面包屑、分页；页脚的一堆链接不算 |
| `main` | 文档主体，**一页只能一个** | 跳过页眉页脚直达正文的地标 |
| `article` | 可独立分发的内容单元 | 博文、新闻、论坛帖子、单条评论 |
| `section` | 文档大纲中的一节，**通常带标题** | 有主题的一章；无标题的纯样式容器用 `div` |
| `aside` | 与主内容弱相关的补充 | 侧边栏、相关推荐、作者简介 |
| `figure` + `figcaption` | 独立插图及其说明 | 图片、代码片段、图表配文字说明 |

```html
<header><h1>站点名</h1><nav><a href="/">首页</a><a href="/about">关于</a></nav></header>
<main>
  <article><h2>文章标题</h2><p>正文…</p></article>
  <aside><h2>相关推荐</h2></aside>
</main>
<footer><p>© 2026</p></footer>
```

- **别为了语义化而语义化**：`section` 是「大纲里的一节」而不是「一个带背景色的块」，判断口径是「去掉样式后，这块内容该不该出现在目录里」。滥用 `section` 会让大纲噪声比全用 `div` 更大。
- **`article` vs `section` 的区分线**：`article` 能单独拎出来发到 RSS / 被转载仍然成立；评论列表里**每条评论是 `article`**，包住整块评论区的才是 `section`。
- **`h1` 数量的口径变了**：HTML5 大纲算法允许多个 `h1`，但该算法已从规范中移除、浏览器从未实现，实践仍是一页一个 `h1`、层级不跳级（`h2` 之后别直接 `h4`）。
- **`div`/`span` 不是「不语义」，而是「无语义」**：作为纯布局/样式容器完全正当，`b`/`i` 与 `strong`/`em` 的分界是「视觉加粗」vs「语义强调」，纯样式用 CSS。
- **SEO 别说成「语义化能提排名」**：它影响的是**可理解性**（结构化数据、富摘要、地标跳转），排名仍由内容与链接决定；真正硬收益在无障碍——读屏软件靠 `nav`/`main` 做地标跳转，细则见 [[工具 31 - 无障碍开发指南（Accessibility）]]。

> 相关：本文档「十一」（HTML5 更新里的语义化标签）、[[工具 31 - 无障碍开发指南（Accessibility）]]、[[工具 12 - 前端学习路线]]

## 二十一、什么是 JavaScript 的尾调用？使用尾调用有什么好处？

**回答重点**：尾调用（Tail Call）= 函数的**最后一步操作**就是调用另一个函数、并直接返回它的结果，形如 `return g(x);`。符合规范的尾调用在严格模式下可以**复用当前函数的调用帧**（Proper Tail Calls，PTC），所以深递归不再增长调用栈。但划重点：**规范里有、引擎里几乎都没有**——目前只有 Safari 的 JavaScriptCore 真正实现，V8（Chrome / Node）明确不实现。必答句：「**最后一步只是 `return g(x)` 就是尾调用；尾调用能不能省栈，要看引擎有没有实现 PTC，主流 V8 没有**」。

| 维度 | 普通递归 | 尾递归 |
|---|---|---|
| 返回形式 | `return n * f(n - 1)`，结果还要参与运算 | `return f(n - 1, acc)`，结果直接返回 |
| 调用帧 | 每层都必须保留（要乘回去） | 严格模式下可复用同一帧（PTC） |
| 空间复杂度 | O(n) 栈深度 | O(1)（**前提是引擎实现了 PTC**） |
| 栈溢出 | 万级递归即 `RangeError` | 理论上不会 |
| 额外代价 | 无 | 需要把中间结果摊成参数（`acc` / `total`） |

```javascript
// 普通递归：调用后还要乘 n，当前帧不能释放
const fact = n => n === 1 ? 1 : n * fact(n - 1);

// 尾递归：中间结果进参数，最后一步只剩「调用」这一件事
const factTail = (n, acc = 1) => n === 1 ? acc : factTail(n - 1, n * acc);

fact(10000);      // RangeError: Maximum call stack size exceeded
factTail(10000);  // V8 上同样溢栈 —— 因为 V8 没实现 PTC
```

- **PTC 的四条硬条件**：严格模式（非严格下 `arguments` / `caller` 可被观察，无法优化）；调用是最后一步；**不再引用当前作用域里的变量**；结果直接就是返回值。所以 `return g(x) + 1`、`try { return g(x) } finally { ... }`、`return [g(x)]` 都不算——`return` 后面那个表达式只要是纯粹的「调用完就没别的事」，才算尾调用。
- **V8 为什么不做**：尾调用帧消失会让 `Error.stack` 不可读、调试体验倒退，实测性能收益不明显，还牵扯 `Function.caller` 语义。这条是面试高分点——比背「省内存」更能体现判断力。
- **引擎不实现时的工程替代**：手写 **trampoline（弹床）** 或改成显式 `while` 循环。trampoline = 递归函数不直接调自己，而是返回一个「待执行的 thunk」，由外层循环驱动，栈深度恒为 1；`reduce` 累加器也是同一思路的语法糖。
- **尾调用 ≠ 尾递归**：尾调用范围更大（`compose(f, g)` 里 `return f(g(...args))` 的外层调用是尾调用，但不涉及递归）；只有**递归形式**的尾调用才谈得上省栈。
- **间接尾调用同样成立**：`const g = x > 0 ? fn1 : fn2; return g(x);` 仍然是尾调用，判断依据是「调用位置」而不是「函数名是否与自身相同」。

> 相关：本文档「十二」（函数与类型基础）、[[工具 12 - 前端学习路线]]

## 二十二、使用 let 全局声明变量，能通过 window 对象取到吗？

**回答重点**：不能。全局代码里 `var` 与函数声明落在**对象环境记录**（浏览器中即 `window`），而 `let` / `const` / `class` 落在**声明式环境记录**（规范里称 global scope / Script scope）。两者都是「全局的」、同页所有脚本都能直接引用，但**只有前者成为 `window` 的属性**。必答句：「**`var` 挂 `window`，`let` 挂的是全局词法环境——都在全局，但一个能被 `window.x` 摸到，一个摸不到**」。

| 维度 | `var` / 函数声明 | `let` / `const` / `class` |
|---|---|---|
| 记录位置 | 对象环境记录 → `window` | 声明式环境记录（Script scope） |
| `window.x` | 可读到 | `undefined` |
| 可被 `delete` | 不可（属性 `configurable: false`） | 无属性可删 |
| 重复声明 | 允许，静默覆盖 | `SyntaxError` |
| 声明前使用 | 得到 `undefined` | `ReferenceError`（TDZ） |
| 块级作用域 | 无，函数/全局 | 有 |
| 是否影响 `this` | 否 | 否 |

```javascript
var a = 1; let b = 2; function f() {}
window.a;          // 1
window.b;          // undefined
globalThis.b;      // undefined —— globalThis 就是 window 的别名
delete window.a;   // false，var 声明的属性不可配置
```

- **`window.b` 取不到，但 `b` 本身随处可用**：它依然是全局变量，只是活在 Script scope 里。DevTools Console 的作用域面板能看到独立的 `Script` 条目，那就是 `let` 全局声明所在的位置。
- **模块顶层连 `var` 都不挂 `window`**：`<script type="module">` 有独立的 Module scope，顶层 `this` 还是 `undefined`。「全局变量污染」在模块化时代等于从根上被堵住。
- **`eval` 的差别最能说明机制**：直接 `eval('var x = 1')` 把 `x` 塞进当前变量环境（非严格非模块下即 `window`）；`eval('let y = 1')` 的 `y` 只活在这次 eval 自己的词法环境里，外面拿不到。
- **设计动机就是治污染**：ES5 时代库一多，`window.$`、`window._`、`window.name` 互相打架（`window.name` 还是内置属性，被覆盖后 iframe 通信直接坏掉）。ES6 让 `let`/`const` 不落 `window`，等于给全局命名空间留了一块「私有区」。
- **`delete` 的经典追问**：`var a` 与直接赋值 `window.x = 1` 都能在 `window` 上读到，但前者 `configurable: false` 不可删、后者可删——这就是「为什么 `delete window.a` 有时 `true` 有时 `false`」的答案。
- **与本文档「十六」的分工**：那节讲 `var`/`let`/`const` 的作用域与提升差异，本节只补「全局这一层到底落在哪个环境记录」这一维度。

> 相关：本文档「十六」（let/const/var 的区别）、[[工具 12 - 前端学习路线]]

## 二十三、使用 link 和 @import 引用 CSS 的区别

**回答重点**：`<link>` 是 **HTML 标签**，解析 HTML 时就能被发现，与其他资源**并行**下载；`@import` 是 **CSS at-rule**，必须等外层 CSS 下载并解析到那一行才知道还要再拉一个文件——天生串行、多一层往返。两者的**样式权重相同**（同来源、同 specificity 下按出现顺序覆盖），差别全在**加载时机与可控性**。必答句：「**`link` 由 HTML 预加载扫描器并行发现，`@import` 要等外层 CSS 解析完才知道，多一跳就慢一截**」。

| 维度 | `<link rel="stylesheet">` | `@import` |
|---|---|---|
| 归属 | HTML 标签 | CSS at-rule |
| 发现时机 | HTML 解析阶段（preload scanner 可提前发现） | 外层 CSS 下载并解析后 |
| 下载方式 | 与 HTML、其他资源并行 | 串行，层层依赖 |
| 位置限制 | `<head>` / `<body>` 内任意位置 | **必须在样式表所有规则之前**（仅 `@charset`、`@layer` 声明可先出现） |
| 条件加载 | `media` 属性，不匹配则不阻塞渲染 | 可在 `url()` 后写媒体查询 |
| JS 可控性 | `link.sheet`、`link.disabled`、改 `href` 换肤 | 基本不可控，需改写 CSSOM |
| 现代能力 | `preload as="style"`、`integrity`、`onload` 异步切换 | `layer()` 级联分层、`supports()` 能力探测（Chrome 91+） |

```html
<link rel="stylesheet" href="base.css">
<link rel="stylesheet" href="print.css" media="print">
<style>
  /* @import 写在规则之后会被整条忽略，不报错 */
  @import url("theme.css") layer(theme) screen;
</style>
```

- **顺序即权重，而 `@import` 的「位置」等于那一行**：引入的规则不排在外层文件末尾，而是插在 `@import` 所在处——这是「我明明写在后面却不生效」的头号原因。
- **`@import` 位置写错会静默失效**：只要前面出现过任何普通规则，浏览器直接忽略这条 `@import`，控制台不报错，排查靠肉眼。
- **现代 CSS 里 `@import` 并非无用**：`layer()` 把第三方库压到最低优先级、`supports()` 做能力分支，表达力比 `<link>` 强；设计系统/组件库内部拆分样式仍常用。
- **性能结论要分协议**：HTTP/1.1 下每个 `@import` 多一次串行请求，伤害明显；HTTP/2 多路复用能缓解握手开销，但**发现时机的延迟仍在**，首屏关键 CSS 依旧走 `<link>` 或直接内联。
- **首屏优化常用组合**：关键 CSS 内联进 `<style>`，非关键用 `<link rel="preload" as="style" onload="this.rel='stylesheet'">` 异步化——别把 `@import` 串在关键路径上。
- **只有 `<link>` 能开关**：`document.querySelector('#theme').disabled = true` 可即时启停整张表，`@import` 引入的表无法这样操作。

> 相关：本文档「九」（`src` 与 `href` 的区别）、[[工具 12 - 前端学习路线]]

## 二十四、如何判断 JavaScript 变量是数组？

**回答重点**：五条路都能走通，但只有一条能上生产——`Array.isArray()`。必答句：「**首选 `Array.isArray`，它按语言内部类型判断、跨 iframe 也可靠；`instanceof`、`__proto__`、`isPrototypeOf` 全都依赖原型链，跨执行环境会误判，`typeof` 更是只能返回 `'object'`**」。

| 方法 | 写法 | 可靠性 | 关键问题 |
|---|---|---|---|
| `Array.isArray` | `Array.isArray(obj)` | ✅ 生产首选 | ES5.1 就有了（常被误记成 ES6 新增），不做原型链查找 |
| `toString` 判型 | `Object.prototype.toString.call(obj).slice(8,-1) === 'Array'` | ✅ 通用兜底 | 能判所有内置类型（`Date`/`RegExp`/`Map`），但 `Symbol.toStringTag` 可伪造 |
| `instanceof` | `obj instanceof Array` | ⚠️ 单页面内可用 | **跨 iframe / 跨 realm 必失效**，两边 `Array.prototype` 不是同一个对象 |
| `isPrototypeOf` | `Array.prototype.isPrototypeOf(obj)` | ⚠️ 同上 | 本质也是原型链查找，只是比 `instanceof` 更显式 |
| `__proto__` | `obj.__proto__ === Array.prototype` | ❌ 不推荐 | 非标准属性（历史遗留访问器），应改用 `Object.getPrototypeOf(obj)` |

```js
Array.isArray(obj);                                          // ✅ 面试就答这个
Object.prototype.toString.call(obj) === '[object Array]';    // 通用类型判定兜底
Object.getPrototypeOf(obj) === Array.prototype;              // 原型链视角（仅同 realm）
```

- **必答句背后的原理**：`Array.isArray` 走的是引擎内部的类型检查，不读原型链、不看 `constructor`，所以 `obj.constructor = Array` 这类伪装骗不过它；反过来 `instanceof` 恰好只认原型链，最容易被跨窗口场景打穿。
- **追问「类数组算数组吗」**：`arguments`、`NodeList`、字符串都是「有 `length` 能下标」但 `Array.isArray` 返回 `false`，要转真数组用 `Array.from` / 展开运算符。
- **追问「怎么判断纯对象」**：`Object.getPrototypeOf(v) === Object.prototype`；要区分数组/日期/正则时统一用 `Object.prototype.toString.call`。
- **与本文档的分工**：「十二」讲 `typeof` 对各类型的返回值、「十八」讲 `typeof` 与 `instanceof` 的差异，本节只回答「数组这一种类型怎么判最稳」。

> 相关：本文档「十二」（JavaScript 数据类型）、「十八」（typeof 和 instanceof 的区别）、[[工具 12 - 前端学习路线]]

## 二十五、如何解决页面请求接口大规模并发问题

**回答重点**：按「**前端限流 → 缓存复用 → 服务端扩容**」三层递进回答，别一上来就说加机器。必答句：「**前端做并发控制（队列、请求合并、防抖节流）把瞬时压力削平，中间靠缓存（浏览器 / HTTP 头 / CDN）把重复请求挡掉，最后才是服务端索引、Redis、负载均衡兜底；浏览器对同域 HTTP/1.1 只给 6 个并发连接，所以首屏真正的瓶颈常常是关键路径争抢而不是接口本身**」。

### 1、前端并发控制：队列 + 合并 + 节流

```js
class RequestQueue {
  constructor(max = 5) { this.max = max; this.queue = []; this.running = 0; }
  async add(task) {
    if (this.running >= this.max) await new Promise(r => this.queue.push(r)); // 排队等空位
    this.running++;
    try { return await task(); }
    finally {
      this.running--;
      if (this.queue.length) this.queue.shift()();   // 释放一个空位，唤醒队首
    }
  }
}

// 请求合并：同一 key 在途时复用同一个 Promise，天然去重
class RequestMerge {
  constructor() { this.pending = new Map(); }
  request(key, fn) {
    if (this.pending.has(key)) return this.pending.get(key);
    const p = fn().finally(() => this.pending.delete(key));
    this.pending.set(key, p);
    return p;
  }
}
```

- **队列 vs 合并别混答**：队列解决「**同时太多**」（限并发数），合并解决「**同样的请求发了多次**」（去重），列表页首屏两者通常一起用。
- **防抖节流**只治「用户连续触发」（搜索框、滚动加载、resize），治不了初始化时一次性打出的几十个接口。

### 2、缓存：把重复请求变成零请求

| 层次 | 手段 | 生效条件 |
|---|---|---|
| 内存 | `Map` + TTL 的 `CacheManager`（`set` 存 `{value, timestamp}`，`get` 过期即删） | 单页生命周期内 |
| 存储 | `localStorage` / `IndexedDB` | 跨会话，需自己管版本与失效 |
| HTTP | `Cache-Control`、`ETag`/`If-None-Match`、`max-age` | 由浏览器与 CDN 执行，最省事 |
| CDN | 静态资源与可缓存的 GET 接口下沉到边缘 | 接口需幂等、无用户态 |

### 3、服务端与传输层

- **数据库**：加索引、避免 N+1 查询、热点数据进缓存；**缓存**：Redis 多级缓存 + 缓存预热；**流量**：Nginx 负载均衡、服务降级、熔断。
- **传输层**：HTTP/2 多路复用（同域一个连接跑多请求，绕开 6 连接上限）、Gzip/Br 压缩、静态资源 CDN。
- **代码层**：`AbortController` 取消过期请求（切页/改条件时立刻 abort）、超时与重试（带指数退避，只对幂等请求重试）。
- **架构层**：能不用轮询就不用——实时性要求高改 SSE / WebSocket；列表接口做分页 + 懒加载，从源头减少一次要拉的量。

## 二十六、如何计算 CSS 的优先级？

**回答重点**：优先级不是一个十进制分数，而是 **(ID 数, 类/属性/伪类数, 元素/伪元素数) 三元组**逐位比较，同分才看书写顺序。必答句：「**优先级按 (ID, 类, 元素) 三元组比较、不进位——11 个类选择器也压不过 1 个 ID；`!important` 和内联样式是三元组之外的两条独立规则，继承来的样式优先级最低**」。

| 选择器类型 | 示例 | 三元组记法 | 常见口头权重 |
|---|---|---|---|
| 内联样式 | `style="color:red"` | 三元组之外，高于所有普通规则 | 1000 |
| ID 选择器 | `#app` | (1,0,0) | 100 |
| 类 / 属性 / 伪类 | `.btn`、`[type=text]`、`:hover` | (0,1,0) | 10 |
| 元素 / 伪元素 | `div`、`::before` | (0,0,1) | 1 |
| 通配、组合符 | `*`、`>`、`+`、`~`、后代空格 | (0,0,0) | 0 |

```css
#nav .item a:hover { }   /* (1, 2, 1) —— 1 个 ID、.item + :hover 两个类、a 一个元素 */
```

- **为什么不能当十进制加**：`.a.b.c.d.e.f.g.h.i.j.k`（11 个类）在「1000/100/10/1」算法里是 110 > 100，看起来能压过 `#id`，实际浏览器里**永远压不过**——三元组比较是逐位字典序，第一位输了就直接出局。
- **`!important` 的正确位置**：它反转的是「来源与层叠层」的顺序，不只是「压过内联」；两个 `!important` 相遇时，回到三元组正常比较。
- **同分看顺序**：权重完全相同则后定义的生效（同一张表内按出现位置，多张表按引入顺序）。
- **继承的样式权重最低**：`div { color: red }` 里的 `color` 会继承给子元素，但子元素上任何一条直接命中它的规则（哪怕只是 `*`）都能盖掉继承值。
- **现代 CSS 的三个新变量**（八股加分项）：`:is()` / `:not()` 取参数里**最高**的权重；`:where()` **恒为 0**（适合写重置样式）；`@layer` 按层声明顺序决定胜负，**层序压过三元组**——`!important` 在层叠层里是反序的（先声明的层反而赢）。
- **实战排查口径**：样式不生效先看 DevTools 的 Computed 面板，划掉的规则会显示「被哪条覆盖」，比心算权重快得多。

## 二十七、常用的 HTML meta 标签有哪些？

**回答重点**：`<meta>` 用 `name`/`content`（或 `http-equiv`/`content`）描述文档元数据——`name` 说明「信息类型」，`content` 给出「实际值」。必答句：「**必背三类是 `charset`（编码）、`viewport`（响应式视口）、`description` + `keywords`（SEO）；再补 `robots`（抓取控制）、Open Graph / Twitter Card（社媒分享卡片）、`http-equiv="refresh"`（定时刷新/跳转）**」。

| 标签 | 作用 | 典型写法 |
|---|---|---|
| `charset` | 声明字符编码，现代网页统一 UTF-8（H5 推荐用它替代 `http-equiv="Content-Type"`） | `<meta charset="UTF-8">` |
| `viewport` | 响应式视口，让页面宽度等于设备宽度 | `<meta name="viewport" content="width=device-width, initial-scale=1.0">` |
| `description` | 页面摘要，可能作为搜索结果里的描述，影响 SEO | `<meta name="description" content="页面描述">` |
| `keywords` | 关键词，SEO 辅助（现代搜索引擎权重已很低） | `<meta name="keywords" content="关键词1, 关键词2">` |
| `author` | 文档作者 | `<meta name="author" content="作者名">` |
| `refresh` | N 秒后刷新或跳转（`content="0; url=..."` 即重定向） | `<meta http-equiv="refresh" content="30">` |
| `robots` | 控制搜索引擎抓取/索引，取值 `all` / `none` / `index` / `follow` / `noindex` / `nofollow` | `<meta name="robots" content="noindex, nofollow">` |
| `X-UA-Compatible` | 让 IE 用最新内核（`edge`）渲染，历史兼容项 | `<meta http-equiv="X-UA-Compatible" content="IE=edge">` |
| Open Graph | 社媒分享时的标题/描述/图/链接 | `<meta property="og:title" content="标题">` |
| Twitter Card | 分享到 X/Twitter 的卡片样式 | `<meta name="twitter:card" content="summary">` |

- **`viewport` 的 content 参数**：`width`（数值或 `device-width`）、`height`、`initial-scale`（初始缩放）、`maximum-scale` / `minimum-scale`、`user-scalable`（yes/no）。移动端要禁止缩放就写 `user-scalable=no, maximum-scale=1.0`（无障碍场景慎用）。
- **三种属性归属别混**：标准元数据用 `name`（`description`/`robots`/`twitter:*`）、HTTP 头等价物用 `http-equiv`（`refresh`/`X-UA-Compatible`/`Content-Type`）、RDFa 社媒协议用 `property`（`og:*`）。
- **SEO 常见说法**：`description` 影响点击率、`robots` 控制收录，`keywords` 已被主流引擎基本忽略——面试时点出这点是加分项。

## 二十八、有哪些 CSS 选择器？请分别介绍

**回答重点**：按「选谁」把选择器分五类——**基础**（类型 / 类 / ID / 通配）、**层次（组合）**（后代、子、相邻兄弟、通用兄弟）、**属性**、**伪类**（状态）、**伪元素**（元素的一部分）。必答句：「**基础 + 层次 + 属性 + 伪类 + 伪元素是五大类；权重按 (ID, 类/属性/伪类, 元素/伪元素) 三元组比较，组合选择器本身不加权、群组选择器取组内最高**」。

| 类别 | 语法 | 匹配对象 | 三元组权重 |
|---|---|---|---|
| 通配 | `*` | 所有元素 | (0,0,0) |
| 类型（标签） | `p` | 指定标签的全部元素 | (0,0,1) |
| 类 / ID | `.intro` / `#header` | 指定 class / id | (0,1,0) / (1,0,0) |
| 后代 / 子 | `div p` / `ul > li` | 所有后代 / 仅直接子元素 | 组合符本身不计权 |
| 相邻 / 通用兄弟 | `h1 + p` / `h1 ~ p` | 紧跟的下一个 / 之后所有兄弟 | 组合符本身不计权 |
| 属性 | `[type]` / `[type="text"]` | 有该属性 / 属性值相等 | (0,1,0) |
| 属性模糊匹配 | `[class^="btn-"]`、`[href$=".pdf"]`、`[title*="hello"]`、`[lang|="zh"]` | 前缀 / 后缀 / 包含 / 连字符前缀 | (0,1,0) |
| 伪类 | `:hover`、`:nth-child(2n)`、`:focus` | 特定状态或位置的元素 | (0,1,0) |
| 伪元素 | `::before`、`::after`、`::first-line` | 元素的某一部分 | (0,0,1) |
| 群组 | `h1, h2, h3` | 同时命中多个选择器 | 取组内最高 |

- **易错点一**：`::before` / `::after` 是伪元素（单冒号 `:before` 是 CSS2 遗留写法），必须配 `content` 才渲染；`:hover` / `:nth-child()` 是伪类。
- **易错点二**：`>` `+` `~` 和后代空格只是「关系」，自身不贡献权重，权重只数两侧的选择器。
- **易错点三**：属性选择器的 `^=` `$=` `*=` `|=` `~=` 是四种不同的模糊匹配，别只记 `[attr=value]`。
- 权重怎么算、`!important` / `:is()` / `:where()` / `@layer` 的边界 → 见本文档「二十六」，此处不重复展开。

## 二十九、说说你对 JS 作用域的理解？

**回答重点**：作用域就是**变量/函数的可访问范围**，静态地在书写位置就确定（词法作用域）。必答句：「**分全局作用域和局部作用域，局部再分函数作用域（`var`）和块作用域（ES6 的 `let`/`const`）；查找变量沿作用域链由内向外，闭包就是函数记住了它被定义时的作用域**」。

| 作用域 | 创建方式 | 可见范围 |
|---|---|---|
| 全局 | 函数体与代码块外声明，或未声明的隐式全局（严格模式禁止） | 整个脚本 |
| 函数作用域 | 函数内 `var` 声明 / 函数参数 | 仅函数体内 |
| 块作用域 | `{}` 内用 `let` / `const` 声明（`if`、`for`、`try` 都算块） | 仅该代码块 |

- **提升（Hoisting）**：`var` 只提升声明不提升赋值（提升后是 `undefined`）；`function` 声明整个函数体一起提升，可先调用后定义；`let`/`const` 也提升但处于「暂时性死区（TDZ）」，声明前访问直接报 `ReferenceError`。
- **作用域链**：先在当前作用域找，找不到逐层向外，直到全局；仍未找到 → 访问时抛 `ReferenceError`（只有 `typeof undeclaredVar` 这种写法返回 `"undefined"` 而不报错）。
- **闭包（Closure）**：内层函数持有外层作用域的引用，外层执行完后变量仍不被回收——用于私有变量、函数工厂、防抖节流里的状态保持；代价是内存不释放，长生命周期的闭包要留意泄漏。
- **IIFE**：`(function(){ ... })()` 立即执行并制造一个新作用域，ES6 之前用来隔离变量、避免全局污染；现在多用块作用域或模块替代。
- **模块作用域**：ES Module 的顶层变量默认只在本模块内可见，靠 `export` / `import` 显式暴露，天然避免全局污染。
- **严格模式**：`'use strict'` 下给未声明变量赋值直接报错（不再隐式创建全局），`this` 在普通函数调用时为 `undefined` 而非 `window`。

> 相关：本文档「十六」（`let`/`const`/`var` 的区别）、「二十二」（`let` 全局声明不挂到 `window`）、[[工具 01 - 前端问题排错指南]]

## 三十、说说你对 fetch 的理解，它有哪些优点和不足？

**回答重点**：`fetch` 是浏览器原生的、**基于 Promise 的网络请求 API**，是 `XMLHttpRequest` 的现代替代品，抽象出 `Request` / `Response` 对象并暴露响应流。必答句：「**优点是基于 Promise 支持 `async/await`、有 Request/Response 对象、能用 `response.body` 读流做流式渲染；不足是默认不带 cookie、没有原生取消和上传进度、HTTP 4xx/5xx 不会 reject**」。

| 维度 | 说明 |
|---|---|
| Promise 化 | 返回 Promise，链式 `then` 或 `await` 都行，避免 XHR 的回调地狱与状态码判断样板 |
| Request / Response 对象 | 请求与响应都是结构化对象，可直接 `clone()`、改 `headers`，便于封装请求库和重试 |
| 流式响应 | `response.body` 是 `ReadableStream`，可逐块解析，实现大模型「打字机」效果的边下边渲染（XHR 做不到） |
| 默认不带 Cookie | `credentials` 默认 `omit`，跨域带票据必须显式设 `same-origin` / `include` |
| 无原生取消 | 靠 `AbortController` + `signal` 中断，超时也可用 `AbortSignal.timeout(ms)` |
| 无上传进度 | 没有 `onprogress`；上传进度需退回 XHR，下载进度可用流的 reader 手动累加 |
| 错误语义反直觉 | 只有网络层失败才 reject，`404` / `500` 是 resolve，必须自己查 `response.ok` |

```javascript
const res = await fetch('/api/data', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'John' }),
  credentials: 'include',          // 跨域带 cookie
  signal: AbortSignal.timeout(5000) // 5s 超时，替代 Promise.race
});
if (!res.ok) throw new Error(`HTTP ${res.status}`);  // 状态码要自己判
const data = await res.json();
```

- **`mode` 三档**：`cors`（默认，可跨域带 CORS 头）、`no-cors`（只发简单请求，响应是 opaque 拿不到内容）、`same-origin`（跨域直接拒发）。
- **超时的两种写法**：`AbortSignal.timeout()` 最简洁；老环境用 `Promise.race([fetch(...), timeout(5000)])`，但要注意 race 失败后请求并未真正中断（仍占连接）。
- **`AbortError` 要单独识别**：`error.name === 'AbortError'` 属于主动取消，不该上报成业务错误。
- **与 axios 的取舍**：axios 自带 JSON 序列化、状态码 reject、进度与拦截器，业务项目省事；`fetch` 零依赖、体积小，做 SDK 或需要流式时更合适。

> 相关：[[工具 04 - Ajax异步通信]]（XHR 与 Ajax 基础）、本文档「二十五」（接口大规模并发：队列与缓存）

## 三十一、TypeScript 有哪些常用类型？

**回答重点**：按「基础 / 复杂 / 特殊」三类记。必答句：「**基础类型 7 个：`string`、`number`、`boolean`、`null`、`undefined`、`symbol`、`bigint`；复杂类型有数组、元组、枚举、`object`；特殊类型有 `any`、`unknown`、`never`、`void`**」。

| 分类 | 类型 | 要点 |
|---|---|---|
| 基础 | `string` / `number` / `boolean` | 小写开头是原始类型，`String` / `Number` 是包装对象类型，业务里别用后者 |
| 基础 | `null` / `undefined` | 默认是其他类型的子类型（`strictNullChecks` 关闭时），开启后必须显式声明联合 |
| 基础 | `symbol` / `bigint` | `Symbol()` 做唯一键；`bigint` 存任意精度整数，字面量需 `123n`，不能与 `number` 直接混算 |
| 复杂 | 数组 `T[]` / `Array<T>` | 两种写法等价，`readonly T[]` 表示不可变 |
| 复杂 | 元组 `[string, number]` | 固定长度且逐位定类型；访问越界元素时用联合类型兜底，赋值超出联合即报错 |
| 复杂 | 枚举 `enum` | 默认从 0 递增编号，可手动指定起始值或全量赋值；编译后是真实对象（有运行时开销） |
| 复杂 | `object` | 指非原始类型，但范围太宽，实际应用对象字面量 / `interface` 描述结构 |
| 特殊 | `any` / `unknown` | `any` 放弃检查、可任意调用；`unknown` 必须先窄化（`typeof` / 断言）才能用，是 `any` 的安全替代 |
| 特殊 | `never` / `void` | `never` 表示永无返回值（抛异常、死循环、穷尽性检查）；`void` 表示函数正常返回但没有值 |

- **`never` 的实战用法**：`switch` 的 `default` 里写 `const _exhaustive: never = value`，新增枚举成员忘了处理时编译期就报错。
- **类型别名与接口**：`type Point = { x: number; y: number }` 与 `interface Person { ... }` 描述对象几乎等价，差别是接口能声明合并、能被 `extends` 多继承；类型别名能表达联合、交叉、条件类型。
- **联合 / 交叉**：`string | number` 表示「或」，`A & B` 表示「与」（成员合并）。

## 三十二、什么是 TypeScript 的对象类型？怎么定义对象类型？

**回答重点**：对象类型描述**非原始类型的值**——具有特定结构的对象、数组、函数。必答句：「**三种定义方式：匿名（内联字面量，适合一次性参数）、`type` 别名（适合联合/交叉/条件类型）、`interface`（适合可扩展、可声明合并的对象契约）**」。

| 方式 | 写法 | 适用场景 |
|---|---|---|
| 匿名 | `function greet(p: { name: string; age: number })` | 只在单处使用的临时结构，不打算复用 |
| 类型别名 | `type Person = { name: string; age: number }` | 需要组合类型（`A & B`、`A \| B`）、给复杂类型起名 |
| 接口 | `interface Person { name: string; age: number }` | 描述对象/类的契约，需要 `extends` 多继承或声明合并（如扩展第三方类型） |

- **属性修饰符**：`?` 标可选（`age?: number`，可省略但存在时类型必须对）；`readonly` 标只读（初始化后不可改，浅只读，嵌套对象仍可变）；索引签名 `[index: number]: string` 描述「键类型已知、键名未知」的字典结构。
- **类型扩展两条路**：接口 `extends` 可多继承（`interface C extends A, B {}`）；交叉类型 `type C = A & B` 效果相同，且能作用于 `type` 定义。
- **泛型对象类型**：`interface Container<T> { value: T }`、`class Stack<T>`、`function identity<T>(arg: T): T`；上限用约束 `T extends Lengthwise` 保证「至少具有 `length`」。
- **接口还能描述函数**：`interface SearchFunc { (s: string, sub: string): boolean }`，用调用签名约束「可被调用」的对象。
- **易错点**：`readonly` 只在编译期生效、运行时无保护；可选属性 `?` 与 `| undefined` 不完全等价（前者允许键缺失，但 `exactOptionalPropertyTypes` 下行为不同）。

> 相关：本文档「三十一」（常用类型总览）

## 三十三、ES6 有哪些新特性？

**回答重点**：先定性——ES6（ES2015）是 JS 历史上最大的一次语言升级，把「函数 + 原型」的语言扩成了「块级作用域 + 类 + 模块 + 异步原语 + 新集合」。必答句：「**按六类记：作用域（`let`/`const`）、语法糖（箭头函数、模板字符串、解构、默认参数、扩展运算符、属性简写）、面向对象与模块化（`class`、`import`/`export`）、异步（`Promise`）、新原始类型与协议（`Symbol`、迭代器与 `for...of`）、新数据结构（`Map`/`Set`）**」。答满 11 项即可收尾，细节留给追问。

| # | 特性 | 一句话作用 | 易错点 / 常考追问 |
|---|---|---|---|
| 1 | `let` / `const` | 块级作用域声明，替代函数作用域的 `var` | 都有 TDZ；`const` 锁的是**绑定**，对象内容照样改（本文档「十六」） |
| 2 | 箭头函数 | 更短的函数写法，`this` 取自词法外层 | 不能 `new`、无 `arguments` / `prototype`、不能 `yield`（本文档「五」「三十四」） |
| 3 | 模板字符串 | 反引号包裹，`${}` 插值，天然支持多行 | 插值里是**表达式**不是语句；嵌套反引号要转义；标签模板可做 `String.raw`、CSS-in-JS |
| 4 | 解构赋值 | 按位置（数组）或按属性名（对象）批量取值 | 对象解构**与顺序无关**、可重命名 `{a: x}`、可给默认值；解构 `null`/`undefined` 直接抛错 |
| 5 | 默认参数 | 形参可写缺省值 | 只在实参为 `undefined` 时生效，传 `null` 不生效；默认值在**调用时**求值，可引用前面的形参 |
| 6 | 扩展运算符 / rest | `...` 展开数组、对象、可迭代对象；rest 把剩余实参收成数组 | 对象展开是**浅拷贝**；`[...'abc']` 得 `['a','b','c']`；rest 是**真数组**，`arguments` 是类数组 |
| 7 | `class` 与模块 | `class` 是原型继承的语法糖（含 `extends` / `super`）；`import` / `export` 做静态模块 | `class` 不提升（TDZ）、必须 `new` 调用、原型方法不可枚举；ESM 顶层 `this` 是 `undefined`，且是静态解析、可 tree-shaking |
| 8 | `Promise` | 异步的状态机：`pending` → `fulfilled` / `rejected` | 状态**不可逆**、`then` 值可穿透、错误走第二个回调或 `catch`；`Promise.all` 有一个失败就整体失败 |
| 9 | `Symbol` 与迭代器 | `Symbol()` 产生唯一原始值当键；`Symbol.iterator` 自定义 `for...of` 行为 | `Symbol()` 不能 `new`；`for...in` / `JSON.stringify` 拿不到 Symbol 键；`for...of` 只吃**可迭代对象**（普通对象不行） |
| 10 | `Map` / `Set` | 键值对集合（键可为任意类型，保插入序）；不重复元素的集合 | 对象键按**引用**比较；`Set` 用 SameValueZero 去重，`NaN` 只留一个、`{}` 不去重 |
| 11 | 属性 / 方法简写 | `{ x, y }`、`{ foo() {} }` 省掉重复的键名与 `function` | 常与计算属性名 `{ [key]: v }` 一起考 |

```js
const m = new Map();
m.set({ id: 1 }, 'obj');       // 也可以 new Map().set(...) 链式
console.log(m.get({ id: 1 }));  // undefined —— 对象键按引用比较，换一个对象就不相等

const s = new Set([1, 1, NaN, NaN, {}, {}]);
console.log(s.size);            // 4 —— NaN 合并，两个 {} 各算一个

const range = { from: 1, to: 3, *[Symbol.iterator]() { for (let i = this.from; i <= this.to; i++) yield i; } };
console.log([...range]);        // [1, 2, 3] —— 有 Symbol.iterator 就能被 for...of / 展开
```

- **别把 ES6 当成「11 个孤立知识点」**：面试官真正想听的是「块级作用域 + 词法 this + 模块 + Promise」这四条改变了什么写法——闭包不再靠 IIFE 兜住循环变量、回调回调不再层层嵌套、全局变量污染被模块隔离。
- **`for...of` 为什么不能遍历普通对象**：它只认 `Symbol.iterator`，普通对象没实现；要遍历用 `Object.keys` / `Object.entries` 或 `for...in`（会带原型链上的可枚举属性）。
- **`class` 不是新东西**：本质还是构造函数 + 原型链，`typeof Person === 'function'`，`Person.prototype.greet` 存在；差异在不可枚举、必须 `new`、内部默认严格模式。
- **兼容性怎么答**：ES6 在现代浏览器已全面可用，老环境靠 Babel 转语法 + `core-js` 补 API（`Promise`、`Map`、`Symbol` 属于**运行时 API**，转译器补不了，得靠 polyfill）。

## 三十四、ES6 箭头函数能当构造函数吗？

**回答重点**：不能。必答句：「**`new` 需要 `Construct` 内部方法和 `prototype` 属性，箭头函数两样都没有，且 `this` 在定义时就绑死在外层，无法被初始化成新实例，因此 `new f()` 直接抛 `TypeError: f is not a constructor`**」。

| 前提条件 | 普通函数 / `class` | 箭头函数 | 后果 |
|---|---|---|---|
| `Construct` 内部方法 | 有 | **无**（只有 `Call`，没有构造能力） | `new` 一开始就失败，抛 TypeError |
| `prototype` 属性 | 有，指向 `{ constructor: fn }` | **无**（`f.prototype === undefined`） | 实例的 `__proto__` 无处可指，原型链断掉 |
| `this` 绑定时机 | 调用时由 `new` 新建对象并赋给它 | 定义时锁定外层 `this` | 无法把新实例写成 `this` |
| `new.target` / `super` | 支持 | 不支持 | 派生类那套初始化逻辑无从实现 |

```js
const f = () => {};
console.dir(f);  // 无 arguments / caller / prototype，但有 __proto__ → Function.prototype
new f;           // TypeError: f is not a constructor
```

补一句区分 `__proto__` 与 `prototype`：前者是**函数作为对象**的原型链（指向 `Function.prototype`，决定它能用 `call` / `bind`），后者只在 `new` 时给实例当原型——箭头函数有前者、没有后者，正好说明「能当对象用，不能当构造器用」。

## 三十五、CSS 优化和提高性能的方法有哪些？

**回答重点**：CSS 优化的落点是**减少请求 / 减小体积 / 缩短关键渲染路径 / 避免触发布局与绘制**四条线，八条常见手段都能归到这四类里。必答句：「**合并最小化减请求与体积，`head` 内联关键 CSS 缩短首屏渲染，选择器与冗余规则减少解析与匹配开销，动画只用 `transform`/`opacity` 避免重排重绘**」。

| 手段 | 解决什么 | 关键做法 | 代价 / 坑 |
|---|---|---|---|
| 合并 + 最小化 | HTTP 请求数、文件体积 | Webpack/Gulp 打包合并；CSSNano、UglifyCSS 去空格注释 | HTTP/2 多路复用后「合并」收益变小，**别为合并牺牲缓存粒度** |
| CSS 预处理器 | 可维护性 | Sass/LESS 的变量、嵌套、mixin、函数 | **不减小产物体积**，嵌套过深反而生成超长选择器 |
| 少用高级选择器 | 选择器匹配耗时 | 用 `.class` 代替 `div p`、`*`、深层后代选择器 | 现代浏览器匹配是**从右往左**，真正昂贵的是最右端不具体 |
| 去冗余样式 | 体积 + 可维护性 | PurifyCSS、UnCSS 扫描未使用规则 | 动态拼接的类名会被误删，需白名单 |
| CSS Sprite | 请求数 | 多图标合成一张图，`background-position` 定位 | 图标改动要重切图；现在多用 iconfont / SVG symbol |
| 动画调优 | 重排重绘 | 用 `transform: translateX(100px)` 代替 `left: 100px` | 只有 `transform`/`opacity`/`filter` 能只走合成层，改 `width`/`top` 必触发 layout |
| 放置位置 | 首屏渲染 | `<link>` 放 `<head>`，避免样式后到导致 FOUC / 无样式白屏 | 放 body 底部会让用户先看到裸 HTML |
| 内联关键 CSS | 首次渲染时间 | 首屏所需样式写进 `<head>` 的 `<style>` | 内联部分**不参与缓存**、每次 HTML 重传；非关键 CSS 应异步加载 |

```css
/* 好：只触发合成 */
.card:hover { transform: translateX(8px); transition: transform .2s; }
/* 差：每帧重排 */
.card:hover { left: 8px; }
```

问「还有吗」时的增量：`content-visibility: auto` 跳过屏外渲染、`will-change` 提前提层（滥用反而吃显存）、按路由拆 CSS、字体 `font-display: swap` 防阻塞文字渲染。

## 三十六、Core Web Vitals 是什么？它包括哪些指标？

**回答重点**：Core Web Vitals 是 Google 提出的**核心网页指标**，用三个可量化指标衡量真实用户体验的三个维度——加载、交互、视觉稳定。必答句：「**LCP 衡量加载（≤2.5s 优秀）、INP 衡量交互响应（≤200ms 优秀）、CLS 衡量视觉稳定性（≤0.1 优秀），三者都进入 Google 搜索排名信号**」。

| 指标 | 全称 / 衡量维度 | 优秀 | 需要改进 | 差 |
|---|---|---|---|---|
| **LCP** | Largest Contentful Paint，最大内容渲染时间 / 加载性能 | ≤ 2.5s | 2.5s – 4.0s | > 4.0s |
| **INP** | Interaction to Next Paint，交互到下一帧绘制 / 互动性 | ≤ 200ms | 200 – 500ms | > 500ms |
| **CLS** | Cumulative Layout Shift，累积布局偏移 / 视觉稳定性 | ≤ 0.1 | 0.1 – 0.25 | > 0.25 |

**各自怎么优化**：

- **LCP**：优化 TTFB（服务端响应 / 缓存 / CDN）、`preload` 首屏大图与字体、图片压缩 + 响应式尺寸、避免首屏资源被 JS 阻塞。
- **INP**：拆分长任务让出主线程、事件处理里少做同步计算、输入类交互用防抖节流、减少不必要的重渲染。
- **CLS**：`<img>`/`<video>` 预设 `width`/`height` 或 `aspect-ratio`、字体 `size-adjust` 防切换抖动、不要在已有内容上方插入内容、广告位提前占位。

```javascript
import { onLCP, onINP, onCLS } from 'web-vitals';

// 三个指标统一上报，sendBeacon 保证页面卸载也能送达
[onLCP, onINP, onCLS].forEach((metric) =>
  metric(({ name, value, id }) =>
    navigator.sendBeacon('/api/vitals', JSON.stringify({ name, value, id }))
  )
);
```

**监控手段**：实验室数据用 Lighthouse / PageSpeed Insights / Chrome DevTools Performance；真实用户数据（字段数据）看 Google Search Console 的 Core Web Vitals 报告，自建则用 `web-vitals` 库上报。注意 **FID 已被 INP 取代**（2024 年 3 月起正式替换），只答 FID 会被认为知识过期；另外这三个指标都在**真实用户、移动端**环境下评估，本地跑分漂亮不等于达标。

## 三十七、DIFF 算法的原理是什么？

**回答重点**：DIFF 是虚拟 DOM 的**差异化更新**策略——比较新旧两棵 vnode 树，只把差异落到真实 DOM。必答句：「**核心是『同层比较 + 类型不同直接替换 + 类型相同则复用节点并递归比较子节点』，配合 `key` 在同层内做节点复用，把 O(n³) 的树编辑距离问题降到 O(n)**」。

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 树递归比较 | 从根节点深度优先遍历新旧 vnode | 只遍历有变化的子树 |
| 同层比较 | 只比同一层级的节点，**不跨层级移动** | 跨层比较是 O(n³)，前端场景几乎不出现跨层移动 |
| 类型不同 | `div` → `p`、组件类型变了：**销毁旧节点整棵子树、新建** | 结构已不同，复用没有意义 |
| 类型相同 | 复用 DOM 元素，diff `props`/`attrs` 增量更新，再递归子节点 | 省掉创建销毁开销 |
| 子节点列表 | 有 `key` 时按 key 建索引做匹配（Vue3 用**最长递增子序列**求最少移动） | 无 key 只能按位置逐个比，插入头部会导致整列 patch |

```js
// 无 key：在头部插入一项 → 后续每项都“被改成”前一项，全部重渲染
// 有 key：按 key 命中旧节点，只新建 1 个、其余原地复用
```

**增量与坑**：`key` 必须**稳定且唯一**，用数组下标当 key 等价于没写（顺序一变就退化成按位置比）；`key` 变化 = 类型变化 = 销毁重建，会丢组件内部状态。React 的 diff 额外靠 `type` + `key` 双重判定，Vue2 是双端对比（头头、尾尾、头尾交叉），Vue3 改为「同步头部 → 同步尾部 → 处理乱序区间 + 最长递增子序列」。延伸一句：DIFF 本身有运行时成本，所以 Solid.js / Svelte 这类编译型框架干脆不要虚拟 DOM。

## 三十八、Node.js 中的 Buffer 对象是什么？它有什么作用？

**回答重点**：Buffer 是 Node 提供的**定长字节缓冲区**，本质是 `Uint8Array` 的子类，用来在 JS 字符串之外直接读写二进制数据。必答句：「**Buffer 是 Node 的全局类，表示一块固定长度的原始字节内存，用于处理文件/网络等二进制数据、配合流做分块传输、以及在 utf8/base64/hex 等编码间转换；它绕过字符串的编解码开销，所以处理二进制比字符串快**」。

| 作用 | 说明 | 典型 API |
|---|---|---|
| 处理二进制数据 | 图片、视频、文件读取、协议报文都按字节处理 | `Buffer.alloc(10)` 分配并清零、`Buffer.from('hi')` 从字符串/数组/ArrayBuffer 创建 |
| 与流结合 | `fs.createReadStream` 的 `data` 事件给的就是 chunk（Buffer） | `readStream.on('data', chunk => chunk.length)` |
| 编码转换 | 同一块字节可在多种编码间互转 | `buf.toString('base64')`、`Buffer.from(str, 'hex')` |
| 读写与切片 | 按下标读写、按区间取视图 | `buf.write('Hello')`、`buf.toString('utf8', 0, 5)`、`buf.subarray(0, 5)` |

```javascript
const buf = Buffer.alloc(10);      // 10 字节，已清零
buf.write('Hello');                 // 写入前 5 字节
console.log(buf.toString('utf8', 0, 5));   // Hello
console.log(Buffer.from('Hello, World!').toString('base64')); // SGVsbG8sIFdvcmxkIQ==
```

**增量与坑**：① `Buffer.alloc` 清零、`Buffer.allocUnsafe` **不清零**（更快，但可能读到同进程遗留的旧内存，涉密场景别用，这也是它性能更好的原因——走 8KB 池化预分配）；② `slice`/`subarray` 返回的是**共享同一块内存的视图**，改一个另一个也变，要独立副本用 `Buffer.from(buf)`；③ 单块 Buffer 有长度上限（`buffer.constants.MAX_LENGTH`，64 位系统约 4GB），大文件必须走流；④ 因为它是 `Uint8Array`，可以直接传给 `crypto`、`fs.write`、`zlib`，无需再转。

## 三十九、Node.js 中的 process 对象是什么？它有哪些常用属性？

**回答重点**：`process` 是 Node 的**全局进程对象**（无需 `require`，任何模块直接可用），暴露当前进程的信息与控制能力，是与操作系统交互的入口。必答句：「**process 提供命令行参数 `argv`、环境变量 `env`、工作目录 `cwd`、内存用量 `memoryUsage`、运行时长 `uptime`、退出 `exit`，以及微任务调度 `nextTick` 等能力**」。

| 成员 | 作用 | 关键细节 |
|---|---|---|
| `process.argv` | 命令行参数数组 | `[0]` 是 node 可执行文件路径，`[1]` 是脚本路径，**业务参数从 `[2]` 开始** |
| `process.env` | 环境变量对象 | 读 `NODE_ENV` 等做多环境配置；值都是字符串，改它只影响本进程 |
| `process.exit(code)` | 退出进程 | `0` 成功、非 0 异常；**不等待未完成的异步 I/O**，正常收尾用 `process.exitCode = 1` 让事件循环自然退出 |
| `process.cwd()` | 当前**工作目录** | 不是脚本所在目录；要脚本目录用 `__dirname`（CJS）或 `import.meta.url`（ESM） |
| `process.memoryUsage()` | 内存统计 | `rss` 常驻集、`heapTotal`/`heapUsed` V8 堆、`external` 堆外（含 Buffer） |
| `process.uptime()` | 进程已运行秒数 | 常配合健康检查接口 |
| `process.nextTick(cb)` | 推迟到当前操作后、事件循环下一阶段前执行 | 属**微任务**，优先级高于 `setImmediate` 甚至 `Promise.then`；滥用会**饿死 I/O** |
| `process.platform` / `pid` / `versions` | 平台、进程号、各依赖版本 | 跨平台分支、日志打点、环境诊断 |

```javascript
// script.js 用 node script.js --port 3000 启动
const port = process.argv[2] === '--port' ? Number(process.argv[3]) : 3000;
const isProd = process.env.NODE_ENV === 'production';
process.on('SIGINT', () => { console.log('graceful shutdown'); process.exitCode = 0; });
console.log(process.memoryUsage().heapUsed / 1024 / 1024, 'MB');
```

**增量与坑**：`nextTick` 与 `setImmediate` 的对比是高频追问——同一轮里 `nextTick` 先于 Promise 微任务、Promise 先于 `setImmediate`；用 `process.stdin/stdout/stderr` 可直接读写标准流；`process.on('uncaughtException')` 只能兜底记录日志，捕获后进程状态已不可信，应退出并由进程管理器重启。

## 四十、Node.js 中的 require 和 import 有什么区别？

**回答重点**：`require` 属 **CommonJS**，`import` 属 **ES Module**，差别不只是写法，而是「加载时机 + 依赖能否静态分析」。必答句：「**require 是同步、运行时加载，导出值拷贝，可条件调用、可省略扩展名；import 是静态声明、编译期就确定依赖图，导出是活绑定，支持 tree shaking，但没有 `__dirname`、路径必须写全，且默认严格模式**」。

| 维度 | `require`（CommonJS） | `import`（ES Module） |
|---|---|---|
| 规范 | CommonJS | ES2015 |
| 加载时机 | **同步**、调用时才执行 → 阻塞后续代码 | **静态提升**、编译期解析依赖图，模块先求值再执行本体 |
| 静态分析 / tree shaking | 不支持（可以写在 if 里） | 支持，未用导出可被摇掉 |
| 导出值语义 | **值拷贝**（基本类型是快照，之后源模块再改拿不到） | **活绑定**（源模块变量变了，导入方看到新值） |
| 路径写法 | 可省略 `.js`、可加载目录（找 `index.js`） | 必须写全扩展名或目录 `/index.js`，浏览器端还要带协议 |
| 顶层 `this` | `module.exports` | `undefined` |
| 目录变量 | 有 `__dirname` / `__filename` | 没有，用 `import.meta.url` 换算 |
| 缓存 | `require.cache`，可手动删除热重载 | 每个 URL 只求值一次，无法手动清缓存 |
| 条件加载 | 天然支持 | 只能靠动态 `await import()` |

```javascript
// CommonJS
const fs = require('fs');
fs.readFile('file.txt', 'utf8', (err, data) => { if (err) throw err; console.log(data); });

// ES Module
import fs from 'node:fs/promises';
const data = await fs.readFile('file.txt', 'utf8');
```

**增量与坑**：Node 14+ 原生支持 ESM，但 `.js` 默认仍按 CJS 解析——要启用 ESM 得用 `.mjs` 或在 `package.json` 里写 `"type": "module"`；ESM 里想用 `require` 要 `createRequire(import.meta.url)`；两套混用时 CJS 里 `import` 会被语法报错，而 ESM 里 `require` 拿到的是 CJS 的 `module.exports` 作为 `default`。CJS 还有**循环依赖拿到不完整 exports** 的经典坑（B 引用 A 时 A 尚未执行完）。

> 相关：本文档「三十三」（ES6 新特性总览）、[[工具 08 - Node.js 学习路线]]（模块系统学习路径）

## 四十一、Node.js 中的回调函数是什么？请举例说明？

**回答重点**：回调函数就是**作为参数传给另一个函数、由那个函数在合适时机反过来调用**的函数。Node 的异步 API 一律采用「**错误优先回调**」（error-first / Node-style callback）约定：回调第一个参数是 `err`，第二个才是结果。必答句：「**回调函数是 Node 实现非阻塞 I/O 的基础——把「读完文件后要做什么」封装成函数交给 `fs.readFile`，主线程立刻返回继续跑后面的代码，等 I/O 完成、事件循环轮询到结果时再调用这个函数；回调第一个参数固定是错误对象，这是 Node 的通用约定**」。

| 维度 | 说明 |
|---|---|
| 形态 | 函数当值传递（JS 中函数是一等公民），调用方决定何时执行 |
| 同步 vs 异步 | `Array.prototype.map` 的回调是**同步**的；`fs.readFile`、`setTimeout` 的回调是**异步**的。是否有回调 ≠ 是否异步 |
| 错误优先约定 | `(err, data) => {}`：`err` 为 `null`/`undefined` 表示成功，非空表示失败 |
| 执行上下文 | 回调不在原 `try/catch` 栈里执行，异步阶段抛出的异常捕获不到 |

```javascript
const fs = require('fs');

fs.readFile('example.txt', 'utf8', (err, data) => {
  if (err) {                 // 错误优先：必须处理并提前返回
    console.error('read failed:', err);
    return;                  // 忘了 return 会继续执行后面的逻辑，用 undefined 数据出错
  }
  console.log(data);
});

console.log('主线程继续执行，这行先于文件内容打印');
```

**增量与坑**：① **异步回调里 `throw` 不会被外层 `try/catch` 捕获**——它已经跳出同步栈，会直接冒泡成 `uncaughtException`，所以错误必须走 `err` 参数；② 嵌套三次以上就是**回调地狱**（`fs.readFile` 套 `fs.readFile` 套 `fs.readFile`），横向缩进爆炸且无法用一条 `catch` 兜住全部错误；③ **Zalgo 陷阱**：同一个函数有时同步、有时异步地回调（比如缓存命中就同步返回），会让调用方顺序不可预期——要保证「永远异步」，用 `process.nextTick(cb)` 或 `queueMicrotask(cb)` 包一层；④ 改造路径有三条——`util.promisify(fn)` 一行 Promise 化、手写 `new Promise((resolve, reject) => ...)`、或直接用 `fs.promises` / `node:fs/promises` 的原生 Promise 版本。异步编排的演进见本文档「四十二」。

> 相关：本文档「四十二」（回调、Promise、async/await 的取舍）、[[工具 08 - Node.js 学习路线]]（异步编程学习路径）

## 四十二、Node.js 中的回调、Promise 和 async/await 有什么区别？

**回答重点**：三者是同一件事（处理异步）的三代写法，区别集中在**嵌套形态、错误处理、流程控制能力**上，不是互斥技术——async/await 就是 Promise 的语法糖，Promise 内部依然由回调驱动。必答句：「**回调是最原始的方式，靠嵌套串联、错误靠第一个参数手工传递，多层嵌套形成回调地狱；Promise 用 then 链式调用把嵌套拍平成队列，状态一旦落定不可变，错误统一由 catch 捕获；async/await 是 Promise 的语法糖，用同步写法表达异步，错误可直接 try/catch，但多个 await 默认串行，要并发得配 Promise.all**」。

| 维度 | 回调 | Promise | async/await |
|---|---|---|---|
| 本质 | 函数当参数，完成时被调用 | 表示未来结果的**状态容器**（pending/fulfilled/rejected） | Promise 的**语法糖**（`async` 函数必返回 Promise） |
| 串联形态 | 层层嵌套（金字塔） | `then` 链式，横向排列 | 顺序书写，和同步代码同形 |
| 错误处理 | 每个回调手工判 `err` 并 `return` | 一个 `.catch()` 兜住整条链 | `try/catch` 包住 `await` |
| 流程控制 | 只能靠手工计数/嵌套 | 可组合（`all`/`race`/`allSettled`/`any`） | 同左，且有 `if`/`for`/`while` 等同步控制流 |
| 可读性 | 差（嵌套深） | 中（链长时仍难读） | 好 |
| 调试栈 | 断点跳跃、栈信息断裂 | 比回调好 | 最接近同步，栈清晰 |

```javascript
// 回调：三层嵌套
readFile('a.txt', (err, a) => {
  if (err) return done(err);
  readFile('b.txt', (err, b) => {
    if (err) return done(err);
    readFile('c.txt', (err, c) => err ? done(err) : done(null, [a, b, c]));
  });
});

// Promise：链式拍平，一个 catch 收口
readFile('a.txt')
  .then(a => readFile('b.txt').then(b => [a, b]))
  .then(([a, b]) => readFile('c.txt').then(c => [a, b, c]))
  .catch(done);

// async/await：同步写法；注意顺序 await 是串行
async function readAll() {
  try {
    const a = await readFile('a.txt');       // 等完才发下一个请求
    const b = await readFile('b.txt');
    const c = await readFile('c.txt');
    return [a, b, c];
  } catch (err) { throw err; }
}

// 三个文件互不依赖 → 并发，耗时从 sum 变 max
const [a, b, c] = await Promise.all(['a.txt', 'b.txt', 'c.txt'].map(readFile));
```

**增量与坑**：① **Promise 状态单向不可逆**——已 fulfilled 后再 `reject` 或再 `resolve` 都被忽略，构造函数里抛错等于 `reject`；② `then` 里**忘记 `return`**（尤其返回内层 Promise 时）会让链断掉、下游拿到 `undefined`，这是 `then` 链最常见的 bug；③ `async` 函数内部**未 `await` 的 rejection 不会被本地 `try/catch` 捕获**，而是变成 `unhandledRejection`（Node 15+ 默认直接让进程崩溃），兜底要 `process.on('unhandledRejection')`；④ **`await` 在 `forEach` 里无效**——`forEach` 不理会回调返回的 Promise，要串行用 `for...of`，要并发用 `Promise.all(arr.map(...))`；⑤ `await` 不是让出线程，只是让出当前函数的执行权，CPU 密集任务照样阻塞事件循环，需要 `worker_threads`；⑥ 回调风格的库可用 `util.promisify` 一行适配，反向（Promise → 回调）几乎不需要。

## 四十三、Node.js 中的定时器函数 setImmediate() 和 setTimeout() 有什么区别？

**回答重点**：两者都调度异步回调，但落在**事件循环的不同阶段**：`setTimeout(fn, ms)` 进 **timers 阶段**（等够时间后执行），`setImmediate(fn)` 进 **check 阶段**（当前轮 poll 一结束就执行）。必答句：「**setImmediate 是「本轮 I/O 轮询结束后立刻执行」，setTimeout 是「至少等 N 毫秒后的 timers 阶段执行」；在 I/O 回调内部调用时 setImmediate 一定先于 setTimeout(fn, 0)，但在主模块顶层调用时两者顺序不确定，取决于进程启动耗时是否已超过 1ms**」。

事件循环一轮的六个阶段（简化）：`timers`（到期的 setTimeout/setInterval）→ `pending callbacks` → `idle/prepare` → `poll`（等 I/O，大部分时间停在这里）→ `check`（setImmediate）→ `close callbacks`。每个阶段结束后清空**微任务队列**（`process.nextTick` 优先于 Promise 微任务），然后进入下一阶段。

| 维度 | `setImmediate(fn)` | `setTimeout(fn, 0)` |
|---|---|---|
| 所属阶段 | `check` 阶段 | `timers` 阶段 |
| 触发时机 | 当前轮 poll 结束后立即 | 至少 `ms` 毫秒后的下一个 timers 阶段（`0` 被钳到 **1ms**） |
| I/O 回调内相对顺序 | **先执行** | 后执行 |
| 主模块顶层相对顺序 | **不确定**（进入事件循环耗时是否 ≥1ms 决定） | 不确定 |
| 语义定位 | 「让出当前栈，本轮末尾就跑」 | 「延迟一段时间再跑」 |
| 取消方式 | `clearImmediate(id)` | `clearTimeout(id)` |

```javascript
const fs = require('fs');

fs.readFile(__filename, () => {          // 处在 poll 阶段的 I/O 回调里
  setImmediate(() => console.log('immediate'));   // 下一站是 check → 先打印
  setTimeout(() => console.log('timeout'), 0);    // 要等下一轮 timers → 后打印
});

// 顶层直接写，两者顺序不保证：
// setImmediate(() => console.log('A'));
// setTimeout(() => console.log('B'), 0);
```

**增量与坑**：① `setImmediate` 的名字有误导性——它不是「立刻」执行，而是「本轮迭代的 check 阶段」；真正的「立刻插队」是 `process.nextTick` / `queueMicrotask`；② `setTimeout(fn, 0)` **不是 0 毫秒**，Node 与浏览器都会钳到最小 1ms，所以「用 `setTimeout(fn, 0)` 拆长任务」在高频循环里会明显变慢，拆任务更该用 `setImmediate`；③ **`setInterval` 会漂移且不防重入**——回调执行时间超过间隔时任务会堆积（或按实现被跳过），需要严格周期就用「`setTimeout` 递归 + 记录上次执行时刻」；④ 定时器句柄是事件循环的引用，**未 `clearTimeout` 的定时器会让进程无法自然退出**（服务里常见内存泄漏），可用 `timer.unref()` 摘掉引用；⑤ 微任务永远先于两类定时器——`nextTick` > Promise 微任务 > `setImmediate` > `setTimeout(fn, 0)` 是同一轮内的稳定优先序（`nextTick` 的细节见本文档「三十九」）。

## 四十四、Node.js 中，同步和异步代码有什么区别？

**回答重点**：区别只有一个——**当前操作会不会占住执行线程**。同步代码（`fs.readFileSync`、`crypto.pbkdf2Sync`）在执行期间**阻塞后续所有代码**，调用栈不返回，谁也别想跑；异步代码（`fs.readFile`、`setTimeout`、`fetch`）把任务交给 libuv，主线程立刻继续往下走，结果通过回调 / Promise / `async/await` 回来。必答句：「**同步代码按书写顺序串行执行、遇到 I/O 就阻塞线程；异步代码发起操作后立即返回，靠事件循环在结果就绪时调度回调，因此 Node 单线程也能扛大量并发 I/O**」。

| 维度 | 同步代码 | 异步代码 |
|---|---|---|
| 执行顺序 | 严格按书写顺序，一步等一步 | 发起后立即返回，完成顺序不保证 |
| 阻塞行为 | **阻塞事件循环**，期间所有请求排队 | 不阻塞，主线程继续处理其他任务 |
| 错误处理 | 直接 `throw` / `try...catch` 捕获 | 回调走 `err` 参数、Promise 走 `.catch`、async 走 `try/catch`（外层 `try` 捕不到回调里的 `throw`） |
| 典型 API | `readFileSync`、`execSync`、大循环计算 | `readFile`、`setTimeout`、`http.request`、`fs.promises` |
| 适用场景 | 启动时读配置、脚本、构建工具 | 请求处理、数据库 / 网络 / 磁盘 I/O |

```javascript
const fs = require('fs');

// 同步：读完才往下走，期间整个进程被卡住
const data = fs.readFileSync('file.txt', 'utf8');
console.log(data, 'done');

// 异步：先打印 done，文件内容稍后由事件循环回调送回
fs.readFile('file.txt', 'utf8', (err, data) => {
  if (err) throw err;   // 这里抛错不会被外层 try/catch 接住
  console.log(data);
});
console.log('done');
```

**增量与坑**：① Node 的「单线程」只指 **JS 执行线程**，磁盘 / DNS / `crypto` 等由 **libuv 线程池**（默认 4 个线程）代劳，所以异步不等于多线程写业务代码；② 异步只解决 **I/O 等待**，CPU 密集计算（大 JSON 解析、图片处理、死循环）写成同步照样卡死事件循环——要么拆成分片 `setImmediate`，要么扔进 `worker_threads`；③ `await` 只是写法上的同步，**`await` 期间事件循环照常跑其他任务**，但当前 `async` 函数会被挂起，多个 `await` 默认串行、要并发得配 `Promise.all`（见本文档「四十二」）；④ 不要依赖异步回调的**完成顺序**——同一批 `fs.readFile` 谁先回来取决于磁盘和线程池，需要顺序就用 `for...of + await` 或串行 reduce。

> 相关：本文档「四十一」（错误优先回调）、「四十二」（回调 / Promise / async-await 演进）、「四十三」（事件循环阶段与定时器）、[[工具 08 - Node.js 学习路线]]

## 四十五、Node.js 的 process.nextTick() 有什么作用？

**回答重点**：`process.nextTick(cb, ...args)` 把回调插到**当前操作执行完之后、事件循环进入下一阶段之前**的 nextTick 队列里，并**先把整个队列清空**才继续。它不属于事件循环的六个阶段，而是每个阶段切换、每次 C++/JS 边界返回时都会检查的「插队队列」。必答句：「**nextTick 是在当前同步栈清空后、事件循环继续之前立即执行的微任务，优先级高于 Promise.then 和 setImmediate；它只推迟、不让出事件循环，递归调用会饿死 I/O**」。

```javascript
process.nextTick((a, b) => console.log(a, b), 'arg1', 'arg2');  // 支持透传参数
process.nextTick(() => {
  console.log('nextTick 1');
  process.nextTick(() => console.log('nextTick 2'));  // 仍在同一轮清空，'nextTick 2' 先于下面那行
});
Promise.resolve().then(() => console.log('promise'));
// 输出：nextTick 1 → nextTick 2 → promise
```

**增量与坑**（`process` 对象本身见本文档「三十九」，与 `setImmediate` 的阶段差异见「四十三」）：① **饿死 I/O 的根因是「清空式执行」**——清空 nextTick 队列时新塞进去的 nextTick 会继续在本轮执行，递归 `nextTick` 会让事件循环永远进不到 poll 阶段，网络请求全部超时；需要「让出」就用 `setImmediate`（下一轮 check 阶段）而不是 nextTick；② **优先序**：`nextTick` 队列 > Promise 微任务 > `setImmediate` > `setTimeout(fn, 0)`，Node 11 之后每轮先清 nextTick 再清 Promise；③ 典型正当用途：**让 API 永远异步**（缓存命中时也 `nextTick(cb)` 回调，避免 Zalgo 同步/异步混用）、构造函数里先注册监听再 `nextTick` 触发事件、把错误异步抛给调用方以统一成 `uncaughtException` 路径；④ 浏览器没有 `process.nextTick`，跨端代码用 `queueMicrotask`（语义等价于 Promise 微任务，且没有 nextTick 的饿死极端情况）。

## 四十六、Pinia 与 Vuex 状态管理有什么区别？

**回答重点**：两者都是 Vue 的官方状态管理方案，**Pinia 是 Vue 3 时代官方推荐的替代品**（Vuex 5 的构想最终以 Pinia 落地）。核心差别是 API 哲学：Vuex 基于 **Flux**，强制「`commit` mutation 同步改状态、`dispatch` action 处理异步」的单向数据流；Pinia 去掉 mutations，只留 `state` / `getters` / `actions`，**直接改 state**，actions 天然可同步可异步。必答句：「**Pinia 用 state/getters/actions 三件套直接改状态、每个 store 独立成模块、TypeScript 推导开箱即用；Vuex 需要 state/mutations/actions/getters 四件套加 commit/dispatch 两层调用、模块要 namespaced 手动拼接路径，TS 支持还得额外配置**」。

| 维度 | Vuex | Pinia |
|---|---|---|
| 设计模式 | Flux（单向数据流，mutation 是唯一改状态入口） | 组合式 API 风格（store 就是一个 `reactive` 对象） |
| 核心概念 | `state` / `mutations` / `actions` / `getters` / `modules` | `state` / `getters` / `actions`（**无 mutations**） |
| 修改状态 | 必须 `store.commit('SET_X', v)`，**同步** | `store.x = v` 直接赋值，或 `store.$patch({...})` 批量 |
| 异步 | 放 `actions` 里 `dispatch` | 直接在 `actions` 里写 `async` |
| 模块化 | `modules` + `namespaced: true`，调用要拼 `模块名/方法` | 每个 `defineStore` 就是一个模块，`useXStore()` 直接引入，无命名空间嵌套 |
| TypeScript | 需额外类型声明，`commit` 字符串无类型校验 | 类型推导原生，getters/actions 自动推断 |
| 体积 / 依赖 | 较大，依赖 Vue 2 的响应式 | 约 1KB 级，独立包，支持 Vue 2.7+ / Vue 3 |
| DevTools / SSR | 支持 | 支持，且有更好的时间旅行与 SSR 友好性 |
| 生态 | 历史长、插件多（持久化、同步等） | 生态在追赶，但已是官方默认（脚手架默认选项） |

```javascript
// Vuex：四件套 + commit/dispatch 两层调用
const store = createStore({
  state: { count: 0 },
  mutations: { SET_COUNT(state, v) { state.count = v; } },      // 同步唯一入口
  actions: { async load({ commit }) { commit('SET_COUNT', await api.getCount()); } },
});
store.commit('SET_COUNT', 1);
await store.dispatch('load');

// Pinia：三件套，直接改，actions 可 async
export const useCounterStore = defineStore('counter', {
  state: () => ({ count: 0 }),
  getters: { double: (s) => s.count * 2 },
  actions: { async load() { this.count = await api.getCount(); } },  // async 直接写
});
const store = useCounterStore();
store.count = 1;            // 直接赋值
store.$patch({ count: 2 }); // 批量修改只触发一次更新
```

**增量与坑**：① `storeToRefs(store)` 解构 `state` / `getters` 才保持响应性，直接 `const { count } = store` 会**丢失响应**（actions 可以随便解构）；② 批量改多个字段用 `$patch`，否则逐个赋值会触发多次渲染；`$patch` 也接受函数形式处理数组 push 等操作；③ Pinia 支持 **Vue 2.7+**（2.6 需装 `@vue/composition-api`），老项目 Vue 2.6 及以下只能留 Vuex 3；④ 两者都**不做持久化**，刷新即丢，需要 `pinia-plugin-persistedstate` 或 `vuex-persistedstate`；⑤ 别把组件内部临时状态（弹窗开关、表单草稿）塞进 store——store 只放**跨组件共享 + 需要跨路由存活**的状态，否则全局状态会迅速腐化。

> 相关：[[工具 11 - Vue.js 学习路线]]（组合式 API 与状态管理学习路径）、[[工具 12 - 前端学习路线]]

## 四十七、React Router 中的 Router 组件有几种类型？

**回答重点**：要分两层看。**底层只有一个 `Router`**——它接收一个 `history` 实例（`createBrowserHistory` / `createHashHistory` / `createMemoryHistory` 的产物）并向下提供路由 context，自己不关心 URL 长什么样；日常用的是它的三个开箱包装：**`BrowserRouter`（HTML5 history API）、`HashRouter`（URL 的 `#` 部分）、`MemoryRouter`（历史存在内存里）**，SSR 再补一个 `StaticRouter`（v6 在 `react-router-dom/server`）。必答句：「**BrowserRouter 用 history.pushState 换干净 URL、需要服务端 fallback；HashRouter 用 hashchange、# 之后不发往服务端所以零配置可部署但 SEO 差；MemoryRouter 把历史放内存、主要用于测试和 React Native；三者共用同一套 Routes/Route/Outlet，只是 history 实现不同**」。

| 类型 | 底层 history | URL 形态 | 服务端要求 | 典型场景 |
|---|---|---|---|---|
| `BrowserRouter` | `history.pushState` / `popstate` | `/user/1`，干净无 `#` | **需要**所有路径回退到 `index.html`（nginx `try_files`、Vercel rewrites） | 常规 Web 应用、需要 SEO 与分享链接 |
| `HashRouter` | `location.hash` + `hashchange` | `/#/user/1` | 不需要，`#` 之后的内容浏览器不会发给服务端 | GitHub Pages / OSS 静态托管、Electron `file://`、被嵌在第三方页面或后台 iframe 里的子应用 |
| `MemoryRouter` | `createMemoryHistory`，纯内存数组 | 地址栏不变 | 无关 | 单元测试（`initialEntries` 指定起点）、React Native、非浏览器宿主 |
| `StaticRouter` | 无（每次渲染传入 `location`） | 由请求 URL 决定 | 由 Node 服务端接管 | SSR 首屏渲染 |

```jsx
// 嵌套路由：三种 Router 都支持，子路由用 <Outlet /> 占位
<BrowserRouter>
  <Routes>
    <Route path="/" element={<Layout />}>
      <Route index element={<Home />} />
      <Route path="about" element={<About />} />
      <Route path="*" element={<NotFound />} />
    </Route>
  </Routes>
</BrowserRouter>

// 测试里用 MemoryRouter 完全掌控历史，无需真实地址栏
render(
  <MemoryRouter initialEntries={['/about']}>
    <App />
  </MemoryRouter>
);
```

**增量与坑**：① v6 起 **`Router` 组件 = history 的注入器**，切换 Router 类型只换这一层，`Routes` / `useNavigate` / `useParams` 全部不用改，这是面试里最能体现「懂抽象」的一句；② `BrowserRouter` 上线最常见的 404 不是路由写错，而是**刷新深层路径时服务器找不到物理文件**——必须配 fallback；`HashRouter` 之所以「部署即用」正是因为 `#` 后的部分不参与请求；③ 一个应用**只包一个 Router**，嵌套两个会导致 `useNavigate` / `useLocation` 拿到最近的那个实例，出现「跳转了但页面不变」；反过来，在 Router 外面调用任何路由 hook 会直接抛错，所以测试、Storybook 必须手动包一层；④ `MemoryRouter` 的 `initialEntries` / `initialIndex` 是测试多级返回（`navigate(-1)`）的关键，别只用默认 `/`；⑤ HashRouter 的 `#` 与页面内锚点、`scrollIntoView` 的 `#id` 会互相打架，且 `#` 后内容不参与 SEO 与服务端日志统计；⑥ v5 的 `Switch` / `component` / `render` props 在 v6 已移除，回答时别混版本。

> 延伸阅读：<https://reactrouter.com/en/main/router-components/browser-router>

## 四十八、React 中除了在构造函数中绑定 this，还有哪些绑定 this 的方式？

**回答重点**：类组件里 `this` 丢失的根因是 **JSX 的 `onClick={this.handleClick}` 传的是函数引用，React 事件系统调用它时等同于普通函数调用**，`this` 为 `undefined`（class 内部是严格模式）。除构造函数里 `this.handleClick = this.handleClick.bind(this)` 外，还有三种主流写法：**类字段箭头函数（`handleClick = () => {}`）、在 render 里写内联箭头函数（`onClick={() => this.handleClick(id)}`）、在 render 里 `bind`（`onClick={this.handleClick.bind(this)}`）**。必答句：「**三种替代方案本质都是把 this 在『定义时』或『调用时』固定住：类字段箭头函数靠词法作用域在实例上生成一次、引用稳定；render 内联箭头函数与 render 内 bind 都是每次渲染新建一个函数，区别只在能否顺手传参；现代 React 用函数组件 + Hooks，根本没有 this 问题**」。

| 方式 | 写法 | 函数创建时机 | 传参 | 评价 |
|---|---|---|---|---|
| 构造函数 bind | `this.h = this.h.bind(this)` | 每实例一次 | 需 `bind(this, id)` 或外包一层 | 引用稳定、可 `removeEventListener`；样板代码多，漏写就是运行时 `undefined` |
| 类字段箭头函数 | `h = () => {}` | 每实例一次（实例属性） | 需外包一层箭头函数 | **官方推荐的老写法**，最简洁；不在原型上，继承/单测 spy 略麻烦 |
| render 内联箭头函数 | `onClick={() => this.h(id)}` | **每次渲染都新建** | 天然支持 | 灵活；引用每次都变，坑在 `memo` / `PureComponent` 子组件 |
| render 内 bind | `onClick={this.h.bind(this)}` | **每次渲染都新建** | `bind(this, id)` | 能提前绑定，但同样每次新建，可读性最差 |

```jsx
class Button extends React.Component {
  // ① 类字段箭头函数：this 在定义时就锁死为实例，只创建一次
  handleClick = (id) => console.log('id:', id, this);

  // ② 普通方法：this 取决于调用方式，必须靠 bind 或外层箭头函数兜住
  handleReset() { this.setState({ n: 0 }); }

  render() {
    return (
      <>
        <button onClick={this.handleClick}>无参直接用</button>
        {/* 需要传参时外包一层箭头函数，不要写成 onClick={this.handleClick(1)}（会立即执行） */}
        <button onClick={() => this.handleClick(1)}>传参</button>
        {/* 引用稳定的场景：提前 bind 一次存起来，卸载时才能 removeEventListener */}
        <button onClick={this.handleReset.bind(this)}>reset</button>
      </>
    );
  }
}
```

**增量与坑**（`this`、`arguments`、`prototype` 层面的差异见本文档「五、ES6 箭头函数和普通函数有什么区别？」）：① 「render 里写箭头函数会拖慢性能」要说得准确——**函数本身的创建开销可以忽略**，真正的代价是**引用每次渲染都变**，导致 `React.memo` / `PureComponent` 的浅比较永远不相等、子组件白渲染，长列表里才需要 `useCallback` 或提到实例上；② 类字段箭头函数是**实例属性不是原型方法**，子类无法通过 `super` 覆盖、`jest.spyOn(Button.prototype, 'h')` 也打不上桩，需要测试注入时改回构造函数 bind；③ `onClick={this.handleClick()}` 是最经典的错——**多了一对括号就在渲染期立即执行**，返回 `undefined` 给事件系统；④ 需要「传参又要引用稳定」时用 `data-*` + 从 `e.currentTarget.dataset` 取值，或在构造函数里 `bind(this, id)` 生成一组预绑定函数；⑤ **函数组件没有 this**，Hooks 里不存在绑定问题，真正的等价坑是闭包捕获了旧 state（用 `useRef` 或函数式 `setState` 解决），所以现代项目这道题更多是「读懂老代码」的能力。

> 延伸阅读：<https://zh-hans.react.dev/learn/responding-to-events>

## 四十九、Redux 如何实现多个组件之间的通信？多个组件使用相同状态时如何管理？

**回答重点**：Redux 把「共享状态」从组件树里抽出来放进**唯一 store**，通信链路是单向的：`dispatch(action)` → **reducer（纯函数）算出新 state** → store 通知所有订阅者 → `react-redux` 的 `Provider` 通过 context 把 store 传下去，组件用 `useSelector` 订阅自己关心的**切片**、用 `useDispatch` 派发。于是两个没有父子关系的组件不需要 props 层层传递，**只要读同一份 state、派发同一个 action 就等于在通信**。必答句：「**单一 store 是唯一数据源，action 是唯一修改入口，reducer 是纯函数；组件之间不直接说话，都通过 store 中转——A 组件 dispatch，B 组件 useSelector 订阅到变化自动重渲染**」。

| 环节 | API | 职责 |
|---|---|---|
| 创建 | `createStore`（旧）/ `configureStore`（RTK） | 组装 rootReducer、挂中间件 |
| 读 | `store.getState()` / `useSelector(fn)` | 取切片；`useSelector` 内部 `subscribe` + 值变化才触发重渲染 |
| 写 | `dispatch(action)` | 唯一入口，`type` 必填，数据放 `payload` |
| 通知 | `store.subscribe(listener)` | 底层订阅，react-redux 已封装，业务代码基本不用手写 |
| 注入 | `<Provider store={store}>` | 让整棵树通过 context 拿到 store |
| 老写法 | `connect(mapState, mapDispatch)(Comp)` | HOC，注入 props，自带浅比较 |

```javascript
// store：多个 reducer 用 combineReducers 合成一棵树，cart 与 user 各自独立
const rootReducer = combineReducers({ cart: cartReducer, user: userReducer });

// 两个互不相邻的组件读同一份 cart，天然同步
const CartBadge = () => {
  const count = useSelector((s) => s.cart.items.length);   // 只订阅数量，粒度越细越好
  return <span>{count}</span>;
};

const AddButton = ({ id }) => {
  const dispatch = useDispatch();
  return <button onClick={() => dispatch({ type: 'cart/add', payload: id })}>加入</button>;
};

// 异步：action creator 返回函数，由 redux-thunk 注入 dispatch/getState
const fetchCart = () => async (dispatch, getState) => {
  dispatch({ type: 'cart/loading' });
  try {
    const data = await api.getCart(getState().user.id);
    dispatch({ type: 'cart/loaded', payload: data });
  } catch (e) {
    dispatch({ type: 'cart/error', payload: e.message });
  }
};
```

**增量与坑**：① 多个组件用同一状态时的正确做法是**都 `useSelector` 同一节点、都 `dispatch` 同一 action**，绝不要在某个组件里 `useState` 复制一份——一旦出现「两份真源」，同步逻辑就会失控；② `useSelector` 默认用 `===` 比较返回值，**返回新对象/新数组（`s => ({ a: s.a, b: s.b })`、`s => s.list.filter(...)`）会让每次 dispatch 都判定为变化**，引发多余甚至无限重渲染——用 `shallowEqual`、拆成多个 `useSelector`，或在 `createSelector`（reselect）里做记忆化；③ `connect` 的 `mapStateToProps` 自带浅比较，这也是老项目「看起来没问题」的原因，迁移到 hooks 时容易踩 ②；④ 异步**不能写在 reducer 里**（reducer 必须纯、不能有副作用），统一交给 `redux-thunk`（简单、返回函数）或 `redux-saga`（复杂流程、可取消），组件只负责 dispatch 一个「意图」；⑤ reducer 里直接 `state.list.push(x)` 不会触发更新，必须返回新对象（RTK 用 Immer 允许「看起来在改」，但依赖它就别再手动 mutate 返回）；⑥ 列表数据做**规范化**（`byId` + `ids`）而不是嵌套大对象，否则任何一处更新都要重建整棵树；⑦ 别把所有状态都塞进 store：弹窗开关、输入框草稿这类**只属于一个组件**的状态留在 `useState`，判断标准是「是否需要跨组件/跨路由共享、是否需要时间旅行调试」——这一点和本文档「四十六、Pinia 与 Vuex 状态管理有什么区别？」里对全局状态边界的判断完全一致，只是 Vue 侧少了 action/mutation 两层。

> 延伸阅读：<https://cn.redux.js.org/>

## 五十、Vue 2 和 Vue 3 有哪些区别？Vue 3 有哪些更新？

**回答重点**：Vue 3 是**重写**而非打补丁，差异可归为六条主线：**① 响应式从 `Object.defineProperty` 换成 `Proxy`；② 新增 Composition API（Options API 仍然可用）；③ 模块化 ESM + 更好的 tree-shaking；④ 支持 Fragments（多根节点）；⑤ 新增 Teleport / Suspense 等内置能力；⑥ 编译器与 Virtual DOM 全量重写**。必答句：「**对外 API 大体兼容、对内几乎全部重写：Proxy 解决「新增/删除属性、数组下标赋值不触发更新」的老坑，Composition API 解决「逻辑按 option 切开、复用只能靠 mixin」的老坑，tree-shaking 让没用到的 API 不进包**」。

| 维度 | Vue 2 | Vue 3 | 影响 |
|---|---|---|---|
| 响应式 | `Object.defineProperty` 递归遍历 + getter/setter | `Proxy` 代理整个对象、惰性递归 | 初始化更快；新增/删除属性、数组下标赋值天然可追踪，不再需要 `Vue.set` / `Vue.delete` |
| 逻辑复用 | Options API + `mixin` | Options API + **Composition API**（`setup`、`<script setup>`） | 同一功能的 data/computed/watch 聚在一处；复用不再靠 mixin 的隐式合并 |
| 打包体积 | 整包引入，未用 API 也进包 | 模块化 ESM，支持 tree-shaking | 只 import 用到的 API，基线体积更小 |
| 根节点 | 模板必须单一根元素 | Fragments，可返回多个根节点 | 少一层无意义的包裹 `div` |
| DOM 位置 | 只能渲染在挂载点内部 | `Teleport` 渲染到任意容器（如 `body`） | 弹窗/通知不受父级 `overflow`、`z-index`、`transform` 影响 |
| 编译与 diff | 全量 diff | 静态提升 + `patchFlag` + Block Tree + 事件缓存 | 跳过静态子树，只比动态部分 |
| 语言 | 源码 JS，可选 class 写法 | 源码 TypeScript 重写 | 类型推导与 IDE 补全更好 |
| 全局 API | `new Vue()` + `Vue.use` | `createApp()` + `app.use`，全局 API 挂 app 实例 | 多实例/微前端不共享全局配置，SSR 无跨请求污染 |
| 平台 | 浏览器（+ Weex） | `runtime-core` + 自定义渲染器 `createRenderer` | 同一套响应式/组件模型可渲染到小程序、Canvas、WebGL、原生 |

### 1、响应式：为什么必须换 Proxy

```js
// Vue 2：初始化时递归遍历 data，逐个属性装 getter/setter
function defineReactive(obj, key, val) {
  Object.defineProperty(obj, key, {
    get() { /* 收集依赖 */ return val; },
    set(next) { val = next; /* 通知 watcher */ },
  });
}
// 于是有三个经典失效场景，Vue 2 里要靠 Vue.set / Vue.delete / splice 补救
vm.form.newField = 'x';   // 新增属性：没装过 getter，不是响应式
vm.list[1] = 'new';       // 数组下标赋值：defineProperty 拦不到下标
delete vm.form.oldField;  // 删除属性：拦不到 delete
```

```js
// Vue 3：Proxy 代理整个对象，get / set / deleteProperty / has / ownKeys 全可拦
const state = reactive({ form: {}, list: ['a', 'b'] });
state.form.newField = 'x';   // 走 set trap，自动触发更新
state.list[1] = 'new';       // 数组下标赋值同样被拦截
delete state.form.newField;  // 走 deleteProperty trap
```

三条补充：① Proxy 是**惰性递归**——只有访问到 `state.form` 时才为它建子代理，大对象初始化成本从「全量属性」降到「实际访问」；② Proxy 代理不了**原始值**，所以 `ref(0)` 用 `{ value: 0 }` 包装，模板里自动解包、JS 里必须写 `.value`，这是 Composition API 最常见的「漏写 .value」坑；③ Proxy 无法完整 polyfill，这是 Vue 3 放弃 IE11 的直接原因。

### 2、Composition API 解决的是「组织」，不是「性能」

| 对比点 | Options API | Composition API |
|---|---|---|
| 代码组织 | 按 `data`/`computed`/`methods`/`watch` 分块，一个功能的代码散在四五处 | 按**功能**聚合成一个 composable（`useCart()`） |
| 逻辑复用 | `mixin`：属性来源隐式、命名冲突静默覆盖 | 显式返回值 + 解构重命名，来源清清楚楚 |
| 类型推导 | `this` 上动态挂载，TS 要靠 `defineComponent` 辅助 | 普通变量，TS 原生推导 |
| 适用规模 | 小中型组件直观 | 复杂组件、跨项目复用友好 |

`<script setup>` 是语法糖：编译后顶层绑定直接暴露给模板，比 `setup()` 返回对象少一层闭包与代理开销。

### 3、Fragments / Teleport / Suspense：三个模板能力增量

- **Fragments**：组件可返回多个根节点，省掉无意义包裹层；代价是**多根组件无法自动继承 attrs**，需显式 `inheritAttrs: false` + `v-bind="$attrs"` 指定落点。
- **Teleport**：`<Teleport to="body">` 把子树渲染到别处，Vue 2 时代要靠 `portal-vue` 插件。
- **Suspense**：为 `<script setup>` 顶层 `await` 与异步组件提供统一 loading 兜底（目前仍是实验性）。

### 4、破坏性变更（面试最常追问这块）

- `new Vue()` → `createApp()`；`Vue.prototype.$x` → `app.config.globalProperties.$x`。
- **移除 `$on`/`$off`/`$once`**：全局 EventBus 方案作废，改用 `mitt` 或状态库。
- 移除 `filters`（用 computed 或方法）、`$children`（用 `ref` 拿子组件）、`.native` 修饰符（声明 `emits` 后 `@click` 直接落在根元素）。
- **`v-if` 与 `v-for` 同节点时优先级反转**：Vue 2 先 `v-for` 后 `v-if`，Vue 3 先 `v-if`（此时拿不到循环变量），官方建议永远不要写在同一元素上。
- 生命周期改名：`beforeDestroy` → `beforeUnmount`、`destroyed` → `unmounted`。
- 渐进迁移靠 `@vue/compat` 兼容构建（对废弃 API 打运行时警告）+ 官方迁移指南逐项替换。

**增量与坑**：① 「Vue 3 更快」要说得具体——收益来自**编译器跳过静态内容**与**Proxy 惰性递归**，不是「换代就快两倍」，业务体感取决于静态内容占比；② Proxy 让新增属性可响应，但**整体替换 reactive 变量会丢响应性**（`state = reactive({})` 重新赋值后模板仍持旧代理），正确做法是 `Object.assign(state, next)` 或改用 `ref`；③ `reactive` 解构会丢响应性（`const { count } = state`），要 `toRefs`；④ `ref` 在模板与 `reactive` 对象里自动解包，**在数组/Map 里不会**，`.value` 极易漏写；⑤ Teleport 的目标容器必须在挂载时已存在（`to="#modal"` 节点还没渲染 → 运行时报错）；⑥ 多根组件 + 自动 attrs 继承冲突是升级后样式错乱的最常见来源。

> 延伸阅读：<https://v3-migration.vuejs.org/>、<https://cn.vuejs.org/guide/introduction.html>

## 五十一、Vue 3 性能提升主要体现在哪些方面？

**回答重点**：提升分**初始化 / 更新 / 体积**三条线，落到五个抓手：**① 响应式换 Proxy（惰性递归、免遍历）② tree-shaking + 模块化（体积）③ 编译器优化（静态提升、`patchFlag`、Block Tree、事件缓存）④ Virtual DOM 重写（`shapeFlag` 位运算、最长递增子序列求最小移动）⑤ 完全模块化按需引入**。必答句：「**Vue 3 的提升一半在运行时——Proxy 惰性递归 + 新 diff 算法，一半在编译时——静态节点提升到 render 之外、动态节点打上 `patchFlag` 收进扁平 block 数组，diff 时直接跳过静态部分，再叠加 ESM tree-shaking 砍体积**」。

| 维度 | Vue 2 的瓶颈 | Vue 3 的做法 | 收益 |
|---|---|---|---|
| 初始化 | `defineProperty` 要递归遍历所有属性装 getter | Proxy 惰性代理，访问到才建子代理 | 大对象初始化从「全量」降为「按需」 |
| 更新 | 全量 vnode 树逐层 diff | Block Tree + `patchFlag`，只比动态节点 | 静态占比高的模板收益最大 |
| 编译 | 模板 → 通用 render，静态节点每次重建 | `hoistStatic` 提升常量、`cacheHandler` 缓存事件、`v-once` | 减少对象创建与 GC |
| diff | 双端对比，移动按索引顺序 | `shapeFlag` 位运算判类型 + LIS 求最小移动集 | 列表更新少做 DOM 操作 |
| 体积 | 整包 = 全量 API | ESM + tree-shaking，用不到的不进包 | 只 import 部分 API 时基线更小 |
| 扩展 | 插件改原型链 | 组合式函数按需组合 | 未被调用的 composable 可被摇掉 |

### 1、编译产物长什么样（最能体现「编译时优化」）

模板：

```html
<div>
  <p class="static">hi</p>
  <p>{{ msg }}</p>
</div>
```

Vue 3 编译后（简化）：

```js
const _hoisted_1 = { class: "static" };   // 静态 props 被提升到 render 之外，只创建一次
export function render(_ctx) {
  return (_openBlock(), _createElementBlock("div", null, [
    _createElementVNode("p", _hoisted_1, "hi"),                                // 无 patchFlag → diff 直接跳过
    _createElementVNode("p", null, _toDisplayString(_ctx.msg), 1 /* TEXT */),  // 只比文本
  ]));
}
```

三件关键机制：**静态提升（`hoistStatic`）**把不变节点/属性提到 render 外复用；**`patchFlag`** 用位标记声明「这个节点只有文本/只有 class/只有 props 会变」（1=TEXT、2=CLASS、8=PROPS、16=NEED_PATCH）；**Block Tree** 把带 flag 的动态节点收集进**扁平数组**，diff 从「递归整棵树」变成「遍历数组」。机制与 Vue 2 的逐层对比见本文档「五十、Vue 2 和 Vue 3 有哪些区别？Vue 3 有哪些更新？」。

### 2、运行时：惰性代理与 shapeFlag

- `reactive()` 访问 `state.a.b` 时才为 `b` 建代理，深层大对象不被连带代理。
- vnode 用 `shapeFlag` 位掩码标记 ELEMENT / TEXT_CHILDREN / ARRAY_CHILDREN，判类型是一次位与，不是 `instanceof` 链。
- 列表 diff 用**最长递增子序列**算出「哪些节点可以原地不动」，只移动真正需要移动的，减少 DOM 插入。

### 3、SSR 与 hydration

借助编译期信息，静态内容在客户端 hydration 时可跳过比对，这是 Vue 3 首屏可交互时间改善的主要来源之一。

### 4、性能收益的边界（面试加分点）

① 官方 benchmark 是**微基准**，业务里组件粒度、静态内容占比、响应式数据规模才是决定因素；② `reactive` 是**深代理**，把上万条纯展示数据塞进去反而更慢——改用 `shallowRef` + 整体替换，或用 `markRaw` 标记永不变化的大对象（地图实例、图表实例）；③ `computed` 有缓存，但**依赖链过长**时收益衰减，能算一次就别在模板里调方法；④ 真正的首屏瓶颈通常在**包体积与请求数**，`<script setup>` + 路由懒加载 + 组件库按需引入，比「升级到 Vue 3」更见效。

> 延伸阅读：<https://cn.vuejs.org/guide/best-practices/performance.html>

## 五十二、Vue 3 的设计目标是什么？在设计过程中做了哪些优化？

**回答重点**：三个设计目标是**更小更快**（可 tree-shaking 的模块化内核 + 编译期优化）、**更好维护与复用**（Composition API + TypeScript 重写）、**更通用也更平滑**（`runtime-core` 平台无关 + 自定义渲染器 + 渐进式迁移）。必答句：「**Vue 3 是带着约束重写的：既要解决 Vue 2 在大型项目里的两个真痛点——逻辑复用只能靠 mixin、类型推导只能靠 `this`，又要让存量应用能渐进迁移，于是选了 monorepo 拆包、`runtime-core` + 自定义渲染器、TS 重写、`@vue/compat` 兼容构建这四条路**」。

| 设计目标 | 具体动作 | 结果 |
|---|---|---|
| 更小 | monorepo 拆成 `reactivity` / `runtime-core` / `runtime-dom` / `compiler-core` / `server-renderer` 等包，全部 ESM | 只 import 用到的包，未用 API 被摇掉 |
| 更快 | Proxy 响应式、静态提升、`patchFlag`、Block Tree、新 diff | 初始化与更新都更快，静态内容跳过比对 |
| 可维护 | Composition API 按功能组织代码，composable 替代 mixin | 复用显式、无命名冲突、来源可追 |
| 类型友好 | 源码用 TypeScript 重写，类型与实现同源 | `defineComponent` / `PropType` / `vue-tsc` 模板检查 |
| 可扩展 | `runtime-core` 不依赖 DOM，平台能力由渲染器注入 | 同一套组件模型可渲染到小程序、Canvas、WebGL、终端 |
| 可迁移 | 保留 Options API、提供 `@vue/compat`、Vue 2.7 反向移植 Composition API | 存量项目可逐组件升级 |

### 1、`runtime-core` + 自定义渲染器 = 跨平台

```js
import { createRenderer } from '@vue/runtime-core';

// 平台只需实现这几个「如何操作节点」的原语，响应式/组件/diff 逻辑全部复用
const { createApp } = createRenderer({
  createElement: (tag) => nativeCreate(tag),
  insert: (child, parent, anchor) => nativeInsert(child, parent, anchor),
  remove: (child) => nativeRemove(child),
  patchProp: (el, key, prev, next) => nativeSetProp(el, key, next),
  // ... parentNode / nextSibling / setText 等
});
```

`runtime-dom` 只是这套原语在浏览器上的一个实现；小程序、Native、Canvas 渲染库都是同一机制的产物。这条设计也让 SSR 复用同一套组件实例逻辑（`server-renderer`）。

### 2、TypeScript 重写带来的连锁收益

- 源码即类型：RFC 与实现同源，`defineComponent` 让 Options API 里的 `this` 也能推导。
- 模板类型检查（`vue-tsc`）：模板里写错 prop 名、漏传必填参数可在编译期报错。
- 组合式函数天然可类型化：`useXxx()` 的泛型直接流到调用方，这是 Options API 的 `this` 混入做不到的。

### 3、渐进式迁移的具体抓手

- **API 兼容**：Options API、`data`/`computed`/`watch`、指令、渲染函数全部保留。
- **`@vue/compat`**：用 Vue 3 运行时模拟 Vue 2 行为，对废弃 API 打运行时警告，可按组件开关，实现「先升级、再逐个改造」。
- **Vue 2.7**：把 Composition API 与 `<script setup>` 反向移植回 2.x，无法立刻升级的项目也能先统一写法。
- **迁移指南**：官方逐条列出破坏性变更，并给出 codemod（`vue-codemod` / `gogocode`）批量改写。

### 4、面试追问的正确答法

① 「Vue 3 完全重写所以不兼容」——**说法要修正**：对外 API 以兼容为主，破坏性变更集中在 `filters`、`$children`、EventBus、`v-if`/`v-for` 优先级、`functional` 组件声明等少数点（清单见本文档「五十、Vue 2 和 Vue 3 有哪些区别？Vue 3 有哪些更新？」）；② 「性能提升 2 倍」是官方 benchmark 的相对值，不是业务承诺，要补一句「真实收益取决于模板静态占比与组件粒度」；③ 「为什么不用 polyfill 兼容 IE」——`Proxy` 的拦截语义无法用 `defineProperty` 完整模拟（`delete`、新增属性、数组下标），且 Vue 3 目标环境已放弃 IE11；④ 设计目标的权衡要能说出来：**体积与功能完备冲突时选 tree-shaking，跨平台抽象与首屏性能冲突时选编译期优化**，这正是 Vue 3 把大量工作放进编译器的原因。

> 延伸阅读：<https://cn.vuejs.org/guide/introduction.html>、<https://github.com/vuejs/core>

## 五十三、Vue Router 中如何获取路由传递过来的参数？

**回答重点**：传参只有两条通道——**路径里的动态段（`params`）**与**`?` 后的查询串（`query`）**，取时分别读 `$route.params` / `$route.query`，Composition API 里用 `useRoute()`。必答句：「**`/user/:id` 声明的动态段从 `route.params.id` 取，`/user?id=1` 的查询串从 `route.query.id` 取；`params` 是路径的一部分、刷新不丢，`query` 是附加状态、可缺省；组件复用时 `created` 不会再执行，必须在 `watch` 里响应参数变化**」。

| 维度 | 动态路由 `params` | 查询参数 `query` |
|---|---|---|
| 声明 | 路由表 `path: '/user/:id'` | 无需声明，URL 自带 `?k=v` |
| 读取 | `this.$route.params.id` / `useRoute().params.id` | `this.$route.query.id` / `useRoute().query.id` |
| 适用 | 资源标识：`/user/123`、`/article/456` | 筛选、搜索、分页、埋点等可选状态：`/search?query=vue&page=2` |
| 优势 | URL 简短、语义化、SEO 友好，参数**必填** | 多参数组合、顺序无关、可缺省 |
| 坑 | 同组件复用（`/user/1` → `/user/2`）时生命周期不重跑 | 取到的值**全是字符串**，数字要自行转换；Vue Router 4 已移除「按 `name` 传 `params` 但路径不体现」的隐式传参 |

```javascript
// 混合使用：/user/123?tab=info
watch: {
  '$route'(to) { this.load(to.params.id, to.query.tab) }
}

// Composition API：immediate 保证首次进入也执行
const route = useRoute()
watch(() => route.params.id, (id) => load(id), { immediate: true })
```

**最佳实践**：参数保持简短有意义；对 `params` 做存在性与格式校验、给 `query` 兜默认值，缺参时重定向而不是让页面白屏。

## 五十四、Vue Router 如何配置 404 页面？

**回答重点**：加一条**通配符兜底路由**指向 NotFound 组件，且**必须放在路由表最后一条**——路由是按顺序匹配的，放前面会把后面的规则全部吃掉。必答句：「**Vue Router 3 用 `path: '*'`，Vue Router 4 改为 `path: '/:pathMatch(.*)*'`；兜底路由放数组末尾，`history` 模式还要服务端把所有路径回退到 `index.html`，否则用户直接访问深链接时服务器先返回真 404、根本进不到前端路由**」。

```javascript
// Vue Router 4（Vue 3）
const routes = [
  { path: '/', component: Home },
  { path: '/:pathMatch(.*)*', name: 'NotFound', component: () => import('@/views/NotFound.vue') },
]
const router = createRouter({ history: createWebHistory(), routes })
```

- **懒加载**：404 组件用 `() => import(...)`，只有真走到才下载，不占首屏包体。
- **history 模式的服务端配合**：nginx `try_files $uri $uri/ /index.html;`；hash 模式（`#/xxx`）零配置但 SEO 差、链接丑。
- **嵌套路由**：子路由未匹配时需在 `children` 里也加通配，否则父级不会渲染子兜底页。
- **页面设计**：给返回首页 / 上一页按钮和搜索入口；要区分「路径不存在」与「已登录但无权限」时，用导航守卫跳 403，别复用 404。

## 五十五、Vue 如何优化网站首页的加载速度？

**回答重点**：Vue 首页慢通常慢在**打包体积大 + 关键渲染路径被 JS 阻塞**，主线是「**拆包按需加载 → 压缩与 CDN → 首屏渲染策略（SSR / 骨架屏）**」。必答句：「**路由懒加载与第三方库按需引入把首屏 JS 砍到最小，gzip/Brotli 配合 CDN 降低传输时间，图片换 WebP 并懒加载，再用 SSR 或骨架屏改善首屏感知；先用 `webpack-bundle-analyzer` 定位包体大头，不要一上来就上 SSR**」。

| 手段 | 优化什么 | 做法 | 代价 / 注意 |
|---|---|---|---|
| 路由懒加载 | 首屏 JS 体积 | `component: () => import(...)` 按路由分块 | 切路由多一次请求（HTTP/2 下影响小） |
| 第三方库按需 | 包体 | `lodash-es` 单函数引入、`unplugin-vue-components` 自动按需注册 UI 库 | 需要配置 |
| gzip / Brotli | 传输体积 | 服务端开启压缩，或 `compression-webpack-plugin` 预压缩 | 服务端要支持对应编码 |
| CDN | 传输距离与并发 | 静态资源走 CDN，`publicPath` 指向 CDN 域名 | 缓存失效策略要管好 |
| 图片 | 体积与渲染阻塞 | WebP/AVIF、`srcset`、`loading="lazy"`、首屏大图 `preload` | 兼容性兜底 |
| SSR / SSG | 首屏可见时间、SEO | Nuxt 3 服务端渲染或预渲染静态页 | 需 Node 服务，改造最重 |
| 骨架屏 | **感知**速度 | 先渲染占位骨架，数据回来再替换 | 真实耗时不变，只改感知 |
| PWA / 缓存 | 二次访问 | Service Worker 缓存静态资源与接口 | 更新策略要防旧版本卡死 |

**排查顺序**：先看包体（`webpack-bundle-analyzer` / `vite build --mode analyze`），再看 DevTools 网络瀑布图确认瓶颈是 TTFB、还是 JS 解析执行，最后用 Lighthouse 复核 LCP。
