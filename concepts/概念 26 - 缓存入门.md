# 概念 26 - 缓存入门

> 缓存是以空间换时间的典型应用：将数据提前存放到内存以提高访问速度。本地缓存、分布式缓存、多级缓存各有适用场景，配合 LRU/TTL 等淘汰策略和 Caffeine、Redis 等成熟实现使用。

## 什么是缓存？

缓存（Cache）本意指可以进行高速数据交换的存储器，通俗来说就是**通过将数据提前存放到内存，以提高访问速度**。

- 设计程序或算法时有两个基本指标：**时间复杂度**和**空间复杂度**。无法同时满足时只能以时间换空间、或以空间换时间——缓存是**以空间换时间**思想的典型应用，牺牲一部分内存空间，可获得数百倍的读取性能提升
- 缓存最常见的数据结构是**键值对（Key/Value）**，类似字典：一个 Key 对应一个 Value，访问缓存时通过 Key 获取 Value

## 为什么需要缓存？

最简单的后端系统只需一个应用服务（如 Tomcat）+ 持久化存储的数据库（如 MySQL），访问量小时足够。但随着用户数和访问量提升：

1. 数据库收到越来越多并发请求，而数据库**从磁盘读取数据、性能较低**，压力越来越大
2. 应用访问数据库的连接数有限，处理能力跟不上请求数时，新请求排队等待，后台程序**阻塞**
3. 并发请求持续增大时，数据库**甚至会挂掉**

因此在数据库之上增加一层缓存：首次读取数据时存入缓存，后续请求读取相同数据只需从缓存读取。缓存将数据存在内存中、读取速度极快，提升性能的同时替数据库分担大量压力。

## 缓存类别

### 本地缓存

直接运行在应用程序本地的缓存组件，如 JVM 中的 Map 数据结构：

```java
class LocalCache {
  private static Map<String, Object> cache = new HashMap<>();
  private LocalCache() {}
  public static void put(String key, Object value) { cache.put(key, value); }
  public static Object get(String key) { return cache.get(key); }
}
```

- **适用场景**：应用只运行在一台服务器上，且多个应用之间不需要共享缓存数据（如用户 token）；访问缓存不需网络传输，非常方便迅速
- **缺点**：与应用程序强耦合，应用停止缓存即停止；分布式场景下每台机器单独维护一份本地缓存，无法共享数据且浪费内存（每台机器可能缓存了相同数据）

### 分布式缓存

**独立的缓存服务**，不与任何具体应用耦合，可独立运行并搭建缓存集群。类似数据库，所有应用都可连接同一个缓存服务获取相同缓存数据。

- **优点**：数据共享；无需每台机器单独维护；可集中管理和整体管控分析；便于扩展和容错
- **缺点**：应用必须通过网络访问，产生额外网络开销；每台机器都可能影响整个分布式缓存服务，分布式缓存一旦挂掉，所有应用都可能瘫痪（缓存雪崩）

### 多级缓存

本地缓存与分布式缓存结合，形成多级缓存服务：首次查询（无缓存）时同时写入本地缓存和分布式缓存；之后的查询优先查分布式缓存，若其宕机则从本地缓存获取。多级缓存起到**兜底**作用，即使缓存挂掉也能支撑应用运行一段时间。

两种缓存没有绝对优劣，应根据实际业务场景选型。

## 缓存淘汰策略

内存不是无限的，实现缓存必须设计淘汰策略，按某种机制回收内存、防止缓存无限增长撑爆内存。关键问题是：缓存空间已满时，选择哪些缓存删除。

| 策略 | 原理 | 特点 |
|------|------|------|
| LRU 最近最少使用 | 按最近访问时间淘汰，「最近没被访问，将来被访问可能性也小」 | 最经典；缺点：一次冷数据批量查询可能误删大量热点数据 |
| 近似 LRU | 每次随机选一批数据做 LRU 淘汰，而非全量运算 | 牺牲部分准确度提升效率；Redis 3.0 后维护候选池优化（随机数据入池做 LRU，池满后新随机数据替换池中最近被访问的数据） |
| TTL 超时时间 | 为缓存设置过期时间，到期删除；空间满时优先淘汰最接近过期时间的数据 | 实现简单直观 |
| LFU 最少使用 | 记录每个缓存数据的访问次数（频率），优先清除使用次数较少的数据 | 缺点：最新写入的数据访问次数少，常刚被缓存就删除 |
| FIFO 先进先出 | 按写入顺序排队，空间不足时最先进入的优先删除 | 比较死板、不考虑数据热度，可能淘汰大量热点数据，但实现容易 |
| Second-Chance | FIFO 改进：给每个数据加引用标志，被访问时置 1；淘汰时检测队首数据，标志为 1 则重置为 0 并重新加入队尾，为 0 直接淘汰 | 比 FIFO 灵活，降低淘汰热点数据风险 |
| Random 随机 | 随机淘汰 | 一般不建议使用 |

其他策略如优先淘汰占用空间最大的数据等。

## 常用缓存实现

自己实现优秀缓存难度大（不止用数组或集合类），可直接使用现成类库、框架和中间件：

| 实现 | 说明 |
|------|------|
| Caffeine | 基于 Java 8 的近似最佳高性能本地缓存库，灵活构造器 API 组合各种特性，堪称进程缓存之王（github.com/ben-manes/caffeine） |
| Guava Cache | Google 开源 Java 工具包 Guava 中的本地缓存实现，提供 time-based、size-based 等多种淘汰策略（github.com/google/guava） |
| Ehcache | Java 实现的开源缓存框架，特性齐全、成熟轻量，支持通过 RMI 等方式实现可扩展的分布式缓存（ehcache.org） |
| Memcached | 开源高性能分布式内存 K/V 缓存系统，支持主流语言 API，适合存储小块数据、可利用多核 CPU；缺点是不支持持久化（memcached.org） |
| Redis | 知名 K/V 存储系统，适用于分布式缓存，支持多种数据结构、读写性能极高，可搭高可用集群、易扩展、支持持久化，还能通过 Lua 脚本实现原子性 |
| Spring Cache | 提供抽象的缓存接口，底层可选择不同缓存实现（如 Caffeine 或 Guava Cache），帮助更好地使用缓存 |

## 没有银弹

缓存优点很多但也不是万能的：引入缓存后还要考虑缓存删除、缓存更新、**缓存穿透、缓存击穿、缓存雪崩**等问题；引入的缓存级数越多，数据不一致的风险越大。架构设计时要根据实际业务需求决定是否使用缓存、选用何种缓存。
