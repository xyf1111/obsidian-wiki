# 概念 23 - 权限管理设计（授权·权限组·RBAC）

> 需求场景：内部任务调度系统中，任务创建者 A 要把任务移交同组 B 维护。临时解决用「直接改库」移花接木，永久解决靠权限管理体系（授权 / 权限组 / RBAC）三选一。

## 需求场景

内部大数据任务调度系统：部门用户可创建、删除、执行任务，前后端均限制只有任务创建者本人或管理员可修改删除。用户 A 已创建大量任务，同组新人 B 入职后需接手维护这些任务（且很着急）。

## 临时解决：方案头脑风暴与取舍

| 方案 | 做法 | 弃用原因 |
|------|------|---------|
| hardcode | 代码里写特殊判断：创建者是 A、操作者是 B 时放行 | 要改代码、走发布评审上线，之后还得去掉特殊逻辑 |
| 移除权限校验 | 所有人可修改所有任务 | 内部系统用户少、默认只能看到自己创建的任务，风险可控但仍存在 |
| 替换用户 id | 用户表把 A、B 的 id 互换（换身份证） | 太粗暴，A 其他任务之外的权限全受影响 |
| 克隆账户 | 克隆 A 的账户给 B | 任务关联唯一 user id，克隆产生的是新 id 的新用户，无用 |
| 加管理员 | 给 B 管理员权限 | 管理员权限过大，有安全风险 |
| 模拟登录接口 | 开放「模拟他人登录」接口给用户 | 接口本身有风险，为安全不采用 |

**最终方案：直接改数据库**——把 A 创建的任务的「创建人」字段改为 B。零代码改动、快狠准（任务少，改库成本低）。

安全改库实施流程（5 步）：
1. 分析「创建人」字段的关联性，确认修改不影响其他功能
2. 找其他开发 + 产品二次确认操作风险
3. 与用户（A、B）确认：之后 A 不再参与编辑，全部交给 B
4. 先改 1 个任务试点，让 B 试修改验证
5. 确认无误后，再批量修改其余任务

> 有些操作和设计长久来看不合理，但能以较低成本临时解决问题，也是不错的方案——多思考、灵活变通（移花接木）。

## 永久解决：权限管理体系 3 方案

| 方案 | 做法 | 特点 |
|------|------|------|
| 授权 | 任务创建者给其他角色分配修改权限（类似腾讯文档） | 开发最快、最好理解；但批量给多人分配麻烦，用户操作成本高 |
| 权限组 | 创建者给其他角色或某个小组的所有人分配权限 | A 建权限组把 B 拉入，后续加人再拉入即可；适合当前场景 |
| RBAC | 基于角色的访问控制：权限赋予角色、角色赋予用户 | 最灵活完整；但开发成本最高，对象/角色/权限少时大材小用 |

**选型建议**：方案 1 开发最快但批量分配体验差；方案 3 灵活但成本高；方案 2 相对最适用小团队内部系统——若系统本身已有权限组功能，只需把任务与权限组关联，开发成本很低。
