# 概念 30 - 大文件上传设计（分块·断点续传·秒传）

> 小文件上传没什么好说的，难点在于大文件怎么传得**更快、更稳定、更灵活**。经典方案是五种设计的组合：文件分块、并发上传、断点续传、秒传、异步上传。

## 为什么大文件上传难

- 上传 GB 级文件时，网络一抖就失败，若要从 0 重新上传，用户体验极差
- 自制网盘还要考虑存储、下载、文件与目录管理；真正上线还要面对权限管理、接口访问、CDN 加速——想省事可直接用开源网盘（Seafile / Nextcloud / Cloudreve / OwnCloud），公用网盘最大的成本是带宽与存储

## 五种经典设计

### 1. 文件分块（分片上传）

把大文件分割为多个连续的小文件块，一块一块发送：

- 每个块额外携带元信息：当前块数、文件总块数、文件大小、所属原文件标识（MD5）等
- 服务器逐块接收，保存到临时目录；收到最后一块后，把所有块拼接成完整原文件

### 2. 并发上传

分块后即可多线程并发上传，同时传输多个块：

- 是否并发、并发多少块要**根据网络情况决定**，不是并发数越多越好
- 网络好 → 调大并发数，大幅提升整体上传效率；盲目调高反而可能更慢

### 3. 断点续传

上传中断后从进度处继续，而不是从第 1 块重传：

- 原理：在分块基础上，服务器记录原文件对应的上传进度，每收到一块就更新进度
- 网络故障后，从进度中得知哪些块已上传、从哪一块继续
- 该原理同样适用于文件下载；实现方式多样（自主实现、HTTP/1.1 协议等）

### 4. 秒传

几 GB 文件 1 秒内完成上传——真相是**该文件之前已被上传过**：

1. 上传前在客户端（浏览器）按文件内容计算 MD5（相同内容 MD5 必然相同）
2. 在服务器已上传文件库中查找该 MD5 是否已存在
3. 不存在 → 正常上传，成功后把文件信息插入数据库
4. 已存在 → 直接新建一个指向该文件的引用，不必重复上传

注意：MD5 可能碰撞（不同内容相同 MD5），导致用户下载到别人的文件；可补充校验，如对文件前几位再生成一个 MD5、或用其他 Hash 算法再生成校验值。

### 5. 异步上传

文件不在本地、已存在对应 URL 时，把上传变成一个**任务**：

- 用户提交文件 URL → 后台新建上传任务，页面立刻响应（如「文件上传中，请留意通知」）
- 后台取出 URL 真正完成后，再给用户发通知，无需用户一直等在上传页

## 开发建议

- 开发中用到文件上传不必自己实现上述功能，用现成对象存储服务（如七牛云，分块上传等都已封装）即可
- 可参考七牛云 SDK（https://github.com/qiniu）了解其大文件上传实现
- 已用对象存储（OSS/COS）接入时参考 [[Java 工具 09 - 对象存储文件上传下载]]；本设计是上传链路本身的分块/续传/秒传机制，二者互补
