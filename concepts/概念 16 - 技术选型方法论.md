# 概念 16 - 技术选型方法论

> 技术选型的目标是**在有限的条件下、选取特定场景下的技术最优解**——由浅入深覆盖「用哪类技术 → 具体用什么 → 哪个版本 → 哪些特性」四个层次，并围绕业务与需求综合权衡。

## 核心要点

### 技术选型的四个层次（由浅入深）

1. **用哪类技术**：编程语言、开发框架、数据存储、缓存
2. **具体用什么技术**：编程语言用 Java 还是 Go？开发框架用 Spring 还是 Netty？缓存用 Redis 还是 Memcached？
3. **用哪个版本**：Java 8 还是 11？Vue 2 还是 Vue 3？Redis 5 还是 6？
4. **用到哪些技术特性**：如 Spring 的 AOP、Redis 的 GEO 高级数据结构等

### 为什么必须做技术选型

- 个人做项目可以随意（用熟悉的技术或想学的技术）；**进入企业、尤其是负责项目时，必须与团队一起确认技术选型**，项目规模越大越复杂，选型要考虑的角度和深度要求越高
- **对项目侵入性强的技术，后期改动成本越大**：页面写了几十个再切换开发框架很麻烦；引入新组件/类库可能和现有库版本冲突，导致项目跑不起来
- 翻车案例：校园贴吧网站用 React 开发前端，做到帖子页面信息状态保存功能时，发现 React 没有 Vue Router 那种现成的 keep-alive，花很久才找到类似组件还一堆 Bug——如果最开始考虑到这点选 Vue 系列技术栈，能节省大量时间

### 选型目标与考量维度

- **目标**：在有限的条件下、选取特定场景下的技术最优解
- **有限条件**：团队同学会的技术（大家都只会 Java、项目又急着上线，就优先 Java，别为了 Go 性能让全员加班学）、时间和金钱成本（公司有钱但缺人手，数据库等服务直接买云服务，不用自己搭）
- **特定场景（围绕业务和需求思考）**：
  - **业务量级**：用户数巨多要不要 Nginx/LVS 做负载均衡？存储量巨大要不要分布式数据库、分库分表？
  - **核心业务流程与关键数据结构**：管理系统选主流关系型数据库 MySQL 即可；数据分析系统选 OLAP 利好的数据库（PostgreSQL、ClickHouse）
  - **性能侧重**：日志收集重高性能和吞吐量选 Kafka；注重低延迟与消息准确性选 RabbitMQ
- 与设计算法同理：**没有绝对的最优解，而是对时间、空间、稳定性、可用性等的综合权衡**

### 两个建议

1. 做选型时先写一个最简单的 Demo 快速验证技术是否可用，**不要直接拍板**
2. 原则上优先选**知名度高、开源、用户多生态好**的技术——没几个人用的技术大概率踩雷
3. 选型前先问清楚项目要做的功能、预计用户量、存储需求，再据此调研；也可以直接问 ChatGPT 辅助选型
