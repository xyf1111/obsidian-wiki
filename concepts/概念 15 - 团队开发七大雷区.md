# 概念 15 - 团队开发七大雷区

> 新手在团队开发中常犯的 7 类问题：硬编码、重复依赖、不确认需求、不测试、无注释无规范、不读自己代码、满足于可运行。团队开发不能像自己写代码那样随意。

## 雷区一：格局小了（硬编码 + 重复代码）

多个文件写死同一个值（如机器 IP），图省事儿。复制粘贴的代码写的时候爽，改的时候要一个个改；团队中 A 的代码被 B、C 复制，A 修了 Bug 但 B、C 依旧带着 Bug——**一个 Bug 永流传**，你根本不知道自己的代码被多少人复制过。

**对策**：少写死值、少写重复代码——重复的值抽成变量/常量/配置文件，重复的代码封装成组件，并写文档和注释指引他人使用。**代码重复 3 次就可以考虑抽象**。硬编码的更多危害与规避见 [[概念 14 - 硬编码的危害与避免]]。

## 雷区二：过于自我（重复引入依赖库）

实现日期计算时新引入 Day.js，但项目已有 Moment.js 完全能满足——「我用得熟」不是理由。每人按自己习惯引入重复库的后果：

1. **依赖冲突**：A 引入 Log4j、B 引入 Logback，项目可能直接跑不起来
2. **项目加重**：项目像滚雪球一样越滚越大，想拆分/去除某部分可能雪球就碎了（极端例子：三大前端框架出现在同一项目）

**对策**：团队中架构师要先定规矩——「日期处理都用这个库、日志都用那个库」；技术选型综合考虑业务适应性、团队学习成本。**谨慎引入新依赖**：先扫一遍项目现有依赖，能满足就直接用；实在要引入先跟伙伴商量，避免冲突。

## 雷区三：急不可耐（没搞清需求就写码）

让拧螺丝，造了个汽车——需求都没理解就上手写代码，出力不讨好。另一种表现：项目里已有现成轮子/简单写法，不看文档就自己造轮子（自己造了个扳手），费事费力。

**对策**：企业里开发要和产品经理反复确认，**先彻底理解需求 → 设计方案 → 再写代码**；动手前先看项目文档，有现成的就用现成的。

## 雷区四：盲目自信（写完不测试）

「这功能不就是增删改查，能有啥问题？」——写完不测直接交。经验越丰富的程序员反而越谨慎，写完认真测试，而不是盲目相信经验和直觉。

**对策**：测试不要只草草点一遍没问题就算完，要尽量覆盖所有正常情况，**尤其异常情况**——用户不听话，你无法想象他们在系统里能干出什么事。

## 雷区五：制造屎山（无注释、无规范）

一个文件千行代码零注释，自己都讲不清自己的代码；代码不遵循规范。人人如此，巨型屎山指日可待。

## 雷区六：过眼云烟（写完不再读代码）

自己写过的代码一定要多读几遍，像考试做完检查卷子一样。自学的代码没人逼你交卷，更要养成习惯。

**实践参考**：写完至少读三遍——**写完一个子功能读一遍、测试前读一遍、提交前读一遍**。自己都不愿看的代码，别人审查时发现一堆问题打回来，浪费别人的时间；线上出了问题肯定还是自己背锅——**没有人能拯救你的 Bug，除了你自己**。

## 雷区七：敷衍了事（满足于可运行）

仅仅满足于代码可运行、功能可用，不注重细节、不做优化。例如两个循环遍历同一边界可合并成一个：

```java
for(int i = 0; i < maxNum; i++) {
  doSomething1();
}
for(int i = 0; i < maxNum; i++) {
  doSomething2();
}
// 可合并为：
for(int i = 0; i < maxNum; i++) {
  doSomething1();
  doSomething2();
}
```

**每个项目都有进步空间，要仔细挖掘而不是敷衍了事**——别整天抱怨增删改查没竞争力，做项目的过程本身就是提升。主动优化代码的习惯见 [[概念 05 - 悲观编程：主动优化代码的编程习惯]]。
