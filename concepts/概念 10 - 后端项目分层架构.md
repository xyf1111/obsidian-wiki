# 概念 - 后端项目分层架构

> 分层架构将系统自上而下分为多个不同层，每层有特定职责，只与直接上下层交互

## 核心要点

### 定义

分层架构把系统自上而下划分为多个层，每层有明确定义的职责，只和自己的直接上层与直接下层"打交道"。

### 优点

- **职责清晰**：每层功能明确，易于理解和维护
- **独立扩展**：各层可独立扩展以适应不同需求
- **应用广泛**：最适合新手入门，也是实际开发中最常见的架构

## 分层结构（Java 企业级后端）

从前端请求出发，自上而下经历以下层级：

### 1. 表示层
用户交互的前端界面（用户层、界面层），负责发送请求。

### 2. 接入层
Nginx 网关或中间件，对请求做预处理和转发（如负载均衡）。非必须层，中大型项目常见，前端也可直接请求后端。

### 3. 控制层（Controller）
接收请求，调用业务逻辑层实现功能并响应结果。**不应写复杂业务逻辑**，保持精简。

### 4. 业务逻辑层（Service）
处理核心业务逻辑：请求数据校验、处理、调用数据访问层存取数据库等。是系统开发的主要编码部分。

### 5. 通用业务层（Manager / Module）
特殊的业务逻辑层，抽取多个业务需调用的公共代码（如文件上传、鉴权），实现复用。

### 6. 数据访问层（Dao / Mapper）
操作底层数据源，对数据库、文件、缓存等进行增删改查。

### 7. 系统资源层（基础设施层）
包括基础服务与系统环境：数据库、消息队列、Redis、文件存储、Linux、Docker 等。复杂场景还包括 K8S 容器编排、资源调度平台。

> 并非所有项目都需要完整七层，不同业务和团队可按需选择与调整。

## 项目目录组织

基于分层架构，代码按目录（包名）组织：

```
controller/   # 控制层
service/      # 业务逻辑层
mapper/       # 数据访问层
model/        # 数据模型
```

还可按文件类型划分：

```
constant/     # 常量
annotation/   # 注解类
common/       # 公共类
config/       # 配置类
job/          # 任务
exception/    # 异常处理
utils/        # 工具类
```

## 相关知识

### OSI 七层模型对比
计算机网络同样采用分层架构。OSI 七层参考模型自底向上为：物理层 → 数据链路层 → 网络层 → 传输层 → 会话层 → 表示层 → 应用层。每层处理特定功能（如数据传输、路由），层间通过接口（协议）通信。

### Spring MVC 与分层架构
Spring MVC 基于 MVC（Model-View-Controller）**设计模式**构建，不能算传统分层架构。现代项目中通常将 Spring MVC 作为整个项目的控制层，但使用了 Spring MVC 的项目大多同时采用了分层架构。
