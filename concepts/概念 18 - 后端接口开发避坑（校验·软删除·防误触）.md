# 概念 18 - 后端接口开发避坑（校验·软删除·防误触）

> 以「删除消息」功能为例，拆解第一次写后端接口最容易踩的三个坑：只在前端做校验、直接物理删除、删除无二次确认——任何一个上线都可能酿成事故。

## 核心要点

### 场景：删除已读消息功能

- 前端：删除按钮 + 点击事件，调用后端删除接口；已读校验做在前端（`msg.id && msg.isRead` 才调接口）
- 后端：接收 msgId → 操作数据库删除指定 id 的消息 → 返回结果

### 坑 1：未做校验（最高级事故）

- 前端校验**不是安全边界**：恶意用户可以用工具绕过浏览器直接请求后端接口，随便传消息 id，甚至遍历所有 id
- 后果：后端不做校验，一上线正常用户的消息可能就被删光
- 正确做法——后端三重校验：
  1. **参数合法性**：msgId 是否存在
  2. **数据最新状态**：从数据库查消息当前状态（不能信任前端传的已读标记）
  3. **登录用户校验**：从 session / 中间件获取当前用户，消息的 userId 必须等于当前用户 id
- 原则：**后端接口是业务核心，必须加强校验**；前后端同一个人写时最容易犯「以为前端判断就够了」的错

```js
function deleteMsgById(msgId) {
  if (!msgId) return false;                    // 1. 参数校验
  const msg = db.getMsgById(msgId);            // 2. 查数据库最新状态
  const user = getCurrentUser();               // 3. 当前登录用户
  if (!msg.isRead || !user || msg.userId !== user.id) return false;
  return db.deleteById(msgId);
}
```

### 坑 2：硬删除

- 直接 `delete` 数据的问题：管理员排查问题缺线索——用户发违规消息后自己删掉，管理员就查不到违规记录了
- 软删除：数据表加 `isDelete` 字段（0 未删 / 1 已删），删除 = 把 0 更新为 1；正常只展示 `isDelete = 0` 的数据

```js
// 原代码，真实删除
db.deleteById(msgId)
// 新代码，软删除（更新标记）
db.updateById(msgId, {isDelete: 1})
```

- **不是所有表都需要软删除**，按业务场景决定：需要留痕审计的业务（消息、订单、用户）适合软删除；纯临时数据可硬删

### 坑 3：无防误触（产品体验）

- 删除属于不可逆操作，用户点击时应弹**二次确认框**，防止误点后消息找不回
- 前端开发做得越多越会注重这类小细节，提升用户体验

### 小结

- 写完接口自查三步：**参数校验了吗？数据状态校验了吗？当前用户校验了吗？删除是软删吗？有二次确认吗？**
- 养成良好编程习惯，别让第一版代码带着隐患上线
