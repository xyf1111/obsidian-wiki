# 概念 25 - 魔法值（魔数）的危害与避免

> 魔数/魔法值是代码中凭空出现、无任何解释的常量，严重影响可读性与可维护性；用常量与枚举替代是基本编码规范。

## 什么是魔数 / 魔法值

- **魔数**：毫无理由、凭空出现、也不需要解释其含义的常量。经典的例子是 C++ hash_map 源码中的宏 `0xDEADBEEF`（"dead beef" 直译"死牛肉"）——常用来标识新分配但未初始化的内存，或表示程序崩溃/死锁（如 32 位 PowerPC 上的 IBM RS/6000、Mac OS 系统）。选这个词没什么理由，它就是程序员界的"魔数"彩蛋。
- **魔法值**：代码中没有任何定义、像魔法一样凭空出现的值，可以是数字、字符串等：

```js
console.log(1);   // 输出
alert("dog");     // 弹出警告框
```

两者是同一概念（魔法值含魔数），共同点：**值本身不携带任何语义**。

### 著名的魔数（编程彩蛋）

| 魔数 | 含义 | 出处 |
|------|------|------|
| `0xDEADBEEF` | 未初始化内存 / 崩溃或死锁标记 | 调试堆、IBM RS/6000、Mac OS |
| `0xBAADF00D`（"bad food"） | 未初始化的已分配堆内存 | 微软 LocalAlloc（LMEM_FIXED）调试堆 |
| `0xDEADC0DE`（"dead code"） | 静态固件末尾 jffs2 文件系统开始标记 | OpenWRT 固件 |
| `0xDEAD10CC`（"dead lock"） | iOS 系统闪退报告 | iOS |
| `0x5f3759df` | 快速计算平方根的倒数（一行魔法代码） | 雷神之锤（约翰·卡马克） |

这些是前辈们公认、约定俗成的魔数，才称得上"浪漫"；普通代码里用魔数，只能叫烂代码。

## 魔法值的问题

### 1. 影响可读性与可维护性

魔法字符串还好，魔法数字必须靠读其他代码才能推断含义：

```js
if (a == 1) {
  alert("good");
} else if (a == 2) {
  alert("bad");
} else if (a == 3) {
  ...
}
```

数字 1、2、3 分别代表什么？自己写的代码过一个月再看也未必懂；多人协作时别人更看不懂，不写注释会严重影响团队效率。

### 2. 影响开发效率与准确性

同样的值反复手写，浪费时间且存在**打错字的风险**；而预定义常量能利用开发工具的**代码提示和补全**功能。例如"操作失败"提示在文件中出现多次，直接写魔法字符串每次都要重复输入，定义 `const ERROR_MESSAGE = "操作失败"` 后只需引用常量。

### 3. 影响易修改性

同一魔法字符串出现多次时，改文案要人工逐个查找替换，即使有全局替换也要逐一检查；定义为常量则**只改定义处**即可：

```js
const ERROR_MESSAGE = "你操作失败了";
alert(ERROR_MESSAGE);
alert(ERROR_MESSAGE);
```

此时常量名就像魔法值的一个"指针"。

## 如何避免魔法值

1. **定义常量**（注意是常量不是变量——魔法值内容固定、结构不会被修改），为相同的值加"注释"：

```java
int ONE_DAY = 86400;          // 3600 * 24
int ONE_GB = 1073741824;      // 1024 * 1024 * 1024
int MAX_INTEGER = 2147483647; // int 类型最大值
```

2. **一系列相关的值用枚举或常量类集中定义**，比如资源审核状态：

```js
const REVIEW_STATUS = {
  WAITING: 0,  // 待审核
  PASS: 1,     // 通过
  REJECT: 2    // 拒绝
}
```

```java
public enum ReviewStatus {
  WAITING, PASS, REJECT
}
```

各种代码规范都建议不使用魔法值。日常开发中常见的裸数字也要警惕：`86400` = 一天的秒数、`1073741824` = 1 GB、`2147483647` = int 最大值——都应该抽成语义化常量。

> 与 [[概念 14 - 硬编码的危害与避免]] 互补：硬编码侧重"把未来可能变化的信息写死"（IP/账号密码/业务逻辑，用配置化解决），魔法值侧重"无定义的裸常量损害可读性"（用常量/枚举解决），两者都指向"抽常量、不写死"的编码习惯。
