# 概念 17 - 企业项目开发流程

> 大厂（企业）项目研发全流程方法论：从需求到上线后运维的完整链路。与个人开发最大的区别在于——个人开发是单打独斗、想到哪写到哪，追求快速实现功能；企业开发是团队作战、强调流程、规范、协作与质量保证，每个环节都有评审、检测与把关机制。流程各阶段并非严格串行，存在交叉（如技术选型在设计阶段就应开始考虑）。

## 研发流程全景

企业研发流程可概括为一条完整链路：

**需求阶段 → 设计阶段 → 研发准备 → 研发阶段 → 测试验证 → 提交阶段 → 发布阶段 → 上线后**

- 需求阶段：需求产生、评审、分析、排期；
- 设计阶段：架构设计、概要设计、详细设计、方案对齐、测试用例设计；
- 研发准备：技术预研、技术选型、资源申请、环境准备、项目初始化、依赖安装；
- 研发阶段：本地/远程开发、AI 辅助、代码优化、单元测试、开发联调；
- 测试验证：集成测试、系统测试、产品体验、验收测试；
- 提交阶段：代码提交、推送、合并请求、代码审查；
- 发布阶段：自动化构建、预发布、正式发布（灰度）；
- 上线后：监控运维、统计分析、事件反馈、文档沉淀、迭代优化。

> 各阶段不是严格从上到下顺序执行，阶段间可能存在交叉，比如技术选型在设计阶段就应该考虑。

## 一、需求阶段

需求是项目的起点，由产品、老板、用户反馈等渠道产生。本阶段要回答三个问题：需求是否合理、怎么做、什么时候上线。

- **需求产生**：用户反馈不好用、老板反馈性能差（如页面加载十几秒）等，都可能催生新项目或大改版。
- **需求评审**：老板、产品、测试、开发共同评估需求「是否合理、要不要做」，各方从不同视角把关。
- **需求分析**：开发分析「这个需求怎么做」，提出改动低、实现快的解决方案；产品与开发意见冲突时，需要技术方案来平衡。AI 时代可用 ChatGPT、Cursor 等工具辅助分析需求、快速生成多种技术方案对比，提升效率。
- **排期**：将需求拆解为多个功能点，逐个安排计划完成日期（如功能 A 本周完成、功能 B 下周二测试、下周四上线），形成可执行的交付计划。

## 二、设计阶段

「想好怎么写代码比写代码更重要。」设计文档写好后，实现只是顺理成章的事。

- **架构设计**：从整体到局部，梳理系统层次结构、各层间交互接口与通讯方式、每层包含的重要模块、模块的物理部署方式。可用 AI 辅助生成架构图、分析方案优缺点、做技术调研。
- **概要设计**：对着 PRD（产品需求文档）分析需求，整理系统需要的功能模块及子模块；比架构设计更贴近需求，是架构设计的细化。类比：架构设计决定楼有几层、管道怎么接、地基怎么打；概要设计决定每户套间内部客厅、卫生间怎么划分。实践中两者常合并在一个文档中。
- **详细设计**：具体分析每个功能如何实现：用到哪些算法、注重哪些细节。
- **方案对齐**：与前端、后端等其他开发同学开会讨论设计方案，最终产生统一方案，再分工执行。
- **测试用例设计**：为保证测试覆盖度与效率，需设计测试用例（如：点击「登录」未传任何数据 → 期望警告用户输入用户名和密码）。用例设计后由其他同学（尤其熟悉代码的开发）一起评审补充，避免个人遗漏，让问题暴露在测试阶段而非线上。

## 三、研发准备

写代码之前，还有一系列准备工作：技术调研、选型、申请资源、搭环境、初始化项目。

- **技术预研**：对项目需要或可能需要用到的技术做调研；AI 工具可快速了解新技术、对比方案、生成选型报告。
- **技术选型**：综合多维度考量——
  - 技术本身：性能、易用性、稳定性、主流程度与生态、文档详细度；
  - 团队因素：成员对技术的熟悉度、掌控度（有无精通该技术的人）；
  - 业务因素：是否适应业务量级（单机 or 微服务）、是否适应业务特征（读多、写多 or 分析多）。
  - 关键项目的选型文档还要与同事、Leader 讨论后才能最终确认。
- **资源申请**：企业有集中管理和分配资源的平台（如申请云数据库），填写预算、等领导审批、下发资源。禁止私自使用自己或外部服务器部署项目，不安全。
- **环境准备**：按申请机器的版本搭建一模一样的本地开发环境和测试环境，便于后续直接连接。
- **项目初始化**：用脚手架自动生成最小可运行 Demo，避免从零手敲重复代码；也可用 AI 工具（Cursor、GitHub Copilot）辅助初始化、生成模板代码。
- **依赖安装**：用包管理工具（前端 yarn/npm，Java Maven/Gradle 等）自动安装依赖，项目即可运行。

## 四、研发阶段

方案已明确，写代码实现阶段相对轻松，重点是效率工具与代码质量。

- **本地开发**：配置热更新工具，代码更新时自动重新编译打包，无需手动重启；使用 Git 等版本控制系统，开发前先创建自己的分支。
- **远程开发**：像编辑本地文件一样直接修改服务器上的代码（每位研发有自己的开发机），省去反复部署调试；VSCode 安装远程开发插件即可实现。
- **AI 辅助开发**：Cursor、GitHub Copilot 等工具已成为主流，能力包括：自动补全代码、生成单元测试、解释复杂代码、发现潜在 Bug、重构优化代码。
- **代码优化**：主动注重代码的时空复杂度；重复代码抽象为函数或使用设计模式，提升可维护性。
- **单元测试**：开发也要为自己的代码负责，为每个数据库读写函数和业务逻辑函数编写单测（Java 用 JUnit，配合 Jacoco 生成覆盖度报告）；每次修改关键代码后执行一遍单测防止意外错误；可用 AI 自动生成单测代码。
- **开发联调**：将代码打包构建，把可执行包发布到测试服务器，与前端同学联调——前端请求后端接口，验证系统功能是否可用。

## 五、测试验证

测试是企业研发的最后一道防线，目的是尽量发现并扼杀 Bug。测试粒度从小到大分为多层：

- **集成测试**：把多个模块/代码单元放在一起，验证模块间的集成与调用关系。单个函数正常不代表组合调用正常（如两个功能各自独立执行没问题，但共享同一资源并发执行时后者报错）。
- **系统测试**：粒度更大，测试对象是整个系统，不仅包括软件，还可能覆盖硬件。
- **产品体验**：产品同学体验功能是否符合预期、是否易用，常提出修改建议，开发需相应调整。
- **验收测试**：把整个产品或功能交给最终用户体验；老板/用户说没问题，才是真的没问题。

## 六、提交阶段

系统验证通过后，代码发布到远程仓库（Git、SVN 等版本控制系统），提交过程有层层检测把关。

- **代码提交**：本地触发 git commit，大项目用提交检测插件（Husky、pre-commit hook）防止错误代码被提交；现代提交还会自动触发：
  - 代码格式检查（Prettier、ESLint）
  - 单元测试执行
  - 代码规范检查（CheckStyle、SonarLint）
- **代码推送**：推送本地提交到远程同名分支，大厂有推送检测工具，检测错误、圈复杂度、代码规范等，防止不规范代码入库。
- **合并请求**：发起分支合并请求（MR / PR），把该分支代码合并到主干分支。
- **代码审查（CR）**：不能直接合并，需通过审查——
  - 人审：上级和其他项目负责人阅读、评论代码，Approve 通过或打回修改；
  - 机审：机器自动检测代码是否符合规范、能否自动化构建成功，由项目负责人配置，可发现人工难以发现的问题（如加号换行、文件行末空行等细节规范）；
  - AI Code Review：自动发现代码问题、提出优化建议，进一步提升代码质量。

## 七、发布阶段

- **打包构建**：传统方式需人工登录服务器拉代码、装依赖、打包、用 Nginx/Tomcat/Docker 运行，效率低且重复。大厂用 CI/CD 工具（Jenkins、GitLab CI、GitHub Actions）自动化构建：代码合并到主分支后，由机器自动打包为部署包。
- **预发布**：先在预发布环境部署观察是否正常运行；预发布环境配置与生产完全一致，但仅内部人员可访问。
- **正式发布**：大项目部署在多台机器，通过可视化发布平台点选机器（先灰度——选一小部分机器验证，再全量发布）、一键发布，管理员审批后交给机器自动部署；云原生时代多用 Kubernetes 进行容器编排和自动部署，发布流程更自动化、标准化。

## 八、上线后

上线不是终点，仍需保持警觉——测试过的系统仍可能冒出预期之外的 Bug。

- **监控运维**：定期查看监控面板，观察运行情况、机器负载、接口响应时间、错误率等关键指标，异常立即告警。常用工具：
  - Prometheus + Grafana：开源监控方案；
  - ELK（Elasticsearch + Logstash + Kibana）：日志收集与分析；
  - SkyWalking：分布式追踪系统；
  - 云厂商监控服务（阿里云监控、腾讯云监控等）。
- **统计分析**：利用日志平台分析用户行为，优化业务与系统。如统计 SQL 查询耗时，对重复率高的慢 SQL 针对性优化。
- **事件反馈**：公司内部有事件反馈平台，产品等同学接收到 Bug 时发布 Bug 事件，详细描述出现时间、状况、详情，便于开发集中分析处理，也避免历史 Bug 难追溯。
- **文档沉淀**：每次上线新功能/项目，写文档记录背景、设计方案、开发过程与坑点。好的文档能帮助新人快速了解项目、记录技术决策与演进历程、避免重复踩坑、方便后续维护迭代。
- **迭代优化**：一个需求的结束往往是另一个需求的开始（一期做完做二期），还要抽时间优化历史代码，持续演进。

## 个人项目 vs 企业项目对比

| 环节 | 个人项目 | 企业项目 |
|------|----------|----------|
| **需求** | 自己想做什么就做什么 | 需求评审、需求分析、排期 |
| **设计** | 想到哪写到哪 | 架构设计、概要设计、详细设计、方案评审 |
| **开发** | 一个人写代码 | 多人协作、分支管理、代码规范 |
| **测试** | 自己点点看 | 单元测试、集成测试、系统测试、测试用例 |
| **部署** | 随便部署 | 预发布、灰度发布、全量发布 |
| **上线后** | 不管了 | 监控、日志分析、Bug 修复、迭代优化 |

企业流程复杂得多，但都是为了保证项目的质量和稳定性。

## 学习建议

### 如何学习企业项目开发流程

1. **项目实战学习**：最好的学习方式是参加真实的企业项目。如果还是学生或刚入职，建议多观察团队的开发流程，主动参加各个环节（评审、设计、测试、发布），而不只是闷头写代码。
2. **跟教程做完整项目**：没有企业项目经验时，可以跟着按企业开发流程设计的实战教程学习——包含需求分析、架构设计、开发、测试、部署等完整环节，完整走一遍相当于模拟一次企业研发。
3. **学 Git 和 CI/CD**：版本控制和自动化部署是企业开发的基础，要重点学习。掌握分支管理、合并请求、自动化构建流水线的用法。
4. **了解敏捷开发**：现代互联网公司大多采用敏捷开发，要了解 Scrum、Sprint（迭代周期）、每日站会等概念，理解团队如何用小步快跑的方式协作交付。

### 推荐的学习路线

按以下顺序系统学习相关技术：

1. Git 和 GitHub：掌握版本控制；
2. 软件工程：理解开发规范和设计模式；
3. DevOps：了解研发运维一体化实践；
4. CI/CD：掌握自动化部署；
5. 做完整实战项目：体验企业级项目开发流程。

## 结语

企业开发与个人开发的核心差异在于流程、规范、协作与质量保证。想进入大厂工作，建议提前了解这套研发流程、学习相关工具与方法论，并通过完整项目实战演练企业级流程——这会在求职和工作中更有竞争力。
