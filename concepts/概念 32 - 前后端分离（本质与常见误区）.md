# 概念 32 - 前后端分离（本质与常见误区）

> 前后端分离的本质是**人员职责的分离**，是架构与协作模式，不是某个技术栈的固有属性：用 React 不等于分离，用 Java Web 不等于不分离。

## 常见误区：把架构模式和技术绑定

- **用了 React = 前后端分离？** 错。React 只是前端框架，与是否分离无关——React 一样可以前后端不分离
- **后端用了 Java Web = 前后端不分离？** 错。是否分离取决于代码与职责的划分方式，而非语言/框架
- **看到 JavaScript 就以为是写前端？** 错。Node.js 让 JavaScript 同样可以写后端

## 什么是前后端分离

- **前后端不分离**：前后端代码混杂、难以划分边界，往往由全栈开发者一人包办，写前端又写后端
- **前后端分离**：前端负责展示页面与数据，后端负责处理与提供数据，二者边界清晰，仅通过请求（接口）交互

## 本质：人员职责的分离

- 代码分离、目录分离只是**顺应职责分离的手段**，分离的本质是让前端、后端开发者各自专注擅长领域
- 代价：前后端接口联调时产生额外沟通成本
- 团队视角：软件开发中最复杂的不是工具、架构或方法，而是人——脱离团队聊架构不合理，架构要为「人」服务

## 好处

- 人员分工明确、各展所长，利于环境维护
- **多端复用**：后端不变的情况下，可以另写一套新前端（小程序、APP），复用同一后端代码

## 适用场景

- **小项目**（用户少、功能简单、团队小）：快速完成需求优先，选团队熟悉的技术栈即可，是否前后端分离没那么重要
- 项目规模与团队扩大后，分离在分工、维护、多端复用上的优势才凸显
- 注意：有些需求前端/后端都能做，但**必须**放在某一端实现，需按职责判断归属

## 前后端分离能提升性能吗？

- **未必**。前端确实可以控制请求时机来优化体验，但现代前端为了提升首屏加载性能，反而流行在**后端渲染**页面（SSR，Server Side Render）：后端先把内容请求好、拼进 HTML 模板再返回前端，前端无需再发请求，更利于首屏加载与 SEO
- 思考：SSR 与前后端分离并非同一维度的问题——前者关乎「在哪里渲染」，后者关乎「职责如何组织」，二者可独立组合（更多架构模式见 [[概念 31 - 架构设计入门（方法与经典架构）]]）
