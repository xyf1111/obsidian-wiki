# 概念 34 - 热数据探测（热 key）

> 热数据是**频繁被访问**的数据，集中访问某个 key 到一定量级会压垮缓存甚至数据库。热数据探测就是「找出热 key」的技术：通过滑动窗口统计访问频率，发现突发热点后第一时间做本地预热、限流降级等特殊处理，提升性能并规避风险。

## 什么是热数据

- 数据可按访问频率分为**热数据、冷数据**（还有暖数据），热数据即很热门、频繁被访问的数据（如热榜新闻每秒成千上万次访问）
- 应对手段：缓存，将数据以 K/V 键值对方式提前存到内存，访问时按 key 找值
- 热数据分两类：
  - **有预期**：成为热门在意料之中，如大促活动中网红代言的爆款商品（双十一购物节）
  - **无预期**：访问量突然飙升——恶意攻击、网络爬虫，或不经意间突然爆火的内容（如突发大新闻把平台打爆）

## 热 key 的常见形态

热 key 是广泛概念，不局限于缓存系统：

1. 数据库中被频繁访问的主键（如爆款应用的 appId）
2. K/V 缓存系统中经常被访问的 key
3. 恶意攻击、机器人刷的请求信息（用户 userId、机器 IP）
4. 频繁被访问的接口地址（如 /app/query）
5. 统计单个用户访问某接口的频率（userId + /app/query）
6. 统计某台机器访问某接口的频率（IP + /app/query）
7. 统计某用户访问某接口特定内容的频率（userId + /app/query + appId）

## 为什么要检测热数据

### 1. 提升性能

- 分布式缓存读取仍需网络通讯，有时间开销；对热点数据提前做**本地缓存（预热）**，可大幅提升读取性能、减轻下层缓存集群压力
- 注意：不是所有数据都应存本地——**缓存级数越多，更新越复杂，数据不一致风险越大**（多级缓存见 [[concepts/概念 26 - 缓存入门|缓存入门]]）

### 2. 规避风险（无预期热 key）

**对数据层的风险**

- Redis 单机正常可支持十万左右 QPS（可集群扩容）；但某商品数据突然爆火或遭恶意请求时，单个 key 的 QPS 可能飙升到**百万、千万量级**——低版本 Redis 单线程工作方式下，正常请求排队、无法及时响应，严重时整个分片集群瘫痪
- 热点 key 突然**过期**：大量请求同时直接砸向数据库，导致数据库挂掉（即缓存击穿，见 [[database/redis/Redis 06 - 过期策略与缓存异常|Redis 过期策略与缓存异常]]）

**对应用服务的风险**

- 每个应用单位时间能处理的请求有限；恶意请求独占大量处理资源后，正常用户的请求无法及时响应

## 如何检测热数据

1. **定义「热」的阈值/规则**：按经验值或系统平均热度定义（如 1 秒内访问 1000 次算热数据）
2. **单机应用**：本地为每个 key 创建**滑动窗口计数器**，统计单位时间访问总数（频率），用集合存放检测到的热 key
3. **分布式应用**：热 key 访问分散在不同机器，无法本地独立计算 → 需要一个独立的、集中的**热 key 计算单元**，流程分四步：

| 步骤 | 内容 |
|------|------|
| ① 配置规则 | 指定热 key 的上报条件，圈出需要重点监测的 key |
| ② 热 key 上报 | 每台机器将自己的 key 访问情况上报给集中计算单元 |
| ③ 热 key 统计 | 收集各应用实例上报信息，用滑动窗口算法计算 key 的热度 |
| ④ 热 key 推送 | key 热度达到设定值时，推送热 key 信息到所有应用实例，各实例将其值做本地缓存 |

检测到热点后即可针对性处理：本地缓存、拒绝恶意用户、接口限流/降级等（高并发防护见 [[concepts/概念 27 - 高并发系统设计实战|高并发系统设计实战]]）。

## 热 key 探测框架的设计要点

高并发场景下设计热 key 探测框架应重点关注的指标：

- **实时性**：热 key 有突发性（甚至 1 毫秒级），必须实时发现并推送
- **高性能**：框架保持轻量、高性能，有效降低成本
- **准确性**：精准探测符合规则的 key，不漏报、更不误报
- **一致性**：保证应用实例与本地缓存的热 key 一致，不出现数据错误
- **可扩展**：key 数量级很大时，集中计算集群可水平扩展

此外还应满足：易接入、业务无侵入、可动态配置、规则热更新、可视化管理等。
