# 职场工作技巧

> 程序员职场个人经验 16 条：写代码只是工作最基础的环节，高效完成工作、获得成长还需要需求管理、节奏把控、日常复盘、快速上手新项目、主动争取晋升、修炼工程师素养、带新人、团队协作、团队管理、试用期总结、代码统计复盘与个人效率方法；工作之外如何自主提升同样关键。

## 核心要点

### 1. 没有明确需求前，不要急着做

- 应届生常见心态：同事提的需求尽快完成，结果理解错意思，交付时才发现返工几周
- **明确需求是工作的第一环**：包括需求的背景、意义、具体功能点
- 需求信息不足时，要求产品经理提供**清晰的需求文档**，确保双方理解与目标一致再设计方案和开发
- **不要接受一句话需求**，需求信息不能只靠口头描述——否则产品抵赖时无法自证，返工也只能怪自己没问清楚

### 2. 上游没有确定前，不要急着开发

- 上游可能来自多个岗位：提需求的产品、核对功能的测试、提供依赖接口的开发、提供资源权限的运维
- 依赖上游的需求，不建议直接上手开发（**可以先做设计**）——上游随时可能改方案、换表名，提前写代码只会返工
- 实例：基于其他部门数据表 A 开发数据表 B，上游表结构变了好几次、表名也换了几次——「等他们把表上线了再说」，省下大量返工
- 紧急需求：拉着所有上游开会核对，把方案先定下来再分工开发；上游一直不确定要主动催，避免需求延期（整个团队都有责任）

### 3. 学会预留空间

- 排期太紧的后果：前一个需求的 Bug 没修完，下一个需求又快到期；系统越大，历史 Bug 浮出水面越多，随时会被抽身去修
- 做法：排期时**多预留时间**，防止前期考虑不到的问题（一个 Bug 可能就要排查一天）
- 心理博弈：提前完成 = 超出预期；准时完成 = 正常；延期 = 「你不太行」——明知 2 天能做完也可以多留些缓冲
- 局限：有时没有选择权（「这个需求明天上线，怎么实现我不管」）

### 4. 学会日常记录总结

- 没成长感、汇报不知道说什么，多半是**没有日常总结的习惯**
- 做笔记/总结的常见坑：想着攒几集一起记 → 越堆越多 → 压力越大 → 索性不记
- 正确做法：**每完成一天的工作、每次做完一个需求、每产出一个阶段性成果，立刻记录**，并定期整理总结、复盘——坚持下来能时刻反思工作节奏与状态
- **落地方式：坚持写日报**——作者在腾讯两年多一直在坚持的习惯（每天下班前用 Typora 记录当天完成的工作、并计划好第二天要做的事），结构可拆成两部分：
  - **今日计划**：列出要做的事，并给每项一个**预期完成时间**，便于把握整体工作进度
  - **实际工作**：记录实际完成的事项与**耗费时间**，与预期对比后复盘——比如计划 1 小时搭好本地项目却花了 2.5 小时，就把遇到的问题单独记录，并思考「下次怎么做才能按预期完成」
- **日报的长期价值**：转正答辩 / 绩效评估 / 职级晋级都要汇报工作内容，平时有日报积累就能轻松汇总（周报也可由一周的日报提炼而成）；养成习惯后每天只需 2-3 分钟，一旦觉得写日报浪费时间，想想「盘点两年工作时无东西可写」的窘境
- **本质上坚持的是「计划」和「总结」**，日报只是一种形式；除了工作内容，还可分类总结用过的技术和平台、读过的文章、写过的 Bug 等，方便日后技术选型、提高效率（呼应第 6 节「多记录多总结」与第 7 节第 3 条「复盘总结」）
- **案例**：作者曾投入大量精力调研某系统的各种技术方案、最后也没给出结论，从高层视角看这段时间「啥代码都没写、零产出」——记录下来后更注重**结果导向**，调整自己在不重要事情上投入的时间（不要为了学技术而学技术）

### 5. 入职新公司，如何快速上手项目

第一次接触已上线的工程代码、且代码量巨大时很容易看懵，可按 6 步走：**获取信息 → 了解业务 → 读文档 → 跑起来 → 读代码 → 上手开发**。

1. **获取项目相关信息**：主动要项目介绍/功能说明文档、业务流程图、历史迭代情况、架构文档、技术选型背景；不懂就问同事（项目背景、有没有文档），有问题一定不能憋着，尽可能多地了解代码之外的东西
2. **了解业务流程**：技术为业务服务——先弄清项目是做什么的、为什么做（背景），对着产品实际体验功能，再重点研究自己要负责的业务模块（历史、业务逻辑）；整体思想是**从整体到局部、由大到小**。避免啥都不懂就接活，替别人收拾烂摊子
3. **阅读项目文档**：README 先扫目录，优先关注**技术栈**和**如何启动**（熟悉的技术栈越多越有底气，还能推断项目结构）；作者没写明技术栈时看依赖管理文件——前端 `package.json`、Java `pom.xml` / `build.gradle` 反推
4. **先把项目跑起来**：拉代码、装依赖、按文档启动，才能更好地了解和调试项目；环境搭建麻烦可请教同事，或用开发机/远程开发环境省事
5. **阅读代码**，遵循两个原则：
   - **由整体到局部**：先看目录结构（哪里写页面、哪里改配置、哪里改接口、怎么切环境），了解模块划分（用户模块、订单模块等），可用 IDE 自动生成 UML 类图
   - **结合业务**：不裸读——前端执行一次操作（如登录），F12 网络请求中找到对应后端请求，再全局搜索定位代码；模拟一次下单操作，理解请求间的顺序与依赖
6. **上手开发**：读代码不能只读，要上手写、执行、调试——新建分支随便折腾（复制代码执行、加日志观察数据流转、Debug）；刚进公司通常先安排 CRUD/小功能帮助熟悉代码，哪怕复制同事代码也能完成工作，但为了长远发展要了解系统上下游与整体架构，提高全局观

作者还提到「打破边界、跨越成长鸿沟」等技巧未展开，可结合个人实践继续补充。

### 6. 提高工作效率的 10 个秘诀

高效不是天赋，是刻意练习出来的方法论——快捷键、无鼠标操作、装效率工具只能提升一点点编码效率，关键在下面 10 条：

1. **完成比完美更重要**：不要过分追求完美，敏捷开发、持续迭代就是这个道理（如果「不完美的完成」对你毫无意义，就按自己的节奏来）
2. **有现成的代码就不要自己写**（学习除外）——重复造轮子是最常见的时间浪费
3. **先想清楚再做**：做项目前充分预研和设计，便于后续扩展，也避免无意义的返工（呼应「先设计再编码」）
4. **大目标拆解**：拆成小任务、做好计划、标记关键节点——既不因目标遥不可及而拖延，也不因盲目乐观而松懈
5. **好作息 + 黄金时间**：养成好的作息习惯，找到自己效率最高的时间段做重要的事
6. **多记录、多总结、定期复习**：记性不好就借助文档、收藏夹软件当「第二大脑」（与第 4 节互补：记录要即时，复习要定期）
7. **积累个人工具库**：配合搜索软件实现随用随取
8. **多交流拓宽知识渠道**：多和团队成员、同行交流，关注优质 UP 主——有些东西只要听说过，用的时候就能省下几个小时的查找时间
9. **找到进入心流的方法**：戴上耳机、嚼口香糖、喝咖啡、深呼吸等，让自己进入专注状态
10. **熟能生巧**：经历过的事情再做一次通常会更快——多做项目、持续积累经验

### 7. 工作后如何自主提升：坚持做 6 件事

> 面对「我是外包，如何提升自己」「工作天天都是重复的 CRUD，如何提升自己」这类提问的统一回答——不考虑工作中被动获得的成长，只讲**工作之外自己主动能做**的事。

1. **每日阅读**：每天读 2 - 3 篇文章（行业趋势 / 技术干货 / 经验分享 / 思维提升），坚持一年就近 1000 篇、相当于几十个教程。来源：想看硬核技术就追大厂技术博客（美团技术团队、阿里技术团队）；了解行业动态看科技资讯（量子位、差评、新智元）；学编程经验与趋势看技术博主（小林 coding、JavaGuide、程序喵、小白 debug、古时的风筝、苏三、阿秀等）
2. **技术学习**：每天抽不到 1 小时看 2 - 3 集教程，一个月就能看完一套课程；每天写 100 行代码、一周做出一个功能，一个月就能做好一个项目——把学习**量化到每天**，比攒大块时间突击更有效
3. **复盘总结**：分三个层次——每天记录完成的工作（哪怕只是贴个需求链接）／每月记录本月重点做的事、完成与学习情况／每半年或每完成一件大事做一次复盘（记录经历 · 过程 · 结果 · 好与不好的地方，防止再踩同样的坑）
4. **整理自己的「弹药库」**：工作五年却感觉和工作一年一样，往往是**没有积累**、把经验忘光了——分类整理自己的 bug 库（解决过的问题）、经验库（踩过的坑）、知识碎片（学过的知识点，做项目时直接复用）、软件库（常用软件与工具）
5. **主动分享**：复盘总结、个人经历、弹药库、知识点、帮人答疑都可以直接分享出去——分享带来关注与认可，形成「正向激励 → 更快提升 → 分享更多」的良性循环
6. **目标拆解**：工作后持续学习最难的是精力和时间，把大项目依次拆成 子系统 → 小功能 → 小模块 → 学一个技术 → 看一套课程 → 看一节教程 → 看 10 分钟教程，拆得足够小、做好计划表按计划执行即可
- **最后的破局思路**：遇到「我无法坚持学习」这类困境，跟改 Bug 一样**先发现问题、再针对性解决**；种一棵树最好的时间是十年前，其次是现在——先从上面任何一件事开始做起，坚持 21 天养成习惯

> 第 3、6 条是对第 4 节「日常记录总结」与第 6 节「大目标拆解」「积累个人工具库」「多交流拓宽知识渠道」的细化；在职成长的心态与自学方法另见 [[编程学习与求职架构]] 三区「在职成长：技术落后时的自救与心态」。

### 8. 创业公司的 5 条工作文化：高效 · 数据驱动 · 用户至上 · 开放包容 · 主人意识

> 来自一家创业公司在「没破产第 100 天」做的文化分享——这些价值观对个人做事同样有参考意义。

1. **追求高效**：不求「追求极致」，但尽量减少重复工作——多利用软件工具、知识沉淀来提效（配置自动化客服、为长期工作编写标准工作流、项目开发共享协作文档、共建知识库）。一旦觉得某项工作花费人力过多，就一起思考如何提效。
2. **数据驱动**：任何工作、判断与决策都避免主观推断，尽量用科学方法和明确的事实数据客观分析。意见不统一时，多数公司的答案是「听老板的」，而更好的答案是「**听数据的**」——用调研、他人的成功/失败案例说服对方，保持理性、拒绝意气用事。
3. **用户至上**：多听（尤其是大多数）用户的声音、避免自嗨；对用户保持真诚，做到 0 投诉、0 黑料；开展活动或做项目前先做一波用户调研再定方案。
4. **开放包容**：大胆表达任何想法或建议，不要因为觉得自己的想法不好就不说——很多价值正来自看似不起眼的点子；营造能自然表达的氛围（如常一起吃饭、随时抛出想法）。
5. **主人意识**：公司里每个人都是「Leader」，无论项目大小都要有独立负责、自主推动事情发展的意识，遇到困难即时记录反馈。把自己当项目的主人而非「机械的打工人」才能把事做好；诀窍是常想一句话「**这件事没有人给你擦屁股**」——写了 Bug 就是自己的责任，不抱怨、不推卸，主人翁意识自然拉满。这也是很多公司招聘要求里都会提到的一点。

### 9. 从 Leader 视角看新人成长：循序渐进 · 代码规范 · 复用 · 清晰需求

> 一位 Java 后端实习生写下自己的实习总结，由 Leader（作者）逐段点评补充——既是新人成长的路径，也是带人的方法。

- **带新人要循序渐进**：别一入职就扔一堆东西、不管不问——合理的培养路径是「先从一个方法写起（熟悉代码）→ 负责一个接口（熟悉前后端对接流程）→ 负责一个功能（收获成果）→ 负责一个模块（承担更多责任）→ 负责整个项目（成为 owner）」，随级别升高逐步负责更多项目（腾讯的晋升体系也类似）。作为新人也可主动按这个节奏适应、逐步参与到开发中
- **代码评审要趁早**：能满足需求但不规范的代码，尽量在代码审核阶段就修正，不要拖到以后——保证项目的可维护性和扩展性（踩过的坑不想再踩）
- **代码复用有原则**：能复用绝不重写、能小改绝不大改；但复用不是强制的——本身差异较大、作用不同的两段代码硬抽成一个公共方法，反而容易出 Bug。抽方法前先想：它的公用性强不强、下次类似场景能不能直接用
- **需求要清晰、设计要前置**：要做什么、为什么要做、为什么用这种方式做，都要清清楚楚，而不是有个大概想法就开干、做完再反复改；小公司最忌讳返工，前期就想清楚可能的风险、做好明确的设计
- **循序渐进地做项目**：在大框架的基础上先把功能跑起来，再完善细节、扩展功能，稳扎稳打
- **把自己当项目负责人**：不要把自己当「实习生」，每位同学都要有独立负责、自主推动事情发展的意识，遇到困难即时记录反馈（即主人翁意识，与第 8 节呼应）；公司内部信息若公开透明，有时间可多读其他项目的代码帮助自己学习

### 10. 创业公司的团队管理实践：知识沉淀 · 茶话会 · 工作记录模式

> 来自一位创业者的管理复盘（公司「不破产第 220 天」）——他没专门学过管理，方法多从前辈处学习、再亲自尝试积累而来；以下三件较大的管理举措，对带团队、带项目同样有参考意义。

1. **共建《技术业务沉淀文档》**：带动开发同学一起梳理团队现有的技术组件与可复用功能（如自建的支付中心、前后端开发模板、搜索中心等），集中成文档便于跨项目复用——核心原则是「**做过一次的功能，绝不重复做第二次**」；这件事源于作者日常记录与复盘的习惯（与第 4 节、第 8 节「追求高效 · 知识沉淀」互补）。
2. **定期茶话会，用「输出」倒逼「输入」**：让成员轮流自主分享自己的工作、积累与经验感悟——如果工作中没有积累和提升，大概率是分享不出来的，所以活动目的不只是让团队互相学习，更是借输出推动成员主动输入知识、提升自己（呼应第 7 节「主动分享」的正向循环，也是费曼式学习的团队化应用）。
3. **工作记录模式随团队规模调整**：人少时用每日工作记录表格密切共享信息；人数变多、各司其职后，集中的日报表不再适用，改用绝大多数公司都在用的**周报模式**，便于定期了解与复盘成员工作——「前人留下来的经典方法确实有道理」，模式要匹配团队当前阶段而非迷信某一种。

### 11. 处理用户反馈与打断的优先级：按紧急程度决定是否中断

> 来自鱼皮的一周工作复盘——专心开发需求时被用户反馈打断是常态，关键是别让「随时响应」拖垮自己的节奏。

- **按紧急程度决定是否立即中断**：专心做需求 A / 需求 B 时突然收到用户反馈（系统哪里有问题、某个功能不太会用），先判断紧急程度再决定是否停下手头工作——紧急的 Bug 和线上问题必须优先修复，非紧急的可以排在手头工作之后。否则很容易一整天都在答疑，新需求只能靠加班补。
- **别默认「所有反馈都第一时间处理」**：曾经始终把用户反馈放第一位，后来发现很多问题用户其实完全可以自己解决，只是换了种偷懒的做法——出了问题直接来问你。不合理分配时间的话，自己的正事反而做不完。
- **本质是把时间的分配权握在自己手里**：在「尽快帮用户」与「保证自己的交付节奏」之间主动找平衡，而不是被动地被每一条反馈牵着走。

### 12. 主动争取成长与晋升：用下一级的标准要求自己

> 来自两段真实的职场经历——「做好本职就能晋升」是常见误解，成长机会往往是主动争取来的。

- **晋升的底层逻辑**：很多人职级晋升时翻车，是因为对晋升的理解有误——**不是做好本职级的事、天天按时完成工作就能晋升**，而是要突破自己、**提前去尝试下一个职级的工作**。比如 T2 要求负责项目的某个功能、T3 要求负责整个项目；若在 T2 时就已经负责了整个项目，跨职级晋升的成功率自然更高。所以要在提升工作熟练度的同时，多用下一级的标准来要求自己
- **有想法要主动向上沟通**：作者刚正式工作时就跟老板说「我想拿五星（公司优秀员工）」，后来老板主动让他独立负责两个新项目的建设，他也借此拿到五星员工、并在同年获得公司内开发竞赛冠军。启发——**如果你有想法，一定要主动、积极地跟上级沟通、传达自己的诉求**，机会常常是自己争取来的（向上管理与汇报的方法见 [[编程学习与求职架构]]）

### 13. 优秀工程师的 12 条素养

> 一位在大、中、小微企业都待过的开发者的总结——优秀的程序员不只是能写一手好代码，更要具备工程素养（与 [[编程学习与求职架构]] 三区「优秀程序员的标准绝不止技术」互补）。

1. 对技术有独特的兴趣和追求，持续学习
2. 有全局观，总能站在更高、更全局的视角去考虑问题
3. 处理事情小心谨慎，而不是凭直觉和过去的经验主观臆断
4. 沟通能力强，能够用方便他人理解的方式来描述问题
5. 强大的设计架构能力
6. 刨根问底，深究问题本质
7. 代码洁癖，精益求精
8. 不止技术，还注重业务底层逻辑，关心用户
9. 执行力强，有责任心
10. 懂得利用自动化工具提升效率
11. 善用绘图、图表来描述技术架构和问题
12. 乐于分享，积极为他人指路

> **实例补充**（来自一位徒弟对导师的观察，把上述特质落到日常动作）：① **全局观**——开会评审方案时主动想「方案对跨团队、整个大项目有没有遗漏 / 风险」，而不是只看自己负责的模块；② **慎行**——设计前先验证可行性（不凭直觉和过去经验臆断）、编码用防御性编程 + 异常处理 + 监控告警、提交前整体通读代码并请同事参与代码审核；③ **刨根问底**——偶发问题也要追到根因（真实链条：程序挂了 → 数据库宕机 → 数据库压力过大 → 共库业务慢查询阻塞，最终把数据库独立迁移根治），「问题不去追溯原因，下次再犯怎么办」；④ **自动化**——「所有人工操作本质上都可以交给机器」，把重复操作（如定时任务失败后重跑）写成程序自动完成；⑤ **带新人**——给新人发挥空间、引导其自己解决问题而非直接给答案，并耐心讲到他彻底理解

### 14. 大厂职场体验：节奏应对 · 保持弹性 · 成长心态

> 来自作者入职腾讯一年（含实习满打满算两年）的复盘——大厂节奏快、资源多、高手如云，如何自处与成长。

- **快节奏工作的应对**：把大的需求**拆分为多个子需求、分清主次、按优先级逐个完成**；做需求前多设计、顾全大局，尽量避免白做和重复工作；工作时保持绝对专注（与第 6 节「完成比完美更重要 · 大目标拆解 · 找到心流」互补）。
- **毕业生别把工作当成全部**：可以有对工作的激情，但**不能 all in 工作、把自己「卖」给公司**，要留出时间学习新东西、培养兴趣（这也是作者做知识分享的初衷之一）。
- **直面互联网的不稳定、保持弹性**：组织架构调整、部门「优化」、需求被砍、项目做到一半中止都是常态——别把自己和公司绑定，多自学、参与开源、提升技术、积累总结，最好的状态是「时刻准备着、随时能跳槽」（与 [[编程学习与求职架构]] 三区「拥抱变化：应对组织调整与被动转岗」互补）。
- **高手如云，把优秀的人当资源**：大厂里学历、资历比你强的人很多，不必妄自菲薄——他们身上有知识、态度与思考方式可以学，都是助你成长的「资源」。选部门优先成熟稳定的业务（新业务更锻炼人但风险大），机会也要**主动争取**（如请导师带你参与需求评审，逐步承担更多责任）。

### 15. 试用期总结与转正：三段式汇报 · 兜底思维 · 排查纪律

> 来自作者在腾讯的三个月试用期总结（部分部门还要当面给领导汇报）——既是转正材料的写法参考，也是新人快速站稳脚跟的成长清单。

- **三段式结构**：试用期总结一般按「**工作 → 成长 → 不足**」三段写。**工作**按本职（完成的需求、排查的线上问题）、培训、基建（补公共知识库 / 脚手架 / 上手文档）、知识（内部技术文章与知识库）、其他分类；**成长**讲习惯养成、主动性、资源收集、沟通、思维、影响力；**不足**坦诚列问题并给出改进方向。平时攒好工作记录，转正答辩 / 汇报时直接汇总即可（呼应第 4 节「学会日常记录总结」）。
- **养成兜底（悲观）思维**：别把第三方依赖都当成可信的——在导师指导下学会凡事**往坏的结果想**，做需求时掌握更全面的信息、提前做好万全兜底，避免「想当然」。
- **资源收集要「人 + 信息」双轨**：通过参与公司 / 部门培训结识优秀伙伴、拓展人脉（人力资源）；持续阅读文档并归纳，整理工作文件夹、网页收藏夹、个人知识库（信息资源）——既方便自己检索，也能帮他人快速了解业务（与第 7 节「整理弹药库」互补）。
- **跨部门沟通要清晰表达**：主动和产品、测试同学沟通，把自己的观点讲清楚便于对方快速理解；表达自己的同时虚心接受他人的信息和建议（呼应第 13 节「优秀工程师素养 · 沟通能力」）。
- **两条真实不足与可照做的改进**：① **效率**——同时处理多个需求易手足无措、计划常被打断；解法是**多做计划、合理安排**，给自己留出完整时间设计方案和写代码，把处理突发问题挪到其他时间（前提是问题不紧急）；② **线上问题排查纪律**——别为了「快速响应」在还没调查清楚时就抢着回复、瞎猜原因，结果往往适得其反，应做充足排查、有清晰判断后再发声。

### 16. 每月代码统计复盘：用「写代码量」量化复盘、定位方向

> 来自作者坚持多年的一个习惯——每月末看一次自己的代码统计（写了多少行、用了哪些语言、各占多少比例），把「这个月干了啥」变成可量化的复盘依据。

- **统计从哪来**：不用自己一行行数，直接看公司提供的**代码提交报告**（按每月 git 提交数自动生成语言饼图 / 代码行数），或用下文的工具自行统计。
- **看统计的 3 点意义**：① **复盘**——回顾本月的工作与效率：代码写得少时，提醒自己工作之余多做项目、别生疏；代码写得多时，又警醒自己**别只沉迷写代码、成为项目和老板的工具人**，多关注业务场景、思考「堆这么多代码实现这个需求是否真有必要」（文档语言占比也侧面反映最近写了多少文档，写文档对项目很有帮助）。② **定方向**——从语言占比确定下阶段的重点学习方向（某月 80% 是 Java，就把重心放 Java）。③ **成就感**——回顾代码量像「打怪升级」，能给下个月冲劲。
- **4 种统计方式**：① **GitHub**——进 `insights` 面板看指定时期的提交数、文件修改数、代码新增 / 删除数；② **编辑器插件**——WebStorm / IDEA / VSCode 等都有代码行统计插件，如 JetBrains 全家桶通用的 `Statistic`；③ **现成工具**——`cloc`，命令行分析本地或 GitHub 代码包，按语言分类统计空行 / 注释行 / 自然行，还能单独分析指定提交；④ **硬核 git 命令**——用 `git log --author` + `awk` 直接统计增删行（见下）。
- **一句话警示**：代码行数本身意义有限（别为了凑行数「一行拆十行」），它更多是**侧面反映没摸鱼 + 帮自己复盘方向**。

```bash
# 用 git 统计某作者的新增 / 删除 / 净增行数
git log --author="_your_name_" --pretty=tformat: --numstat \
  | awk '{ add += $1; subs += $2; loc += $1 - $2 } END { printf "added lines: %s, removed lines: %s, total lines: %s\n", add, subs, loc }' -
```

> 来源：鱼皮·编程导航 / codefather
